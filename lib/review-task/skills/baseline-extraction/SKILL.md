---
name: baseline-extraction
description: Extract and maintain task requirements in the private RC baseline agent, using frozen original sources, candidate batches and compact recovery tools.
---

Preserve the ENTIRE user scope, including process, tooling, agent lifecycle, recovery and UI requirements. User clauses describing RC remain task obligations, not internal prompts.

Record `expectedFiles` in per-outcome metadata (draft `overrides`/group metadata) for exact output paths explicitly required during THIS task, including files not yet created. Keep each path in the original claim text and use category `requirements` for file delivery. Preserve conditions; never derive required outputs from input paths, examples, code references, prohibited outputs, globs, directories, or future application output. Omit this field when no exact output path was specified.

For ordinary draft batches omit unused fields and omit fullTextReason. fullTextReason is exclusively a mode-switch request containing only batchId and fullTextReason; never use it to explain keep/split/merge decisions. Empty collections make no decisions and do not cover any source. Supply every unit's decision and retain all original-read requirements.

- One claim = one user operation/result with its triggers, validation, failures, exceptions and prohibitions. Keep creation fields together, export with privacy, recovery with evidence restrictions, and agent lifecycle with queue/isolation/idle conditions. Split distinct workflows, not sentences or semicolons. Keep clauses identifiable for precise feedback.
- Keep a feature's title, problem background and requested changed behavior together, including across blank separators. Draft merge accepts consecutive nonblank units and retains intervening blanks; never skip a nonblank unit. Do not turn the prior broken behavior into an independent obligation to preserve it. Project command/API catalogues and optional examples are context unless the original requires their execution; preserve actual imperative project rules with their original conditions and prohibitions.
- Compact mode uses `outcomes` with `name`, `file` and local `lines:[start,end]` (or sourceIndex and original lines), plus explicit shared `defaults`. It never accepts text/source/bindings. Use `metadata` only for real differences; omit unused optional fields rather than null. For IMPLEMENTATION choose the actual implementationRole: PRODUCTION, TEST or SUPPORT; PROCESS/ARTIFACT omit implementationRole. Full text is an explicit fallback, not required for split sources.
- Draft mode starts with each original paragraph as one claim. `keep` lists its source-unit IDs; do not split a workflow's conditions into separate checks. Use `split` only for genuinely independent workflows sharing a line, partitioning ALL clause indices exactly once. `merge` joins consecutive paragraphs of the same workflow. Every unit needs a decision; whole paragraph retention is the default. Explicit metadata defaults apply to ADD claims. The program captures exact text, source and current original-read receipts.
- `exclude` is only for unadopted material context or original text already entirely covered by explicit existing claimIds. User statements that a quote/example is unauthorized are ACTIVE constraints: keep them. Other semantic exclusions need fullTextReason. Do not duplicate or silently omit current obligations.
- Check each multi-clause line before choosing keep: independent feature workflows MUST split. Example: “上传前检查类型，失败不得落盘；通知支持免打扰。” has upload validation `[0]` and notification settings `[1]`, two groups. “上传前检查类型；失败不得落盘。” is one upload workflow, keep both clauses together. Paragraph completeness does not imply semantic cohesion.
- Set verificationTarget explicitly: IMPLEMENTATION for delivered runtime behavior, ARTIFACT for document content, PROCESS for actions performed during this task. IMPLEMENTATION also needs implementationRole. Use per-unit `overrides` or split-group `metadata` when shared defaults differ; split mixed proof owners. No target is inferred by the program.
- Classify by the requested deliverable, not keywords. In a code task, plugin agent pooling, baseline reconciliation, compact recovery and phase UI are IMPLEMENTATION capabilities. Actually following a task procedure is PROCESS. ARTIFACT means delivering document contents; a requirement mentioned in notes or an unauthorized example does not thereby become an artifact-delivery obligation.
- Category and proof owner are independent. Imperative project development rules (coding, text encoding, testing, build/tool lookup and similar repository conventions) belong to `developmentStandards`, including when their verificationTarget is PROCESS. Do not file those rules as generic `constraints` or task `workflowSteps`: that loses their development-standard ownership. Preserve the original source authority, applicability, triggers and exceptions; a conditional rule does not become an unconditional action request.
- Use `constraints` for task bounds, exclusions and environment restrictions; `workflowSteps` for an actual task procedure; `requirements` for requested capabilities/deliveries or explicit task actions. Use `acceptanceCriteria` only for original acceptance conditions and `criticalJourneys` only for original required end-to-end journeys. Do not invent, duplicate or recategorize claims merely to populate an enabled metric, or to bypass a disabled one. Categories express the original obligation, not a desired score.
- A section title, command catalogue or example is not an action obligation by itself. Retain a useful heading with its substantive rule when needed for context; never save a bare heading such as a build/testing section label as an independently required execution. Preserve the real imperative below it and its complete conditions.
- Before saving a PROCESS development standard, identify the original instruction/prohibition and its trigger in the selected text. A heading such as "Test Framework Baseline" followed by sample commands does not, by itself, require running all those commands, installing packages, or executing device smoke tests. An available/optional command catalogue remains context unless an original instruction adopts it; its title and your outcome name cannot supply missing authority. A rule about HOW to perform an action when needed must not become a request to perform that action.
- Keep an explicit task action together with its supporting environment bounds when they describe the same operation; use `requirements` with the actual proof owner. Do not split merely at a semicolon and hide the requested action inside a generic environment constraint. A source that only grants permission or lists available tools still does not require every available invocation.
- Set applicabilityKind per original obligation, independently of category and shared batch defaults. Use CONDITIONAL for a rule whose activation depends on an original trigger (such as changing permissions, retrieving documentation, modifying files containing Chinese, or producing a sub-agent handoff); retain that trigger in its text/applicability. Merely belonging to the current repository does not establish that the trigger occurred. Override a shared CURRENT_TASK default for those units instead of making every project rule unconditionally due. CURRENT_TASK remains appropriate for obligations actually required without a further trigger; never invent a condition to exempt one.
- Request `fullTextReason` for existing-claim edits or synthesis; full mode continues in this SAME session/deadline. Prefer `outcome` + `textFrom` using `file` and the part-local lines already shown by tools. Or select `sourceIndex` and ORIGINAL lines, including boundary-spanning lines; request metadata gives each part's startLine/endLine. All selected bytes still need current original-read receipts; do not repeat reads solely for already-issued citations. Use full text/source/bindings for synthesis. Set operation explicitly here or in defaults. Preserve language, IDs and authority. Old notes are not existing ledger claim IDs. Never use non-ADD without an actual current claimId. A changed condition must retain all unaffected conditions within that claim.
- After compact/refresh recover `review_history` state and `baseline_notes` list. Read pending original ranges; revalidate stale notes. Notes are navigation, never evidence. Update stable note keys for unresolved scope and next actions.
- Before finish, check ALL original outcomes, global constraints and deferred work. New tasks do not clear old requirements. Preserve ambiguity as a question. Empty deltas still require complete reading. Only actionable findings reach the host; program supplies the phase UI.
