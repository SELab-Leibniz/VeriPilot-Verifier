name: baseline-extraction
description: Extract and maintain task requirements in the private RC baseline agent, using frozen original sources, candidate batches and compact recovery tools.
---
After saving a candidate, inspect the returned **effective** preview against the complete original sources already read. It is navigation, not semantic approval or new read proof. A claim must have one scoped evidence owner: preserve separate implementation, delivered document, and executed action duties with all original conditions and exclusions. Do not infer owners from a filename extension, remove an umbrella duty, or assume explicit fields make the semantics correct.

If you notice a mistake in saved, unpublished candidates, use the existing `finish_baseline` tool with all current `batchIds`, ordinary `taskClassification` and `summary`, plus `reviseCandidate:{generation,reason}` from current state. This explicitly requests another candidate generation in the same session and consumes one existing repair allowance; it does not finish or publish. Original sources, acknowledged reads, retained claims, turn/token budgets and absolute deadline remain unchanged. Recover state and decide every remaining source unit again. Retry the exact control after a lost acknowledgement; do not guess a newer generation. `fullTextReason` only changes encoding, and does not revise saved candidates. Correct candidates finish normally without an extra mandatory review round. A truncated preview points to the complete existing `review_history` entry; history is never a substitute for original evidence.


Preserve the ENTIRE user scope, including process, tooling, agent lifecycle, recovery and UI requirements. User clauses describing RC remain task obligations, not internal prompts.

Record `expectedFiles` in per-outcome metadata (draft `overrides`/group metadata) for exact output paths explicitly required during THIS task, including files not yet created. Keep each path in the original claim text and use category `requirements` for file delivery. Preserve conditions; never derive required outputs from input paths, examples, code references, prohibited outputs, globs, directories, or future application output. Omit this field when no exact output path was specified.

For ordinary draft batches omit unused fields and fullTextReason. Prefer scoped `operations` with `text` + `sourceFrom:{unitId}` for mixed obligations in one original clause: submit every supported scoped obligation together. EACH sourceFrom operation writes applicabilityKind, verificationTarget and, only for IMPLEMENTATION, its own implementationRole. Any containing batch omits ALL THREE fields from defaults; share applicable category/authority/severity only. The program binds source/kind/subject/excerpt/current citations, never semantic owner/scope or activation. Do not repeat source, bindings or textFrom. fullTextReason is only a mode switch for unsupported selections/revisions. Empty collections/defaults make no decisions. All current original reads remain required.

`preservedSourceUnits` are program-verified KEEP_EXISTING decisions from a new, formally accepted complete source-to-claim certificate. Their entire current claim group is retained without ADD or metadata regeneration; do not keep/exclude them again. Missing/old proof is not preservation: actual current claimIds or identical excerpts alone do not certify complete source coverage. NEW Skill/MATERIAL sources still need their own decisions and complete reads. Never invent a preservation ID, suppress a new user revision or manufacture an old certificate.

Mode switches do not save or consume a batch ID. Use state/response `nextBatchId`; rejected saves reuse that unsaved ID. Full-mode sourceFrom has the SAME raw owner/scope rule as draft; defaults cannot substitute it. Every effective operation still needs `operation`, `category`, `authority`, `severity`, `applicabilityKind`, `verificationTarget`. IMPLEMENTATION needs its chosen role; PROCESS/ARTIFACT omit it. Legacy-only synthesis and homogeneous exact-copy/outcomes keep their effective metadata rules; legacy-only draft defaults still require applicabilityKind. This compatibility proves no semantic homogeneity. Exact copying uses outcome+textFrom, without source. Repair all fields without changing obligations/allowance.

- One claim = one evidence owner for one user operation/result, with all its triggers, validation, failures, exceptions and prohibitions. This evidence-owner rule takes precedence over paragraph or workflow cohesion: delivering code and actually executing a requested verifier are separate obligations even in ONE sentence and ONE workflow. Keep creation fields together, export with privacy, recovery with evidence restrictions, and agent lifecycle with queue/isolation/idle conditions within each obligation. Split distinct obligations, not mechanically at sentences or semicolons.
- Keep scope bounds and exclusions attached to the obligation they constrain; they are not independent PROCESS duties. Draft clause maps are exact top-level semicolon navigation, never inferred sentence boundaries, classification, authority or read proof. Match labels to literal clauses. When one clause mixes evidence owners, use separate scoped text+sourceFrom operations in one batch, sharing the complete original without copying the whole mixed sentence into each owner.
- Keep a feature's title, problem background and requested changed behavior together, including across blank separators. Draft merge accepts consecutive nonblank units and retains intervening blanks; never skip a nonblank unit. Do not turn the prior broken behavior into an independent obligation to preserve it. Project command/API catalogues and optional examples are context unless the original requires their execution; preserve actual imperative project rules with their original conditions and prohibitions.
- Compact mode uses `outcomes` with `name`, `file` and local `lines:[start,end]` (or sourceIndex and original lines), plus explicit shared `defaults`. It never accepts text/source/bindings. Use `metadata` only for real differences; omit unused optional fields rather than null. For IMPLEMENTATION choose the actual implementationRole: PRODUCTION, TEST or SUPPORT; PROCESS/ARTIFACT omit implementationRole. Full text is an explicit fallback, not required for split sources.
- Draft `keep` creates an ADD from a whole original paragraph with ONE evidence owner; it does not retain existing ledger claims. Code + document deliverables also mix owners, just as implementation + actual task actions do: separate their supported obligations with sourceFrom, rather than assigning the whole sentence one target. Do not split an obligation's conditions into unrelated checks. Use split only at faithful existing clause boundaries, partitioning ALL indices exactly once; merge only consecutive same-owner paragraphs. Every unpreserved original unit still needs a decision.
- `exclude` is only for unadopted material context or an exact whole-original duplicate. For user text, ALL referenced claimIds must exist and at least ONE current USER_EXPLICIT USER_MESSAGE claim's text must equal the entire original unit after trimming outer whitespace. Semantic overlap, paraphrases and several partial claims are insufficient. Do not retry equivalent IDs after rejection. Preserve new duties through keep/merge/split or scoped operations+sourceFrom. Genuine existing-claim revisions/unsupported selections may request ONLY batchId+fullTextReason. Non-ADD needs the actual current claimId. Denials of authorization remain ACTIVE constraints; do not duplicate or silently omit obligations.
- Check each multi-clause line before choosing keep: independent feature workflows MUST split. Example: “上传前检查类型，失败不得落盘；通知支持免打扰。” has upload validation `[0]` and notification settings `[1]`, two groups. “上传前检查类型；失败不得落盘。” is one upload workflow, keep both clauses together. Paragraph completeness does not imply semantic cohesion.
- Choose verificationTarget for EVERY actual obligation: IMPLEMENTATION for delivered runtime behavior, ARTIFACT for document content, PROCESS for actions performed during this task. SourceFrom requires this choice on EACH operation before defaults merge; its batch defaults omit target AND role. IMPLEMENTATION also requires its own PRODUCTION, TEST or SUPPORT role; PROCESS/ARTIFACT omit it. Legacy-only selections keep their explicit shared/per-item metadata rules. Removing a stray PROCESS role cannot fix a document already assigned the wrong target. Do not change the real target just to pass validation. Actual verifier execution remains PROCESS; source code or test authorship cannot fulfill it. A syntactically explicit choice can still be semantically wrong; the program never infers or repairs it.
- Classify by the requested deliverable, not keywords, filenames or source kind. Writing a usage guide is a document-content obligation even without a specified filename: choose ARTIFACT and omit expectedFiles if no exact path was required. Describing a feature in a document does not require implementing that feature; implementing code that processes documents is still runtime behavior. Actually following a task procedure is PROCESS. Input notes/examples do not themselves create new document-delivery obligations.
- Source kind records provenance independently of proof owner: adopted material requirements about runtime behavior remain IMPLEMENTATION. Existing input tools, example source code and their individual lines do not automatically create new ARTIFACT delivery duties. Unadopted context may use the existing guarded exclusion mechanism; preserve genuinely requested verifier execution as PROCESS. Do not infer owners from filenames, keywords or source kind, or aim for a fixed claim count.
- Category and proof owner are independent. Imperative project development rules (coding, text encoding, testing, build/tool lookup and similar repository conventions) belong to `developmentStandards`, including when their verificationTarget is PROCESS. Do not file those rules as generic `constraints` or task `workflowSteps`: that loses their development-standard ownership. Preserve the original source authority, applicability, triggers and exceptions; a conditional rule does not become an unconditional action request.
- Use `constraints` for task bounds, exclusions and environment restrictions; `workflowSteps` for an actual task procedure; `requirements` for requested capabilities/deliveries or explicit task actions. Use `acceptanceCriteria` only for original acceptance conditions and `criticalJourneys` only for original required end-to-end journeys. Do not invent, duplicate or recategorize claims merely to populate an enabled metric, or to bypass a disabled one. Categories express the original obligation, not a desired score.
- A descriptive section label, command catalogue or example does not by itself require execution. A heading containing an actual imperative/prohibition may be normative: preserve its complete section qualifiers and exceptions, without guessing force from Markdown or turning every label into an action. Preserve real imperatives in headings/body and their complete conditions.
- Before saving a PROCESS development standard, identify the original instruction/prohibition and its trigger in the selected text. A heading such as "Test Framework Baseline" followed by sample commands does not, by itself, require running all those commands, installing packages, or executing device smoke tests. An available/optional command catalogue remains context unless an original instruction adopts it; its title and your outcome name cannot supply missing authority. A rule about HOW to perform an action when needed must not become a request to perform that action.
- Keep an explicit task action together with its supporting environment bounds when they describe the same operation; use `requirements` with the actual proof owner. Do not split merely at a semicolon and hide the requested action inside a generic environment constraint. A source that only grants permission or lists available tools still does not require every available invocation.
- Choose applicabilityKind per original obligation: sourceFrom requires it on EACH raw operation and forbids it in batch defaults. Use CONDITIONAL for an original activation trigger; preserve the trigger/limits in text and natural applicability. Repository membership does not prove activation. Internal behavior that must be implemented remains a current implementation obligation, not an external exemption because no matching input was observed. CURRENT_TASK is for obligations without another activation trigger; FUTURE/UNKNOWN cannot grant PASS. Legacy-only selections retain existing defaults/overrides, not a semantic guarantee. Never invent a condition or pick a tag just to evade an obligation.
- Request fullTextReason only for existing-claim revisions or unsupported selections; it continues in this SAME session/deadline. Prefer outcome+textFrom for exact copying, sourceFrom for finer semantic separation, legacy text+source+bindings only when unavailable. Keep conditions/exceptions/mandatory force. SourceFrom defaults share applicable category/authority/severity; each operation chooses scope/owner and only IMPLEMENTATION has role. Never repeat acknowledged reads solely for citations. Full mode requires operation; non-ADD needs actual claimId. Genuine scope revisions remain possible via the guarded revision flow; preserve unaffected language/authority, not earlier semantic mistakes. Notes are not claims.
- Full mode has THREE mutually exclusive encodings. Synthesis text+sourceFrom:{unitId} lets the program bind the complete acknowledged original, never supply source/textFrom/bindings. Legacy synthesis text+source+current batch bindings remains available when unit selection is unavailable; omit textFrom/outcome. Exact copying uses a SHORT outcome (at most 100 characters)+textFrom with exactly ONE file/sourceIndex; omit source and normally text (any supplied text equals the captured original). Never attach exact-copy coordinates to synthesized text. No encoding infers a semantic owner or grants unread evidence.
- After compact/refresh recover `review_history` state and `baseline_notes` list. Read pending original ranges; revalidate stale notes. Notes are navigation, never evidence. Update stable note keys for unresolved scope and next actions.
- Before finish, check ALL original outcomes, global constraints and deferred work. New tasks do not clear old requirements. Preserve ambiguity as a question. Empty deltas still require complete reading. Only actionable findings reach the host; program supplies the phase UI.
- finish_baseline completes a local candidate, not independent semantic acceptance. After the native run settles, the parent may independently audit every original and the actual effective ledger. Its source-grounded omission/owner/condition feedback returns to THIS extractor through the existing repair generation. Preserve originals, triggers, exceptions and unaffected duties; do not treat reviewer feedback as new USER authority. This consumes the original shared turns, original repair allowance and absolute deadline. Do not create another reviewer or assume navigation units, exclusions, NO_CHANGE or a prior PASS waive an original. An unknown extraction remains incomplete; missing business execution proof for an already retained duty is a separate downstream judgement.
