---
name: code-understanding
description: Trace implementation and compatibility obligations through public entry points, source relationships, and existing tests when the semantic_graph tool is available.
disable-model-invocation: true
---

Use semantic_graph early for source changes. Start with the public entry point, shared helper, or state field. If the name is unknown, use `search` with a short behavioral phrase to find symbols and existing tests. Ask for `context` using an exact symbol, preferably `Type.method`. Use `outline` when you have a file path. Scope ambiguous hits to a file.

Before choosing an implementation, distinguish three parts of each affected contract: the input domain where the operation is meaningful, the rule applied within that domain, and the independently observable entry points that promise that rule. A request can change the rule while preserving the input domain and public signatures. Keeping a signature does not imply keeping its old decision semantics; adding a correct private path does not update other public entries that still promise the same behavior.

Build a small set of source-backed checks rather than a list of suggestions. For each decisive check, name the actual entry, input and prior state, relevant configuration or dependency outcome, and expected return/state/effect. Separate a newly required positive case from a nearby unchanged boundary case. Use only conditions present in the task-start source or request. An input normalized to a display fallback or sentinel is not thereby a valid target for persistence or an external action. Follow normalization to the first effect before deciding that a missing or malformed value qualifies for the new rule.

Use incoming/context to find sibling callers and direct consumers of the shared predicate, not just the route chosen for the new implementation. If several public entries express the same decision, compare their behavior under the same active configuration. Preserve genuinely distinct semantics; do not infer that all similarly named functions are interchangeable. Cite the source that establishes the relationship. A task can require semantic consistency without mentioning the helper's name.

When the existing generic public operation already owns the requested decision, prefer repairing that owner over duplicating its rule in a private path. Preserve its signature and unaffected conditions. Exempt it only when source establishes deliberately different semantics, rather than because its old body omits the new rule. Keep separate checks for the public owner and a consumer when they are independently observable.

Challenge a claim that a public decision must keep its old semantics. Is that scope explicitly part of its contract, or inferred from the old body, a list of existing checks, the absence of a mode parameter, or tests running only under default state? Those facts do not by themselves exempt an entry from a requested rule change. Inspect ambient configuration and supported callers, then seek a counterexample changing only the requested condition. Likewise, preserve an old input-domain boundary unless the request actually changes it. A source-supported counterexample is a useful check; an imagined edge case is not a new requirement.

`context.stateDependencies` locates state read by an entry when the graph knows a writer, with a few writer and sibling-reader locations. Inspect those sources to discover ambient configuration, setup changes and other operations consuming the same state. A function can depend on current context without accepting a mode argument. These are bounded navigation facts: no listed writer is not proof of immutability, and a shared state read alone does not prove that two operations have identical contracts.

For each decisive path, distinguish the public boundary constrained by the request, the actual dependency outcome, and the first observable effect. Use the graph to locate the caller and its test setup, then read the substitute configuration and returned fixture. Keep separate checks for a caller guarantee and a callee guarantee; a scenario invoking only the callee does not exercise the caller.

- Use `incoming` on the exact symbol to find callers and existing tests. Use `depth:2` or `depth:3` when a shared helper reaches the public entry point through other methods. Read dependency substitutes, setup and assertions separately. A setup call may only prepare a different operation: identify which expectation the request explicitly changes and which later effects remain required. Adding a new dependency or updating a mock does not explain away an unrelated failure. For a mocked or injected data loader, follow each required field from its returned value to observable caller state, including later fetches, merges and fallbacks that can replace it.
- When an import cannot resolve, use `dependencies` on the importing file. A `case-mismatch` shows the requested and existing paths. Verify the actual file name and import spelling, especially after a case-only rename on a case-insensitive filesystem.
- Use `outgoing` on the public entry point. Follow calls and writes to the observable result, including the first write, external call, or returned value that matters. For a restriction, find the condition that prevents the first forbidden effect at each independently callable public boundary. `testBoundaries` joins a caller's dependency call to test-helper arguments, setup scopes and later call/write sites. Read those locations to confirm what is actually substituted and returned; the graph does not infer interception or branch reachability. For a caller-owned no-effect guarantee, ask whether that effect remains prevented when the existing substitute returns success. A lower helper's rejection alone cannot settle this question. Follow success, returned failure, and thrown failure separately before deciding that a check is covered.
- Use `outgoing` with `depth:2` or `depth:3` to follow resolved calls across helper layers. Each callee is expanded once, with its first resolved route in `via`. Follow pagination and inspect source for the actual branch conditions.
- For a multi-step mutation, list each resource changed or destroyed and the prior state needed to restore it. Trace failure after each completed write through its compensation and final reload. Restoring references needs valid underlying resources, including any IDs allocated during recovery. Check awaited writes after a catch block and exceptions inside recovery itself.
- When an operation must recover or roll back, use `outgoing` on the code that reads the state before writing. Check `catchReturns` on called functions and read the return and its caller. If a failed read can produce the same value as a successful empty read, trace whether the caller proceeds with a write or accepts that value as confirmed state.
- Identify the shared owner before suggesting a new path. Look for other public callers that would retain the old behavior, and for adjacent defaults, fallback inputs, or state transitions that existing code and tests depend on.
- For a rule shared by several operations, locate the common predicate and inspect its callers' actual arguments. Trace modes and feature metadata through helper parameters to each consuming operation. For a merge with cached state, identify the fields supplied by the fresh result and the fields the original request explicitly preserves, then follow both to the public result.
- When a shared operation gains a dependency, follow its incoming callers through to their own results. Compare adding a fetch above the established service boundary with enriching the existing return value inside its owner. The latter can preserve callers and their test substitutes without changing the requested behavior. A wrapper with the same final return type can still bypass a substituted method. Inspect how the test framework intercepts calls, especially inside the same class. Treat newly missing mocks as a signal to reconsider the implementation boundary, not authorization to alter otherwise valid setup. Preserve unrelated observable effects; replace only assertions directly contradicted by the request, explaining the distinction per assertion.

  For example, a caller test replaces `load()` with a fixture. Adding `extraRead()` in the caller reaches real I/O outside that fixture; enriching `load()` internally can preserve the caller while separate tests exercise the loader. The caller test intentionally does not execute the substituted implementation. Changed argument matching or timing can break the same boundary even with unchanged method names. Choose placement from the requested observable behavior and existing callers, not the user-interface wording. When the caller itself owns a no-effect guarantee, trace its successful substitute to the first effect and find the condition that prevents it; do not assume the real callee will reject instead. This does not require duplicate guards at boundaries outside the requested guarantee.
- When a string-valued contract changes, use `context` on its type and `literal` with each introduced, changed or removed value. Check the remaining switch branches, producers, renderers, and tests. Trace returned or persisted discriminators through their consuming fields and preserve the contract's vocabulary and meaning. A matching string is a location to inspect. Confirm the enclosing type or input before linking it to the contract.
- Trace the origin and validation of the inputs to any new effect. Separate values used for display or logs from validated targets for a write or external call. Follow missing, empty, and invalid inputs through the same public entry point and verify where each path stops.

Choose a few decisive paths. For a no-effect claim, identify the entry point, input condition, dependency outcome, guarding condition and first prohibited effect. A scenario should name any existing setup that changes that path. During Stop, verify this chain against current source even when the frame says it is covered; guidance is a hypothesis, not proof of conformance. A whole-suite failure that passes alone can be introduced by changed setup, cleanup or dependencies; compare its task-start result before explaining it. Include decisive locations in guidance or findings. Deviations can attach narrow path/ranges directly; no session-local citation ID or mandatory prior read is required. If the graph misses a call or reports a partial index, follow the original source and tests directly.
