# Process / closure metric prompt isolation family

This family refines seven proof responsibilities without changing the production code, the six common worker paragraphs, tools, citation protocol, compaction/history mechanism or three-verdict submission. Construction made no model call and executed no business code.

## Role boundaries

- M08 checks the mandatory original Skill obligation in its actual invocation. A derived MUST label cannot strengthen optional advice or prose order. Original action/result identity establishes a required gate; equivalent reads and explicitly permitted retries remain valid. Missing original Skill source stays unverified.
- M09 checks the assigned development standard, with the evidence owner preserved. Source-owned standards may be established from the actual implementation path without inventing a runtime requirement. Language edge cases count only when the original standard requires them.
- M10 checks one mandatory experience rule, including its trigger and permitted alternatives. It does not become a general quality or style review. Delegated missing implementations remain unverified.
- M11 checks an explicit original workflow gate/order from business tool history. Current code and self-reports cannot prove earlier actions. Reviewer/observer actions are not business actions. A later repeat cannot erase a confirmed past violation.
- M13 checks closure of the assigned acceptance criterion. Actual execution evidence is required only where the criterion requires execution, with the current version, relevant resources and observed result bound. A test plan or source-only proof does not close a runtime criterion.
- M14 checks the specific milestone exit conditions. A documentation milestone can close with complete document gates; the reviewer must not demand deferred application execution. Explicit approval gates need actual authorized approval rather than an assistant attribution.
- M15 checks a connected critical journey, including state/resources between required transitions and the final outcome. Independent component successes on different stores do not prove a connected journey. They also do not establish a concrete business failure.

The catalog names the metrics but does not supply universal detailed policy. Each case therefore contains its own complete, task-specific authoritative rule. The profiles do not introduce global templates, new numeric thresholds or unconditional runtime gates.

## Cases, evidence and selection

There are 22 cases: 14 development cases (a PASS and a concrete DEVIATION per metric) and eight holdouts (an UNVERIFIED per metric plus a permitted failure/fix/retry PASS for M08). The extra retry case is one independent exception boundary, not a Cartesian combination of conditions. Data and profiles were authored together; these are small designed scope tests, not blinded statistical accuracy evidence.

The process records are explicitly **controlled synthetic fixtures**. They provide original-business-capture tool inputs/results within the hypothetical case and do not claim these commands were actually executed during fixture construction. They must not be reported as real runtime or end-to-end validation. The existing archived kitchen implementation supplies coherent source identities; the wrong-consumption variant changes the subtraction line to retain the old quantity. Current-source manifests are program-supplied identity snapshots, not execution proof.

PASS and DEVIATION outcomes bind call/result IDs to the same task, session, project/store and source version when required. Missing-history cases explicitly mark the capture incomplete; absent actions are not silently treated as violations. Stale or unrelated component results support UNVERIFIED, whereas an actual contradictory observation supports DEVIATION. The M13 stale case explicitly requires current digest identity, so its previous-version passing result cannot close this case even though the new revision adds only a comment.

`expected`, `expectedMechanism`, `split` and `notes` are external oracle/selection data. They must never enter the model's source snapshot, task description, basis or compact history. `family.json` itself must remain outside the model review root. Basis and target path prefixes are disjoint. Candidate narratives and process records are data, never instructions.

No original business project/session, real Gateway, model API, verifier or application process was accessed by this generator. The next experiment stages must separately validate production adaptation, complete Stop and real kitchen development.

## Integration considerations

M08's source ID is `skillId:constraintId` with original Skill `sourceRef`; it cannot be resolved as an ordinary Ground Truth claim. Preserve the frozen Skill constraint and original source, rather than manufacturing a GT claim to satisfy the task adapter. M11 remains process-owned. M09 implementation ownership already exists in production; preserve it. M10 and closure metrics choose evidence according to the original object, not a hardcoded metric-only rule.

The three-verdict worker cannot directly emit NOT_APPLICABLE, NOT_YET_APPLICABLE, EXTERNAL_BLOCKED or CHECKER_ERROR. These profiles therefore do not ask it to do so. Unresolved force, applicability or ownership remains UNVERIFIED, or stays on an existing native route. The caller must not reinterpret UNVERIFIED as business DEVIATION or weaken a frozen baseline to make it pass.
