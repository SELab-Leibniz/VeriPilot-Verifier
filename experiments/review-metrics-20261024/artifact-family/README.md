# Artifact-family metric isolation data

The five profiles refine proof responsibility while retaining the production worker's six common system paragraphs, read-only tools, cite IDs, compact/history mechanism, and small decision shape. No production files were changed and no model was called while constructing these data.

## Responsibility boundaries

- M02: qualification of the assigned requirement/decomposition; concrete and verifiable meaning consistent with the authoritative obligation. It does not require working implementation or actual test results.
- M03: coverage of the assigned acceptance obligation by formal test specifications or executable checks. It does not require those checks to have run.
- M04: quality of the assigned test contract's setup, stimulus and discriminating oracle. A complete, correct unexecuted contract can qualify.
- M06: qualification of the assigned acceptance criterion, including observable outcomes and condition/exception semantics. It does not substitute test-plan completeness or execution closure.
- M07: actual endpoint resolution and semantic ownership of one explicitly required traceability relation. Correct-looking IDs are insufficient; extra endpoint types are not invented.

The current catalog names these metrics but does not define a universal detailed quality rubric. Therefore each fixture's authoritative basis explicitly states its task-specific qualification or mapping obligation. The append prompts do not impose a new ID scheme, template, technical detail threshold, number of atomic subrequirements, or code/run evidence requirement. This avoids silently strengthening acceptance conditions through the reviewer prompt.

## Cases and oracle audit

There are 15 small semantic cases: three per metric, with one PASS, one concrete DEVIATION and one UNVERIFIED. All deviation cases are marked holdout; the remaining ten are dev. This split tests negative generalization after prompt selection, but its label distribution is intentionally not treated as representative production data. The design author knows the data and the five profiles; this is not a blinded benchmark or a statistical quality estimate. Root will run a separate fixed worker baseline and candidate against the exact same snapshots and independently review diagnoses.

PASS candidates use genuine alternative wording or labels and sufficient evidence for exactly the metric's scope. Their lack of application code or actual execution must not force UNVERIFIED for document-design metrics. DEVIATION candidates provide complete current content that concretely weakens an authoritative input type, omits a required store observation, uses a wrong numeric oracle, collapses temporal image states, or resolves a trace link to an unrelated check. The conditions behind these expectations are included in the frozen basis; they are not conclusions inferred from expected labels.

UNVERIFIED candidates explicitly declare an incomplete snapshot or inaccessible archived body. The available index does not claim to be the requested candidate body and does not prove the body is defective or absent in the actual project. It is therefore insufficient for either PASS or a business DEVIATION. This checks evidence ownership, not file-existence acceptance. Every such fixture has at least one real project target file for honest citations or navigation.

The expected label and expectedMechanism fields belong to the external oracle. They must not be copied into the worker's basis, candidate files, initial prompt, or compact history. The family JSON itself must stay outside the review root. Basis and target path prefixes are disjoint. There are no model-directed instructions in candidate files, hidden test execution results, credentials, or business-code execution requirements.

The cases intentionally do not enumerate combinations of clauses. One assigned obligation plus the applicable conditions is checked; a single supported contradiction suffices for DEVIATION. These data are small tests of proof scope, not a simulation of long-task context stress. The existing complex and long-session suites remain necessary.

## Supplemental file quality during integration

The previous native Stop instructions also request fileAssessments for the current quality of requested deliverable files. Once every metric routes to the task worker, that duty must be preserved explicitly. A metric object's PASS does not establish entire-file quality.

The minimal compatible design is one additional task per requested deliverable file, using the same worker and the file's intended artifact obligations plus relevant common constraints. Adapt its short verdict and program-resolved citations into the existing fileAssessments schema and merge path. Do this once per file under the same parent deadline, not once per metric or every obligation combination; do not alter the metric population or start a summarizer. Unknown expected file scope or missing quality baseline yields explicit UNVERIFIED. Do not silently remove this duty or promote M01/M02 PASS to file PASS. The existing quality wording is at lib/runtime-v2/orchestrator.mjs around line 1242 in the c64969a baseline.

## Reproduction

build-cases.mjs writes family.json deterministically. Use root's shared all-metrics lab runner for paired live review; the generator is not a model runner. Preserve the family hash before observations and retain mismatches rather than rewriting an expected label after seeing a model answer.
