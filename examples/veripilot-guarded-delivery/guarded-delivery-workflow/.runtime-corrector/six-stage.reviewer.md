# 六阶段节点审阅标准

只审查当前正在写入的 Stage 产物。上游文档和代码证据均为只读。

## 通用标准

1. “文档目标、输入依据、核心结论、追溯关系、风险与开放问题”必须相互一致。
2. 所有结论必须有可定位证据；无法确认的内容必须标记为假设或开放问题。
3. 不得把建议、推测或未来可能性写成已经实现或已经获批的事实。
4. 不得擅自扩张用户范围，也不得静默删除稳定标识、约束、非目标或异常路径。
5. Finding 必须指向当前目标文件；不得建议修改前序产物或代码事实源。

## requirement-analysis

- 明确业务目标、角色、主场景、范围、非目标、约束和验收点。
- 为需求和验收点分配稳定 ID，例如 `REQ-001`、`AC-001`。
- 区分用户事实、仓库事实、假设和待确认问题。
- 不提前虚构模块、接口或实现承诺。

## requirement-breakdown

- 每个拆分项追溯到一个或多个需求 ID。
- 拆分项边界清楚、可独立验证，合起来覆盖全部需求和验收点。
- 不合并语义不同的需求，不把实现偏好伪装成产品需求。
- 保留范围、非目标、约束和开放问题。

## code-understanding

- 每个代码结论引用真实项目相对路径、符号、入口或调用关系。
- 区分已实现行为、可复用能力、修改候选和未知项。
- 不引用不存在的文件、类型、函数、接口或测试缝。
- 只解释与当前需求有关的代码。

## solution-design

- 每个需求拆分项映射到方案组件、接口、数据流或关键决策。
- 设计使用的模块、接口和依赖与代码理解证据一致。
- 明确主流程、失败路径、状态变化、兼容性和修改边界。
- 不引入没有需求依据的新产品能力。

## manual-test-cases

- 每个需求 ID 和验收点至少被一个人工测试用例覆盖。
- 覆盖正向、异常、边界、状态变化和必要回归场景。
- 每个用例包含前置条件、步骤、测试数据和可观察预期。
- 不存在无法追溯到需求或方案的孤立用例。

## dt-design

- 每个自动化场景追溯到需求拆分项和方案决策。
- 驱动路径、接口、测试缝、数据准备和可观察点在真实代码中存在。
- 断言验证业务结果或稳定契约，避免依赖偶然实现细节。
- 说明测试层级、隔离、清理、稳定性风险和暂不自动化项。
