# 鸿蒙应用 IR 纠偏知识

`default.json` 是面向不同类型鸿蒙应用手写的轻量纠偏标准。它检查需求是否足以指导实现与验收，不规定某一份样例文档的章节外形。

## 判断原则

- 内容优先于排版：允许按项目规模合并或拆分章节，也不要求固定章节顺序；
- 最小但完整：所有 IR 都要交代目标与范围、功能需求和可验证验收标准；
- 平台明确：文档要能识别目标鸿蒙技术栈，并尽量说明 API 基线和设备形态；
- 需求可执行：功能描述应覆盖用户动作、系统响应、数据变化和关键异常路径；
- 不凭空扩张：范围外能力应显式记录，未知项应说明原因，而不是用占位符糊弄；
- 能力按需检查：只有文档实际使用敏感能力、网络服务、持久化或外部开发服务时，才要求补充相应约束。

## 通用必备信息

- 一个能识别应用与文档用途的 H1 标题；
- 应用解决的问题、本期范围与边界；
- 可实现的功能需求；
- 可观察、可勾选的验收条件；
- 目标用户或使用场景；
- 鸿蒙平台、版本/API 和设备范围（已知时给出，未知时说明决策条件）。

章节可以使用“产品概述”“背景与目标”“核心功能”“完成定义”等自然名称。别名只用于识别语义，不代表推荐模板。

## 条件检查

- 定位、相机、麦克风、相册、通讯录、日历、通知、蓝牙等能力：检查权限、授权时机、最小化原则和拒绝后的行为；
- 网络、账号、支付、地图或云服务：检查断网、超时、服务不可用和配置缺失时的行为；
- 本地保存、数据库或 ArkData：检查关键字段、约束以及创建、更新、删除或清理规则；
- Kit、SDK、AGC、密钥、证书或第三方服务：检查依赖、配置和不可用条件。

## 文档质量

- 必需章节不能只有标题；
- Markdown 标题层级不能跨级；
- 文档内锚点必须指向已有标题；
- `TODO`、`TBD`、“待补充”等无解释占位内容会被诊断；
- 多个关联 IR 中显式声明的需求 ID 不能重复。

插件只返回诊断和建议 Diff，不会修改被检查的 IR。
