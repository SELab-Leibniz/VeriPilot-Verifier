先建立正确心智模型

Stage 不是一段隐藏代码，而是一组项目自己拥有、随时可审计的策略。

注册artifacts[] 声明 stage 与文件
启用enabledStages 决定是否工作
检查rules 执行确定性判断
审阅reviewer 处理语义与取舍
纠偏主 Agent 最小修改并复检
i
注册 ≠ 启用

把 app-design 写进 artifacts[] 只是安装；只有它同时出现在 enabledStages，写入 design.md 才会触发纠偏。

2

在 config.yaml 注册 app-design

下面是一个可直接运行的“仅自定义 stage”完整配置；已有项目只需合并 artifact 项。

.runtime-corrector/config.yaml
version: 1

# 先保持关闭，完成核对后再用命令开启
enabledStages: []

artifacts:
  - name: app-design-document
    stage: app-design
    type: app-design
    format: markdown
    patterns:
      - design.md
      - docs/design.md
      - "**/design.md"
    relatedPatterns:
      - requirements.md
      - "**/requirements.md"
    relatedRoot: project
    rules:
      enabled: true
      file: app-design.rules.yaml
    review:
      enabled: true
      criteria: app-design.reviewer.md

ignorePatterns:
  - "**/.runtime-correction/**"

output:
  persist: true
  mode: centralized
  directory: .runtime-correction

limits:
  maxRelatedFiles: 20
  maxFeedbackChars: 24000
  maxReviewerChars: 12000

逐项理解配置

配置项本例值它控制什么
version1策略文件格式版本。当前必须为 1。
enabledStages[]当前启用列表。空列表表示 stage 已注册但不触发，便于上线前检查。
nameapp-design-documentartifact 的可读标识；建议稳定、明确。
stageapp-design控制命令使用的 stage 名。必须小写字母开头，只含小写字母、数字、连字符，最多 64 字符。
typeapp-design诊断结果中的 artifact 类型标签，帮助编排器区分产物。
formatmarkdown产物格式；可选 markdown、json、text、auto。
patterns**/design.md哪些写入会触发。* 不跨目录，** 可跨目录。
relatedPatterns**/requirements.md检查时一并读取的上下游证据。本例让 reviewer 能对照需求。
relatedRootproject相关文件从项目根查找；若设为 artifact-directory，只从 design.md 所在目录查找。
rules.enabled / filetrue / app-design.rules.yaml显式控制节点硬规则；关闭只需改为 false。
review.enabled / criteriatrue / app-design.reviewer.md显式控制节点语义审查；criteria 是附加标准，不再兼任开关。
ignorePatterns.runtime-correction永不触发的路径，避免诊断产物反过来触发自己。
output.persisttrue每次当前快照检查后是否写诊断留痕。
output.modecentralized诊断集中写入一个目录；adjacent 则写在产物旁边。
diagnostic + diffalways paired每次匹配写入先执行已启用检查；存在 review.enabled: true 时才创建隔离 fork。随后成对创建 diagnostic.md 与 patch.diff。
limits20 / 24000 / 12000分别限制相关文件数、反馈字符数、reviewer 字符数，防止范围失控。
patterns决定左侧检查谁只有命中 **/design.md 的写入才进入工作台。
rules形成右侧硬规则结构、数量与禁用文本都能确定复现。
reviewer形成右侧 Agent 标准语义问题必须引用左侧文档和上游证据。
+
合并到已有配置时

在现有 artifacts: 列表末尾追加本 artifact；不要新建第二个 artifacts:。暂时不要把 app-design 加进 enabledStages，先完成后面的核对。

3

编写可解释的硬规则

只写机器能够确定判断的结构与文本，不让规则“猜”架构好坏。

.runtime-corrector/app-design.rules.yaml
version: 1

rules:
  - id: DESIGN-GOALS
    type: require-heading
    heading: 设计目标
    severity: error
    suggestion: 增加设计目标，并说明它对应哪些需求。

  - id: DESIGN-ARCHITECTURE
    type: require-heading
    heading: 架构与模块
    severity: error
    suggestion: 列出模块职责、边界与依赖方向。

  - id: DESIGN-INTERACTIONS
    type: require-heading
    heading: 关键交互
    severity: error
    suggestion: 描述关键流程、状态变化与失败路径。

  - id: DESIGN-ACCEPTANCE
    type: require-checklist
    under: 验收检查
    minimum: 3
    severity: error
    suggestion: 至少增加 3 条可观察、可勾选的设计验收项。

  - id: DESIGN-PLATFORM
    type: require-text
    values:
      - HarmonyOS
      - Android
      - iOS
      - Web
    severity: warning
    suggestion: 明确目标平台及平台约束。

  - id: DESIGN-NO-PLACEHOLDER
    type: forbid-text
    values:
      - TODO
      - TBD
    severity: error
    suggestion: 补全占位内容，或删除不在本期范围内的段落。

本例使用的 4 种规则类型

require-heading标题存在适合规定设计文档骨架；可通过 aliases 接受同义标题。
require-checklist清单数量目标章节内必须有 - [ ] 或 - [x] 项。
require-text至少一项本例要求出现至少一个目标平台；warning 不会变成 failed，但最终状态为 warning。
forbid-text禁止文本拦截未完成占位符。默认区分大小写，可设 caseSensitive: false。

severity 可选 error、warning、info；单条规则可用 enabled: false 暂停，保留 ID 方便审计。

4

把语义判断交给 reviewer

Reviewer 解决“是否忠实、是否合理”，硬规则解决“是否存在、是否符合格式”。

.runtime-corrector/app-design.reviewer.md
# App Design Agent 审阅标准

## 必须检查
1. 每个设计目标是否能追溯到 requirements.md 中的明确需求。
2. 模块职责是否单一，边界和依赖方向是否明确。
3. 关键交互是否覆盖输入、状态变化、可观察结果和失败路径。
4. 技术取舍是否给出原因，并区分事实、假设和待确认项。
5. 验收检查是否能够通过测试、日志或界面行为观察。

## 不要检查
1. 不建议 requirements.md 范围外的新功能。
2. 不因个人偏好要求更换框架、架构风格或命名。
3. 不把上游缺失信息伪造成确定事实。

## 输出约束
- 每个问题引用 design.md 的具体章节和 requirements.md 的对应证据。
- 给出最小修正建议，不重写已经有效的章节。
- 无法从证据确认时标记“待人工确认”。

适合 reviewer

  • 需求忠实度
  • 模块边界合理性
  • 取舍是否有证据
  • 失败路径是否完整

适合硬规则

  • 必需标题是否存在
  • 清单是否达到数量
  • 占位符是否残留
  • JSON 是否符合 Schema

先核对，再启用

四个命令构成透明控制面：看状态、看执行源、看完整规范、切换开关。

在项目目录执行
# 1. 确认 app-design 已注册且当前为 off
node "${CLAUDE_PLUGIN_ROOT}/scripts/cli.mjs" stages --cwd "$PWD"

# 2. 查看实际命中、rules、reviewer 和检查项
node "${CLAUDE_PLUGIN_ROOT}/scripts/cli.mjs" explain app-design --cwd "$PWD"

# 3. 展开完整规范包；即使 stage 关闭也能查看
node "${CLAUDE_PLUGIN_ROOT}/scripts/cli.mjs" spec app-design --cwd "$PWD"

# 4. 确认无误后启用
node "${CLAUDE_PLUGIN_ROOT}/scripts/cli.mjs" stage app-design on --cwd "$PWD"

点击右侧任一标准，左侧会高亮它实际检查的文档区域；再点击左侧段落，可以反向查看相关标准。

  • 点击“开始检查”，然后用“下一步”逐层观察。
准备就绪写入命中路径后，PostToolUse Hook 会自动执行同样的链路。

真实运行时会发生什么

  1. 主 Agent 用 Claude 的 Write 或 Edit 写入 docs/design.md。
  2. PostToolUse Hook 把文件路径交给 Runtime Corrector；stage 关闭或路径不匹配时安静退出。
  3. 路径命中后，插件读取 design.md 与 requirements.md，执行当前项目的 rules。
  4. 路径命中后，节点或入边存在 review.enabled: true 时才创建一次性只读 fork；全部关闭时只执行已启用硬规则。
  5. hook 校验 fork 返回的诊断与编辑计划，统一生成候选 Diff；主 Agent 只修正命中的偏差，再次写入会重新触发检查。
  6. 本轮组合结果写入 .runtime-correction/；fork 随后释放，插件不会自动修改或应用 Patch。
T
透明性来自可追溯来源

explain app-design 告诉你当前实际读了哪些文件；spec app-design 展开完整规则；失败诊断会保存同一份 specification，避免 Agent 反复猜格式。

Δ
按显式开关审查

节点或入边存在 review.enabled: true 时，bundle 成员写入才从当前 session 自动 fork；全部关闭时只执行硬规则。fork 不会修改或应用 design.md。

这张图表达的运行规则

  1. 写入当前节点时，只执行它自己的节点纠偏和显式配置的直接入边纠偏。
  2. 需求分析 → 人工测试用例设计 是跨层直连，证明可以连接任意前序节点，不需要自动级联全部祖先。
  3. 上游文件只读；Finding、编辑计划和候选 Diff 只能指向当前节点产物。
  4. 某条边的 source 尚未生成时，该边保持 pending，其他节点规则和可用入边继续执行。
  5. 节点 review 和边 review 分别使用显式 enabled；全部关闭时不创建隔离审查 session。

第二个例子：Markdown + JSON 一起纠偏

用一个精简的 mini-planning Stage 看懂 Bundle、Schema、局部检查和跨文件语义审阅。

先看目标拓扑

PilotPlan.md人类可读的里程碑与 SR 分组
relations.json机器可读的节点和依赖边
同一 Bundle任一文件写入都会收集另一份
rules + Schema分别做结构和图关系检查
reviewer核对两份文件是否表达同一计划
2
一个 artifact 声明可以覆盖两种文件

把两个文件都放入同一个 patterns 和 relatedPatterns，并使用 format: auto。这样写入 Markdown 或 JSON 都会触发同一套 mini-planning criteria。

.runtime-corrector/config.yaml · 合并片段
# 暂时保持 enabledStages 不变，让新 stage 先处于 off。
# 在已有 artifacts: 列表末尾追加整个 list item：
  - name: mini-planning-bundle
    stage: mini-planning
    type: mini-planning-bundle
    format: auto
    patterns:
      - PilotPlan.md
      - relations.json
    relatedPatterns:
      - PilotPlan.md
      - relations.json
    relatedRoot: artifact-directory
    rules:
      enabled: true
      file: mini-planning.rules.yaml
    review:
      enabled: true
      criteria: mini-planning.reviewer.md
Y
只追加 artifact，不创建第二份顶层配置

项目里只能保留一组 enabledStages: 和 artifacts:。把完整 list item 加入现有 artifacts 列表，先让 mini-planning 保持 off；完成 explain 和 spec 核对后，再用后面的命令启用。

这几个配置项为什么这样写

配置项本例值实际效果
stagemini-planning两个文件共用一个开关和一份规范地图；诊断仍按触发文件分别保留 Latest。
formatauto清楚表达 artifact 接受混合格式；当前实现实际按文件扩展名读取内容，不会根据本字段转换文件。
patterns两个文件名写入任意一个都会触发；不需要声明两个互相竞争的 artifact。
relatedPatterns同样两个文件名触发后把另一份产物一起收进当前检查上下文。
relatedRootartifact-directory只在触发文件所在目录收集另一份文件，避免不同目录中的同名计划串进一个 Bundle。
rules一个规则文件JSON Schema 与图规则通过 artifact 字段精确指向 JSON；Markdown 语义由 reviewer 核对。
!
不要把无 artifact 定向能力的规则直接套在混合 Bundle 上

require-heading、require-checklist 和 require-text 检查本次触发文件；forbid-text 会扫描已收集文件。JSON 触发时，前一组不适合执行 Markdown 规则，后一组也可能误伤 JSON 字符串。本例只对 JSON 使用带 artifact 参数的 json-schema 和 graph-invariants，Markdown 结构与跨文件语义交给公开 reviewer。

.runtime-corrector/mini-planning.rules.yaml
version: 1

rules:
  - id: MINI-PLANNING-REQUIRED
    type: require-artifacts
    artifacts:
      - PilotPlan.md
      - relations.json
    pendingUntilComplete: true
    severity: error

  - id: MINI-PLANNING-RELATIONS-SCHEMA
    type: json-schema
    artifact: relations.json
    schema: schemas/mini-relations.schema.json
    severity: error

  - id: MINI-PLANNING-RELATION-GRAPH
    type: graph-invariants
    artifact: relations.json
    caseSensitiveIds: false
    nodes:
      pointer: /nodes
      idField: id
      typeField: type
      typeRules:
        - id: RELATION-NODE-TYPE
          idPattern: "^SR-"
          expectedType: sr
        - id: RELATION-NODE-TYPE
          idPattern: "^M"
          expectedType: milestone
    edges:
      pointer: /edges
      fromField: from
      toField: to
      typeField: type
      endpointRules:
        - id: CONTAINS-DIRECTION
          edgeType: contains
          fromType: milestone
          toType: sr
        - id: REQUIRES-DIRECTION
          edgeType: requires
          fromType: sr
          toType: sr
          allowSelf: false
      acyclic:
        - id: REQUIRES-CYCLE
          types: [requires]
    severity: error
require-artifacts控制 Bundle 完整度缺一份时返回 pending，不把写入顺序误判为最终失败。
json-schema + graph-invariants只检查 JSON先检查字段，再按 YAML 检查节点、边方向、引用和 requires 环。
reviewer检查 Markdown 与跨文件语义核对里程碑、SR、标题和边是否表达同一计划。

  "required": ["schema_version", "nodes", "edges"],
  "properties": {

    "nodes": {
      "type": "array",
      "minItems": 2,
      "items": {
        "type": "object",
        "required": ["id", "type", "title"],

            "type": "string",
            "enum": ["milestone", "sr"]
          },
          "title": { "type": "string", "minLength": 1 }
        },
        "additionalProperties": false
      }
    },
    "edges": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "required": ["from", "to", "type"],
        "properties": {
          "from": { "type": "string" },
          "to": { "type": "string" },
          "type": {
            "type": "string",

  },

Schema 能做什么，不能做什么

这个例子只使用插件当前明确支持的 JSON Schema 子集：type、required、properties、items、const、enum、pattern、minLength、minItems 和 additionalProperties。不支持的关键字会在加载策略时明确报错，不会静默略过。

Schema 负责“字段长什么样”，graph-invariants 只按 YAML 负责“边是否引用存在的节点、方向是否正确、是否成环”。核心规则不认识 Planning、milestone 或 SR。

.runtime-corrector/mini-planning.reviewer.md
# Mini Planning Agent 审阅标准

## 必须检查
1. PilotPlan.md 与 relations.json 是否表达同一组里程碑和 SR。
2. 每条 contains 边是否能在 PilotPlan.md 的 Contains SR 中找到证据。
3. milestone node.title 是否与 PilotPlan.md 对应 M 章节标题一致。
4. 是否有只出现在一份文件中的 SR、里程碑或依赖。

## 不要检查
1. 不因为个人偏好要求拆分更多里程碑。
2. 不把 Schema 通过误当成产品语义已经正确。
3. 不自动修改任何文件，也不自动应用 Patch。
4. 本例没有收集上游需求，因此不判断需求忠实度；如需该能力，先把上游文件加入 relatedPatterns。

## 输出约束
- 每个问题同时引用 Markdown 行和 JSON Pointer/边。
- 只建议最小同步修正；无法判断哪一侧权威时转人工。
