1一页纸

定位

宿主插件，挂在 MatrixAssistant / OpenClaw 的编码会话上。只读，只给出有依据的反馈，修复由主 Agent 完成。

一份清单

纠偏检查体系：五类检查（需求实现、项目规则、Skill 步骤、验证闭环、需求分解与验收设计）、十六项指标、四条准入规则。需求分解只是其中一类。

缓解纠偏

开工时在看不到候选代码的条件下，从开始版本代码和项目文档中找出该查的条目，作为简报交给主 Agent，同时成为终审的必查项。

纠偏

写文档、执行中、交付三个时点对已形成的产物下结论；有反证才报偏差，进入反馈→修复→复审闭环，次数封顶。

当前状态

闭环已在真实宿主跑通。开发集上相对基线有正向观察，增益最大的是项目规则（G3）；泛化净收益尚未证明，增益也不能归到某个组件。
两条线只按一条标准区分：是否针对已经形成的产物下结论。简报不下结论，属于缓解；文档纠偏、Skill 看护、终审都对已有产物下结论，属于纠偏。文档纠偏对文档本身是纠偏，对下游代码起缓解作用，是两条线的衔接点。

2背景与目标

只改提示词已试过无效（st7、st6 回放结果不变，docs/stop-contract-pass.md）。根因是结构性的：清单由已看到候选代码的同一会话生成会被候选带偏；"无法证明就省略"会让漏检默认通过（docs/requirement-frame-spec.md §1）。

目标

  • 减少编码 Agent 在隐性契约、规划、过程、交付四类问题上的偏差
  • 偏差发生后，用可归属的证据把它交回主 Agent 修复并复审
  • 结论诚实：证据不足就是未验证，放行不等于通过
  • 成本可控：次数与时限封顶，RC 故障不拖累主任务

非目标

  • 不修改业务文件，不替主 Agent 修复
  • 不替代测试，不充当测试神谕
  • 不新增用户没要求的义务，不向用户提问、不替用户做需求决定
  • 没有对照证据，不宣称提分或省成本

3设计原则（所有组件共用）

① 依据分层，原文优先

用户原文决定要改什么；既有代码、测试、项目规则、已加载 Skill 决定不能破坏什么、必须怎么做；冲突时原文优先。RC 生成的简报、检查项、反例、笔记只负责定位该看哪里，不构成义务。

② 提示与判定分离

缓解只提供信息：不下结论、不阻塞、不占纠偏次数。纠偏只对已形成的产物下结论，且必须有可归属的反证。在检查体系内部表现为开工找、交付判。

③ 三种结论，放行≠通过

偏差（有反证）→ 闭环修复；通过（仅覆盖已检查范围）；未验证（证据不足）→ 交由人判断。额度耗尽、超时、RC 故障可以放行，但不产生通过。

④ 成本封顶，故障不拖累

每条纠偏通道都有次数或回合上限；终审每会话、每流程最多实际纠偏 3 次，修复真正开始才计数。RC 故障时主任务照常，留下未验证记录。

原则 ① 回应"原文是唯一权威，RC 却去抓原文没写的东西"：隐性契约属于"不能破坏什么"一层，依据是旧代码和旧测试本身，而不是 RC 的推断。

4纠偏检查体系：查什么

纠偏检查体系是方案的骨架。它规定检查的内容；四个组件规定何时、由谁检查；两条线规定检查结果是提示还是判定。代码落点：lib/runtime-v2/metric-policy.mjs（五类与开关）、metrics.mjs（指标目录与最早适用阶段）、config/stop-defaults.json（插件缺省）、docs/correction-checklist.md。

4.2 准入规则：什么能进入清单

原文权威

只收原文明确提出或明确采用的要求。

落点：检查项文字须为引用行的短原文摘录，不得补充细节；引用少于 80 行；依据冻结为开始时的文档副本及 sha256。

当前触发

前提条件对本任务成立。

落点：原文前提必须原样保留，不能把有条件的义务改成无条件。

可以判定

能明确核对，且只有一个检查目标。

落点：每条只检查实现、产物或过程动作中的一种；判不了就是未验证。

时机正确

到该检查的阶段才检查。

落点：指标目录记录最早适用阶段；尚未到达的步骤不算偏差。

不满足准入规则的内容不进入清单。开启指标不新增交付义务：没有对应原文时报告不适用，不会为了得分要求 Agent 补写文档或调用 Skill（docs/stop-metric-switches.md）。

不是需求澄清

"需求分解与验收设计"（配置名 clarification）检查的是 Agent 自己写出的规划工件，不是向用户澄清需求。开工时的代码理解与提议服务的是需求实现、项目规则、验证闭环三类。

开工为什么只找三类

这是"时机正确"规则的直接结果：开工时规划工件还不存在，Skill 也还没加载，没有可定位的原文。真正的覆盖缺口只有一处：项目规则在执行过程中没有看护 ○。

分工边界

"修改某类代码时必须使用某 Skill"属于项目规则（M11），由检查项提议者提出。Skill 看护只看到已加载的 Skill，看不到"该加载却没加载"。

4.4 开工找，交付判

开工
提议者在开始版本上定位 G / S / C / K→ 简报
G / S / K 作为提示送达，不下结论→ 终审建清单
读完必读原文，set_original_checklist→ 并入检查项
标 proposedCheck；完全相同的条目只审一次→ 逐项处置
G / S / C 写入 frameDispositions→ 有反证才报偏差

同一条目，两种身份

在简报里是提示：不下结论、不扣纠偏次数。到终审是必须给出处置的候选必查项。

检查项不创造义务

义务来自项目文档原文本身（原则 ① 中"必须怎么做"一层），检查项只是指向原文行的定位。引用行没有陈述约束或本需求未触发时，不构成偏差；与用户原文冲突时以原文为准。

如实说明

终审能看到检查项和框架项。独立性的结构保证只有一条：它们在候选代码出现之前生成；而且它们单独都不能构成偏差。

4.5 偏差在哪个时点还能被拉回来

偏差形态例子还能拉回的时点由谁负责
交付类：代码或产物的性质生产路径没覆盖；违反编码规范；验收不通过交付时仍可修复终审
动作类：必须执行某个动作构建后要跑 lint；修改后要回读修复轮可以补做终审，配合简报中的检查项
顺序类：先后关系先设计后编码；Skill 步骤顺序；编码前完成需求分解只能事前预防，到 Stop 已成历史简报中的检查项、Skill 看护、文档纠偏

这张表回答"为什么不只做终审"：顺序类偏差到了终审只能通知一次（终态"带历史偏差结束"），不派发修复，必须靠前面的时点预防。

内容独立

RC 的条目在运行时从本任务材料生成；评测清单由独立评测方结合标准补丁和测试补丁事先冻结。RC 读不到评测清单、隐藏测试和标准答案。

对外成绩只用独立评测

RC 内部比率只用于控制台观察。对外只报独立评分的 F2P/P2P 和冻结的 G0–G3。

相关，不是责任划分

一个 G 维度通常由多个时点共同影响，单个组件的贡献目前没有拆分。评测清单须在运行前冻结，构建者不参考 RC 轨迹。

6组件设计

6.1 代码理解 · 提议 · 简报缓解纠偏● 主体已实测◐ 检查项 / 部分简报 / 分批账本○ 前提来源记录
目标
在候选代码出现之前，把开始版本代码中决定实现方式的约束（隐性契约）和项目文档中的规则交给主 Agent；同时为终审预置一份不受候选代码影响的必查清单。
检查类别
找：需求实现（代码提议 → G / S / C）、项目规则与验证闭环（检查项提议 → K）。只为已开启的指标提议。

第一个真实用户回合（OpenSpec 下为提案回合）开始时在后台启动，不阻塞主任务。每个会话生成一次；开始版本变化或上次失败时重建。RC 内部会话、纠偏续作、RC 关闭或 shadow 模式下不触发。

项目规则 / 验证闭环→程序校验
证据行存在且 ≤80 行；原文摘录；前提原样保留→反例复核→选择账本
选中 / 拒绝 / 已覆盖 / 延期；无置信度门槛→发布
输出

8判定语义与两条线的兜底

偏差 DEVIATION有适用的当前反证。反馈保留原文和证据身份，进入修复闭环，计入额度。
通过 PASS必要条件有当前有效证据支持，只覆盖已检查范围，不扩张为整个任务通过。
未验证 UNVERIFIED证据缺失、过期、未完成、检查器故障或证据不足。逐项保留，交由人判断，不触发修复。
放行 ALLOW流程控制允许停止。额度耗尽、取消、不支持续作时也可能放行，不等于通过。

流程关闭规则

  • 任务完成且没有当前偏差（包括有未验证项）时，关闭本条纠偏流程。
  • 阶段完成、中间输出、等待用户、外部阻塞：只结束本次 Stop，同一流程沿用已用次数。
  • 纯历史顺序偏差：通知一次，终态为"带历史偏差结束"，不派发修复，不扣次数。

两条线如何互相兜底

缓解失败时降级为检测

简报晚到、没生成或只生成一部分时，已产出的框架项、检查项和反例仍作为终审必查项。准备不完整只记入覆盖统计，不算作业务代码问题。

防止同源错误

框架项和检查项在候选代码出现前生成；终审先从原文自建清单再并入；判"已检查"必须追到当前代码；单独都不构成偏差。剩余风险：两边一起选错检查角度（st9），对应 6.1 的前提来源记录 ○。

纠偏不会无限循环

次数和时限封顶；证据不足交给人，不靠反复纠偏凑出"通过"。

11可靠性与安全边界

只读与职责边界

RC 不写业务文件；宿主执行、文件权限、模型选择、工具审批和业务修复始终由宿主负责。

隔离

私有审查会话使用冻结请求和受限工具；清除父凭据后注入指定提供器环境；配置只保存环境变量名，日志与请求中不保存令牌。

读取凭据

读取证明记录路径、当前字节摘要、披露范围和调用归属；模型提交的路径、行号或引文本身不构成读取证明。

失败语义

普通入口故障时失败开放；活动 Stop 缺少有效结算时保留未验证。取消、超时、依据变化和额度耗尽都不伪造通过。

持久化与并发

事务日志增量提交，配合校验、检查点和原子替换；跨进程锁；迟到回调在提交前核对身份，旧回执不能覆盖新一代结果。

审批模式

普通模式：在 MA 聊天中显示原生确认卡。无人值守模式：只自动授权本会话、本次 RC 后台已登记的工具。两种模式都不切换宿主的全局策略。

宿主支持范围：OpenClaw 原生入口固定适配 2026.7.1-2 和 2026.10.3；代码理解简报和检查项目前只支持 OpenClaw；终审引擎由 Claude Code、CodeAgent、OpenClaw 三个宿主共用。

13风险与对策

风险已观察到的表现控制手段
成本一次终审约 170–210 万 token；检查项提议成本未单独计量次数封顶；简报后台运行；可切换到"只报偏差"或关闭简报的低成本档

检查项拔高要求尚未观察到逐字引用、前提原样保留；单独不构成偏差；与用户原文冲突时以原文为准；监测检查项精确率
误报引发乱改正确实现上暂未观察到偏差必须有反证；反馈要求先复现；未验证不触发修复
漏检数独、st2 删除公共方法、M09 错判通过原测试回归前移、项目验收命令；公开漏检案例
"用自己的尺子给自己打分"RC 与评测共用 M 编号内容独立生成；评测清单事先冻结、不参考 RC 轨迹；对外只报独立评测

复杂度分支领先 main 约 590 个提交；核心文件两千多行；分类较多大部分代码用于身份、取消、截止时间和证据校验，目的是防止伪造通过；对外只讲"一份清单、四个时点、两种作用"
适用范围宿主固定两个版本；简报和检查项仅支持 OpenClaw；需要 git；检查项只读 Markdown口径定为"MatrixAssistant / OpenClaw 首发"

  6. "准备不完整是否计入终审未验证"，两份文档说法不一致；按第 8 节统一为"只记入覆盖统计"。
  7. 并发槽等改动尚未提交，不作为已交付能力讲。
  8. docs/correction-checklist.md 写"保留置信度不低于 0.75 的项"，代码已明确没有置信度门槛（选择器提示词 "There is no confidence cutoff"）。

  11. 引用行不构成约束的检查项：完整审查模式要求记为未验证，仅偏差模式记为已检查。应统一为"原文证明不适用即为已检查"，避免抬高未验证占比。
