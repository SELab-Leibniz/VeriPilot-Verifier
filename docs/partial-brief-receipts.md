# 逐项简报回执与终审绑定

宿主终态读取：对同一 `agent.wait` 的已知传输超时，以及连接异常关闭 1006/1012/1013，在原有期限内重新读取。不会重发 `chat.send` 或 `subagent.run`；鉴权、协议、不同运行编号及取消仍按原边界失败，宿主返回的错误终态也保留为错误。只有匹配原运行编号的真实 Gateway 终态才能推进。重试日志只记编号、受控错误类型和次数，不记认证数据或响应正文。短请求探针只能验证这条基础接口，不能代替四题的真实终审与独立评分。

本改动继续使用冻结的任务开始源码、用户消息、独立提议和反例复核，不将评测题目或答案写入运行时。

原生 `agent_end` 的粗粒度成功标志不能覆盖消息快照中最后一条助手的 `error` / `aborted`。这类失败沿用既有尝试边界，在转录读取之前隔离旧控制器，允许宿主按原运行编号自动重试；历史助手报错不影响后来真实成功的完成。仍必须等待匹配的 Gateway 终态，不生成终态、不重发业务请求。该接口回归证明边界缺陷，不能单独证明某次运行中 hook 超时的成因。

选择器通过 `submit_frame_selection` 分批提交 `{reviews, finish}`。每项处置为 select、reject、covered 或 defer，并说明依据。程序接受有效兄弟项，拒绝未知或重号、空理由以及跨类型、行为或公共入口的覆盖。覆盖只能指向实际已选且能发布的候选。所有有效候选保留明确内部状态；未处理为 pending，明确延期或超出发布预算为 deferred，不能冒充完整覆盖。发布预算不再导致整份简报被丢弃。

每次提交保存 `selection-receipts.jsonl` 及当前 `selection-coverage.json`。到时或选择器失败时，只从已接受的结构化处置生成部分简报；不猜测截断文本，不直接发布原始提议。没有已接受的选择就不产生实质简报。反例阶段失败但仍有后续通过选择复核的内容，也允许部分交付。

阶段预算保留：独立提议最多使用总准备预算的前 50%，反例复核最多使用前 70%，剩余时间用于筛选收敛；较早完成即可提前进入下一阶段。慢提议不能耗尽全部时间，其他已完成提议仍要通过原有来源检查和筛选账本才能发布。已被工具确认接受的提议，在其会话尾部失败或到达阶段期限后保留；未确认、迟到或已取消的提交不能加入。程序对阶段等待设有中止边界，不依赖单个会话主动结束。未完成阶段只在内部记录，宿主仍只收到经过筛选的有效内容及通用遗漏提醒。生命周期取消继续禁止交付。

frame schemaVersion 为 3；status 区分 ready、partial、empty 和 unavailable。partial 必须有经过程序检查的可发布项，保留内部未完成原因。宿主只收到有效内容及通用提醒：“本次梳理可能仍有遗漏，请结合用户原文与实际代码，自主补全检查并作出决策。”不会列出未完成项目、编号或内部错误。继续使用既有会话、任务开始版本、取消与单次发送检查；过期工具提交不能追加回执。

Stop 按项 ID 绑定原入口与原前提，审查者提交 `contractAssessment {applicability, trace}`；若兼容旧格式提供入口/前提，仍核对原值，不能替换依赖。持久化覆盖记录由程序补全原绑定。明确要求追踪原成功依赖、配置写入分支及其实际消费者；看到源码中存在某次调用不能证明可选参数省略时也到达。旧错误优先级本身不构成必须保留的授权。

部分建议与真实交付契约分开：简报准备不完整继续在 frameCoverage 中记录，不凭它新增业务 UNVERIFIED。证据不足的实际契约仍为 UNVERIFIED；有来源证明建议不适用时允许 NOT_APPLICABLE。独立评分、实际终审闭合与自然结束分别报告。

实验只在隔离配置中启用 M01–M07、M09–M11、M13–M15 和既有 M16，开启 requirementFrame.checks，并采用完整逐项终审。未请求的 M08/M12 保持关闭。开启指标不授权推断新义务，仍须检查实际冻结策略、适用对象和结算证据。产品默认配置不改变。简报上限继续为 15 分钟。

独立反例复核产生的有效、带入口及源码依据的场景，若没有进入宿主简报，会以 `C*` 保留在仅供 Stop 使用的 `reviewOnlyScenarios` 中。筛选的拒绝、覆盖、延期或简报名额不会取消这些复核；即使没有可交付简报，也可保留终审场景。原简报只交付已选内容和统一遗漏提醒，不列这些内部条目。Stop 复用原逐项机制，必须按每条原入口、原前提检查实际代码，允许有来源依据的不适用判断，证据不足继续未验证；反例自身不产生新需求，不能仅凭它判业务偏差。

### 显式项目验收命令

`stopCorrection.projectChecks` 可声明至多 16 项项目验收检查；默认不运行任何新命令。每项包含唯一 `id`、显式 `command` argv、适用的 `metrics`（M13–M15），以及命令依据的 `source {path,sha256,start,end}`。可用 `inputs [{path,sha256}]` 固定原验收脚本及其辅助文件（至多 64 项），避免修改后的检查器替代原验收口径；可配置相对 `cwd`、超时与输出上限。命令来自配置，模型不能通过审查工具选择或改写命令。来源与固定输入必须在项目内，内容 SHA256 与行范围必须匹配；工作目录的真实路径也必须留在项目内。

Stop 在选择适用范围后，由程序在原生工具调用之间执行命令，再向同一次审查提供实际退出状态、输出、来源和候选摘要。原测试仍先于首轮语义审查执行。只有来源、固定输入、候选及已选验收对象的前提均未变化的已完成结果可以缓存；对象身份或条件变化会重新执行。缺失来源、启动失败、超时与取消保留为未验证；输入变化会使该批结果失效，并阻止与此前的原测试证据混用。已执行的失败或中断尝试另存记录，不以重试覆盖。

命令完成仅提供该命令的执行证据。配置不产生新义务，退出零不等于全部验收通过，命令失败本身也不等于业务偏差；审查者仍须逐项核对原要求、实际适用条件和证据范围。原依赖复核同时检查原替身边界之外新增的调用，不能仅因源码中仍调用了原函数，就认为整个原测试前提得到保留。

稳定性目标为同一冻结版本连续三轮、每轮四题中至少三题独立测试全部通过且实际终审完整。先运行首轮；不足三题则如实记录，分析后另开版本，不把不同版本或失败样本拼成达标轮次。已看过标准答案的四题属于开发验证，不宣称盲测泛化，也不把任务专用反例注入业务或 RC。

原测试回归检查前移：任务开始的原始基线记录保持不变。当前候选修改了既有非产物源码且启用 M16 时，先执行配置的原测试检查，再进入模型逐项审查；完整模式和仅报偏差模式均加入同一个程序持有的 REGRESSION 项。原输入、原测试依赖与已经保存的反例不能因切换模式消失。范围确定时重新核对候选及缓存身份；相同候选复用有效结果，候选改变则重启审查，不能用早先结果证明新代码。不可用的执行结果保持未验证，不在同一次审查中重复消耗整段检查预算。失败逐项解释为授权改变、回归或未验证，有证据的偏差与未验证兄弟项分别保留。
