日期：2026-09-15；宿主 OpenClaw `2026.7.1-2`；插件 `1.9.1-openclaw.5`。本次修复总时限耗尽后的状态和交付；不将昨晚失败任务改成已通过，也不声称重新完成了 GLM 的完整三文件长任务。

## 原错误的实际原因

对应用户 2026-09-14 23:29 至 23:59 的截图：

- 任务 `task-20260914T152940709Z-91e069d2`，父运行 `b13bd37c-3dd2-4c49-b330-09add5a31ed9`。
- 主模型 `ark-work/ark-code-latest`，reviewer `review/glm-5.3`。插件 reviewer/Hook 上限均为 600000 毫秒，主运行 `agents.defaults.timeoutSeconds` 为 1800 秒。
- 23:36:27 需求基线完成；proposal 的矛盾收到反馈后修正并复验；design、tasks 的故意问题分别收到 2 条、5 条 error 诊断。看护功能确实运行，不是没有启动。
- 23:54:03 进入最终验收，23:55:07 完成其 Ground Truth 刷新；Stop reviewer 尚未给出结论时，23:59:18 达到总时限。控制器耗时 1800147 毫秒。
- 原控制器用 `setTimeout(cancel, timeoutMs)` 结束工作，错误记录成 CANCELLED；父回复又按取消规则被抑制，因此网页只显示笼统的 blocked/没有可见回复。核心本身仍是 STOPPED_UNVERIFIED，没有通过验收。
- 日志还显示 GLM 两次发生原生 `LLM idle timeout (120s)`，随后按有限规则修复。单个角色上限并不能替代全任务上限，也不能解决 provider 不响应。

工作区初始化已正常，本次与前面的 WorkspaceVanishedError 无关。

## 改动

1. 将用户取消与插件自己的总时限耗尽区分。到时仍终止内部执行和评审，但保留 UNVERIFIED 收据并交付中文说明；真正的用户停止、重置与插件关闭仍取消交付。
2. 内部工作及每次 reviewer 的截止时间都不超过父任务的剩余时间。角色交接、JSON 修复不突破共同上限，原有纠偏次数和评审基础设施重试规则不变。
3. 总时限耗尽时保存明确的 `RUN_BUDGET_EXHAUSTED` / `SUPERVISED_RUN_BUDGET_EXHAUSTED` 原因。已结束 worker 的成对工具证据保留在父历史，未验收候选文字仍不交付。
4. 等待最终历史写锁期间再次校验总时限，避免排队后把候选成功写入历史；未验证的超时说明可以写入，用户取消仍优先。
5. 未验证结束也保留已经返回的原生模型用量，继续区分最近调用上下文与累计用量。

全部改动在插件内完成，没有修改或替换 OpenClaw 宿主模块。

## 配置与交付边界

本次更新插件，不修改用户 `.runtime-corrector`，也不改写默认 reviewer、API 地址/凭据或原有 1800 秒总时限。若要继续使用耗时较长的 reviewer，可自行给整个任务更长的有限时间，例如：

```sh
openclaw config set agents.defaults.timeoutSeconds 3600
```

若选用此前已跑通完整看护任务的模型：

```sh
openclaw config set plugins.entries.runtime-corrector.config.reviewerModel ark-work/ark-code-latest
```

配置后重载 Gateway。增加总时间不是验收通过保证，不能用关闭 Stop 或 shadowMode 掩盖未验证结果。升级后请针对已有文件提交新的明确验收要求；旧任务记录不自动改成成功，也不要盲目重做可能已有副作用的操作。

原会话冻结转录、需求基线及指标的独立 Stop 重放被自动审批拒绝，理由是再次外发这些数据可能含未明确授权的敏感信息，且不是本次失败路径测试所必需；该操作没有执行。后续仅完成已获授权的隔离测试，没有绕过这一拒绝。
