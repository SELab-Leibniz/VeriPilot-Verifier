# 可配置原生 Stop 续作隔离实验（2026-10-12）

从 `codex/openclaw-native-transparency` 的 `522a6ea` 建立 `codex/openclaw-native-stop-followup`。只修改 RC；OpenClaw 固定 `2026.7.1-2`，GLM-5.3-Flash。本实验未合入 `codex/openclaw-2026.7.1-2`，未替换当前安装。

结论：在这一 App 中，原生续作有实际收益。两组首稿均为 13/14，候选收到 Stop 偏离反馈后自动交给同一会话的原生宿主，实际修正硬链接保护及文档，独立检查提高至 14/14；原版透明候选没有续作，最终补核明确发现偏离后仍为 13/14。过程文字、工具活动与正常交付保留，终审保存 PASS。不是宣称跨所有任务的统计收益。

## 实现与配置

```yaml
stopCorrection:
  enabled: true
  maxCorrectionsPerEpoch: 3
```

沿用既有参数及纠偏 epoch，不新增同义配置。默认 3 从 `config/stop-defaults.json` 读取；项目 YAML 覆盖，移除 RC `Math.min(3, configuredK)` 截断。次数不是 Reviewer 格式修复次数；模型故障仍使用原版独立故障预算，未验证不伪造通过。

流程：完整 Stop 产生有依据的业务偏离 → 保存独立回执 → `api.runtime.subagent.run` 请求同一会话原生续作 → 宿主接受 → 实际反馈记录出现在该原生运行转录中 → 标记已投递 → 宿主判断、执行 → 该自有运行的 `agent_end` 再做完整 Stop。无需旧业务 harness 或 `before_agent_finalize`，不压制原生流，也不自动应用补丁。

只传 `sessionKey/message/idempotencyKey/deliver:false`，不覆盖 provider、model、cwd、lane、思考级别、工具、审批或沙箱。受宿主原生准入和执行政策约束。只等待启动确认，不在原回复 Hook 中等待新业务轮结束。

公开续作接口会持久化一个 user-role 提示，RC 不改宿主转录。RC 根据自己的派发回执、真实 runId、会话身份、原始分支边界和消息 ID，仅在自己的转录投影中标记为操作反馈；不用可复制的文本前缀判断来源。初次纠偏的两条反馈均未重置需求版本或 epoch。真实用户的最终验收范围更新才进入下一 epoch。

同次评审只派发一次；不确定结果不重放，保留次数预留；确认拒绝才退还该机会。重置、取消或新用户轮使旧请求失效。旧结束回调不能覆盖新运行状态。Stop 是否已武装以原纠偏核心为准，不能通过中途改关闭配置绕过续作。

## 实际对比

同一离线 Python CLI 备忘录的 R01–R12、相同项目策略、模型/API。开始没有业务代码，首稿故障探针明确保留 CSV 硬链接保护缺口。没有 evaluator 修改 App 代码；修复均由真实宿主执行。

| 项目 | 原透明候选 522a6ea | 原生 Stop 续作候选 |
|---|---:|---:|
| 首稿独立 CLI 检查 | 13/14 | 13/14 |
| 最终独立 CLI 检查 | 13/14 | 14/14 |
| 首段宿主文字 | 4.433 秒 | 5.148 秒 |
| 首稿业务工具事件 | 35 | 37 |
| 首个需求 epoch 的续作 | 0 | 2/3 |
| 明确最终范围后的验收 | DEVIATION，未续作 | PASS |

候选 epoch 1 的第 1 次反馈指出 `notes_app/export.py` 只比较路径、不能拒绝已有硬链接。宿主增加 inode/device 身份比较、真实硬链接回归、冒烟测试。第 2 次反馈指出 ACCEPTANCE.md 仍写硬链接未完成且计数过期，宿主自行同步文档，第三次完整 Stop 保存 PASS。

原生续作第 1 轮有 95 个文字增量、20 个工具事件；第 2 轮有 49 个文字增量、8 个工具事件。其首段文字分别在本轮约 2.055 秒、22.771 秒到达，工具活动没有被关闭。真实浏览器历史能看到反馈、宿主修正说明和工具活动。

补充最终验收步骤两组完全相同，明确首稿许可结束、所有要求当下适用，并运行同一份独立检查。原版实际失败在硬链接保护，Stop 记录 DEVIATION；候选继续为 14/14，又通过 epoch 2 的一次续作修正烟测硬编码计数，程序实际记录 17 次检查/13 次 CLI 调用，最终 Stop 再次保存 PASS。该一次属于真实用户范围更新后的新 epoch，不是 RC 反馈重新开预算。

对照版的 CLI 检查非零退出被宿主汇总为 Exec warning，幂等状态查询因此返回错误；这是预期业务测试失败，不是 RC 崩溃。评审已完成、DEVIATION 已保存，代码未修复，不能把通信警告视为已纠偏。

程序引用核对：对照 254 条、候选 478 条，冻结文件 SHA-256 与引用行区间原文逐条一致。最终回归 `node --test --test-concurrency=4 test/*.test.mjs`：693 项，691 通过、2 跳过、0 失败；另有 42 项针对性状态/续作/故障检查通过。最终防绕过检查 42/42、注册/打包 37/37、普通问答及通知边界 66/66。

## 实验修正与局限

- 首稿允许暂留缺口使对照 Stop 判为 STAGE_COMPLETE，而候选查出了实现偏离，不能仅凭这一步作严格因果比较。因此额外对两组做了相同、无首稿延期许可的最终验收，结果才用于最终状态对比。
- 初始收集器匹配路径过宽，把私有 Reviewer ID 计入业务续作，导致等待未结束；已改为精确 `/native-followups/` 路径，原日志保留，候选阶段时间从真实 FINISHED 回执校正。没有重放模型输出或补造评审结果。
- 曾误以为续作结束后未评审，加入了仅运行身份的诊断构建；实际正常终审已在后台运行，诊断没有触发且已撤销。试验行为代码未变，最终源和包重新核对；不把这次诊断构建当成性能比较证据。
- 补核实际暴露旧核心在新 Stop 偏离时仍保留 COMPLETED 状态，已小修为重新 ACTIVE，并通过先完成再失败的回归。另保留不确定派发的预算预留，以及原 Stop 已武装的防关闭机制。这些是书面状态/拒绝路径修正，正常续作路径与实测一致；另外修正了新普通问答不继承旧业务 Stop 标记、通知按真实接受记录显示。未再次运行整个 App 来宣称这些异常分支已实测。
- 这是同一会话的新原生运行，不是无痕的同 run 重试。宿主 UI 会把 RC 提示显示成额外的 You 消息；正文明确标记为插件反馈，RC 需求账本不把它当新用户要求。未为改标签改宿主 UI。
- 实验两组临时执行策略均 `security: full, ask: off`，仅在独立配置中。实际审批 UI 未覆盖，不能声称已经验证所有客户端和权限场景。
- 每次业务运行仍按宿主自身模型、超时与权限。RC 角色 YAML 为 20 分钟；原生 Hook 上限本实验仍是 10 分钟，不以修改原宿主时间设置取得通过。
- 仅一个 App、一次主要对照和一个共同补核，模型判定/耗时有波动；未做三 App 或高并发普遍性保证。
