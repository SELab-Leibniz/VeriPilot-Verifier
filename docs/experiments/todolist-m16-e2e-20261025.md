## 功能验收与实际轨迹

业务模型自行读取合同和测试，只写入一次 `todo.py`。它实际执行冻结验收器，退出 0 并得到 `TODOLIST_VERIFIED`。实验结束后，观察器再次独立执行同一冻结验收器，仍为 **10/10 PASS**。最终源码为 220 行，SHA256：`24d9c868db040cef0279b798feccc2e112acf498e534b2b6a03bb38bc89d79ca`；纠偏续跑未修改它。

## M16 实际运行了什么

冻结人口中的 M16 为 1 条实现范围加 14 条需求，共 15 个实现单元。普通 Stop 和独立实现复核分别审查了同一批对象，实际启动 **30 个 M16 单项会话**，均返回 PASS；最终原始指标记录为 `MEASURED, 15/15, value=1`。

这些会话使用当前六条件提示和程序采集的 `todo.py` 源码哈希，引用是真实读取的 SOURCE 证据，不是测试替身、开发者自述或错误插件版本。命令入口、处理逻辑、持久化和返回链路确实存在：`main()` 解析输入、分派命令，`persist_atomic()` 调用 flush/fsync/os.replace，结果经 JSON 输出，幂等回执保存到元数据文件。

**但真实代码存在、默认验收通过，并不足以证明全部必要数据流都成立。**

### 补充复验确认的 M16 漏检

冻结 HARD 条目 `gt-req-005` 是“list returns an array”；`gt-req-008` 要求持久化存储由 `--store PATH` 选择。原合同没有声明保留文件名 `todo.meta.json`。

在不改源码、测试和配置的条件下，观察器只使用并清理项目本地应用数据，执行：

```text
todo.py --store <项目本地应用数据目录>/todo.meta.json add "boundary item"
todo.py --store <同一路径>/todo.meta.json list
```

两条命令均退出 0。第一条返回正常待办项；第二条返回 `{"next_id": 1, "receipts": {}}`，是对象而非数组。

原因可以直接定位到当前生产源码：`meta_path()` 在第 21–23 行固定返回同目录的 `todo.meta.json`；第 207 行先将待办列表写入所选 store，第 212 行又把元数据写入这个相同路径，覆盖待办列表。后续 list 第 151–154 行直接使用 load_store 读回的对象并输出。

原 `M16:gt-req-005` 却判为 PASS，理由假定“loaded items array”，引用整份 `todo.py#L1-L220`。它没有沿输入路径计算、两次持久化和再次读取检查路径冲突。这是本轮六条件中“数据流有效”判定的一个实际反例，不是新增功能要求，也不是另一版本源码。

该补充探针与冻结十项验收分开保存。原业务验收和 M16 原始 PASS 均未改写；不能据一个反例重算整套真实覆盖率，也不能再把原始 15/15 解读为实际完整覆盖。探针没有启动第二次业务模型任务。

## 插件闭环中的两个主要问题

### 手动检查缺少当前运行身份，形成自身等待

实测 `runtime_corrector check` 阻塞约 364 秒，宿主据此中止纠偏续跑；不是模型拒绝继续，也不是业务测试失败或上下文 overflow。

调用链为 `lib/openclaw/entry.mjs:74–91` 将工具工厂 ctx 传给 `manualCheck`，但没有利用 tool-call ID 取得精确调用绑定；`runtime.mjs:972` 的 `manualCheck` 进入 `withState({}, ctx)`，继而在第 282 行调用 `waitForStop`。后者第 356–365 行依赖当前 runId 判断是否应放行已授权纠偏子运行。已安装宿主的工具工厂 ctx 类型没有 runId 或 abortSignal 字段。

另做了一个零模型、零 Gateway 的受控生产代码复现：同一待完成纠偏链中，缺少 runId 的手动检查持续等待；提供合法纠偏运行 ID 的等待门立即放行。复现也确认调用已进入 Stop 门，而非仅等待文件准备。现场未额外插桩 ctx，因而“实际阻塞由这个身份缺口造成”属于轨迹、声明类型、调用链及受控复现共同支持的归因，不冒充现场变量转储。

优先修复应使用可信 tool-call 绑定恢复调用身份及取消信号，保留当前性和项目围栏；不能通过绕过全部 Stop 等待来放行其它新任务。

### 本轮取消后未提交任务终态

续跑被中止后，回执为终态 `CANCELLED / RC_NATIVE_ATTEMPT_ENDED`，但核心任务仍为 ACTIVE。观察器关闭网关后再次读取也相同，不能将它描述为正常 `STOPPED_UNVERIFIED`。

代码路径与结果吻合：`runtime.mjs:274` 先设置 `nativeInvalidated=true`，再取消 Stop 链；链的收尾回调在第 441 行要求 `!state.nativeInvalidated`，使本轮自己的 `settleIncompleteStop` 无法更新 task 终态。此外 `agentEnd` 先取消回执再调用 finish，而 `native-followup.mjs:183` 的 finish 不接受已 CANCELLED 的回执，所以没有补上 finishedAt。CANCELLED 已是回执终态，但这不等于核心任务收尾完整。

应区分“当前运行主动终止”与“旧运行已被新任务替代”：前者需要落终态，后者仍须防止旧结果覆盖新任务。

## 其它判定是否合理

**正确的行为：**

- 关闭文档、Skill 纠偏的设置真实生效，没有对应评审角色或 watcher；基线提取和 Stop 源码复核仍按配置开启。
- M11 发现初始目录查看命令缺少显式 workdir，有原调用证据，符合本次投入请求。该命令只读且使用绝对目标路径，偏差不等于 TodoList 功能损坏。这个额外操作纪律比原 TodoList 业务合同更严格，实验分析必须分开解释。
- 文件质量未完成保留 UNVERIFIED，整体保留检查器故障；没有用 M16/source PASS 覆盖它，也没有把它冒充业务缺陷。
- 已审对象、引用、完整反馈和索引均落盘，续跑模型实际读取了反馈；原应用、保护输入及宿主原文件保持可核对的完整性。

**仍需改进的范围和效率：**

- M01–M07 仍生成 56 个没有合法候选的文档视图，全部程序化 UNVERIFIED，没有分别调用模型。一个 HARD/ARTIFACT 的既有验收追踪关系阻止了源码专属适用性路径成立。这不是 56 个业务缺陷，也不能为变绿而直接删除原义务；应澄清实际交付物与原有证据材料的角色及绑定。
- 2 个总目标及 1 个测试契约 HARD/IMPLEMENTATION claim 没有直接的非文档执行指标对象。它们的语义可能已被其它需求和共同基线覆盖，不能据 ID 缺少直接归属断言有三个功能缺失；应记录等价覆盖或补足归属，避免仅依赖隐含审阅。
- M16 对同一源码、同一 15 个单元审了两遍，共 30 次、累计 SDK 执行约 6 分 20 秒。增加独立会话没有捕获上述路径冲突。应明确单一证明职责；可选实现复核关闭时仍保留普通 Stop 的 M16 源码回退。
- 普通 Stop 的 104 项串行共享一个审查时窗，文件质量排在最后。虽然单项上限为 120 秒，实际文件质量 SDK 仅运行 24.2 秒即取消；不能说它单独耗尽 120 秒。应同时处理对象范围、重复审查和末项时间分配，不能只增加单项上限。

原始 103 个指标对象为：45 PASS、56 UNVERIFIED、1 DEVIATION、1 NOT_APPLICABLE。M09 2/2、M12 14/14、M13 1/1、M14 2/2、M15 1/1、M16 15/15；M11 为 10 PASS、1 DEVIATION、1 NOT_APPLICABLE。这些是原始评审记录，不是补充反例后的正确性认证。

SDK 单项会话共 79 个，累计输入 4,719,658 token、输出 122,046 token，345 轮、797 次工具调用。累计量含跨请求/缓存使用口径，不是同时上下文或账单金额。最大预估单请求 93,470 token，窗口 204,800；压缩、压缩失败和 unsafe-request 拦截均为 0。本次故障没有 overflow 证据。

## 建议的处理顺序

1. 修复手动检查调用身份与当前运行取消后的任务收尾，并补精确的纠偏子运行回归。
2. 将本次存储路径碰撞作为 M16 真实负例，要求审查贯通路径计算、相互覆盖的写入及消费关系；不能用整文件引用和“loaded array”假定代替证明。
3. 明确文档视图适用性及 HARD 义务的直接/等价归属；减少 M16 重复审查，给末项质量审查合理的可用时窗。
4. 修复后再以相同合同、开关和两次上限重跑。当前这次不证明两个纠偏周期、预算耗尽出口、无漏检或总体效率已经合格。

本次没有在实验结束后替业务模型修复应用，也没有修改生产插件以改变这次结果。
