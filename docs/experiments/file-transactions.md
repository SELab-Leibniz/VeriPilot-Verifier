# 文件事务历史复制：独立实验与修复

分支：`codex/file-transaction-deltas`。统计时间：2026-10-14 15:51:41 UTC+8。所有复现均为纯文件持久化，不调用模型或业务系统。落盘实验只使用新建临时目录；默认删除测试目录，未操作原现场数据。

## 定位与实现

问题位于 `lib/runtime-v2/task-store.mjs` 的 `withTaskDecision`：旧提交将完整 `scope.files["task.json"]` 和本次结果写入不可变文件，旧评估历史随每个 hook 被再次复制。

修复保留文件后端、现有任务锁、评估 ID 去重、守卫检查、决策暂存和结果输出流程。新增 `lib/runtime-v2/transaction-journal.mjs`，不增加依赖。

- 普通提交记录 `commitId`、`operationId`、`baseVersion`、`newVersion`、前序哈希、状态增量、JSON 投影增量、本次事件及输出引用。删除提交中的完整 `task.json` 与重复的顶层决策结果。
- 字典逐键记录新增、修改和删除；数组记录追加、索引修改及长度变化。现有历史不会因追加而整体替换。其他 JSON 投影中的历史也采用相同增量机制。
- 默认 4096 字节以上的字符串及大 `result` 使用 SHA-256 内容引用。JSON 评估投影、状态和输出共用正文；测试中 500 KB 正文只有一份大 blob。小结果内联，避免每个普通 hook 再产生一个小结果文件。
- 输出载荷单独保存并引用，输出 ID 为提交 ID 加索引。重试读取原始载荷，沿用原 `roundId` 和路径，不重新生成模型结果或输出轮次。
- 所有 `withTaskState` 更新（含取消、版本、授权等非决策修改）也记录增量，保证完整状态可从检查点恢复。业务 `revision` 与文件日志版本分开；输出确认会增加日志版本，不新增逻辑决策。

## 发布、恢复与保留策略

发布顺序为：正文引用可靠落盘 → 增量提交可靠落盘 → 原子发布 `transactions/head.json` → 写当前任务投影 → 完成其他文件、事件和输出 → 记录投影完成状态。日志、检查点和任务投影采用临时文件、文件同步、原子重命名和平台支持的目录同步。普通读取验证当前任务投影的版本与摘要，失配时回放日志；已发布的待投影文件也可直接按提交读取。

默认每 **128 个日志版本或 4 MiB 增量日志** 建立检查点。这是日志版本数量，包含状态更新及投影确认，不等于模型审阅次数。检查点保存编码后的完整状态和投影引用。

回收顺序为：可靠保存等价的紧凑审计段 → 写检查点 → 原子发布检查点指针 → 删除被覆盖的恢复文件。完整恢复检查点最多保留 **两份**，另保留一份固定的审计初始化基线。崩溃后的下一次锁内维护继续回收，不会永远积累所有检查点。

恢复采用最近有效检查点与已发布增量；最近检查点损坏时尝试之前的检查点，必要时可用审计基线与保留的增量审计重建。已发布记录缺失、截断或校验失败会报错，不会把它静默当作未提交尾部。发布指针之外的尾部和临时文件可丢弃。事件投影的残缺尾行会先截断，再按稳定事件 ID 重试。

明确保留政策：恢复文件在检查点后回收；紧凑审计段、必要结果及其引用长期保留，不自动丢弃审计证据。它们按新增数据量增长。暂不自动回收未被引用的正文文件，以避免误删审计或并发读取所需内容。长久保留的数据仍会线性增长。

## 旧格式迁移与接口边界

第一次锁内访问旧任务时，先恢复旧的待投影提交，再将全量提交转换为逐键状态差分、事件和结果引用的审计段，建立当前状态基线并发布新格式。完成这些可靠写入后才删除旧全量提交。删除过程可在中断后继续；迁移清单完成后清空，避免每个 hook 重复扫描旧文件。

旧记录的事件、结果、其他文件和完整候选状态均可通过增量审计重建。可由当前评估字典或旧发布指针确认的记录标为 `confirmed`；其余保留为 `unknown`，不推定已提交并回放副作用。旧代码缺少独立发布索引，因此无法凭文件存在证明所有旧候选都已发布。旧候选的排列使用旧提交文件名顺序，不声称恢复原格式没有记录的因果信息。

`findTask`、`withTaskState`、`withTaskDecision`、评估结果结构及完整当前 `task.json` 的读取保持兼容。升级后当前文件是投影，修改应通过 `withTaskState`；手工覆盖当前文件不再构成提交。常规 JSON 投影保留缩进、换行与末尾空白；特殊布局和非 JSON 文本按原文保存。JSON 对象键的排列视为数据等价。切换时需停止旧格式写入者和直接依赖旧提交文件名的读取者；不要混用旧、新版本写入同一个任务目录。

以下只累计序列化字节，不生成大型文件。新增记录为 300 字节元数据。增量列扣除初始化正文、基线及检查点，只统计普通日志记录；记录大小的微小差异来自序号长度与首次前序哈希。

## 实际任务存储 hook 路径

直接调用项目的 `withTaskDecision(kind="hook")`，插入 80 次操作，并重复请求每次操作一次。复现不执行模型。

- 80 次逻辑决策、80 个事件；80 次重复请求没有再次计算或生成新事件。日志共 161 个版本，包含初始化状态更新与投影确认。
- 以同一组实际状态重建旧格式，事务合计 12,058,971 字节；新保留增量及审计记录 161,759 字节。
- 旧普通提交从 133,208 增至 168,276 字节；新普通决策提交从 1,474 到 1,446 字节。首次创建评估字典的开销也计入。
- 新任务目录共 41 个文件、505,493 字节；这包含正文、当前状态、审计及检查点，不与仅旧事务字节混淆。
- 工作期间实际完整任务状态写入 **24,311,356 字节（24.311 MB）**，通常每个决策两次（发布与投影确认）。保留完整状态接口意味着这部分写入仍随历史增大；本修复没有消除所有写入放大。

当前状态读取、克隆、差分比较仍需遍历历史，周期检查点仍整体写编码状态，其他文本投影和用户报告仍会物化。有限检查点限制保留空间，不等于累计检查点 I/O 已变为线性。

## 验证与复跑

最终全套 `npm test`：**776 项测试，774 通过，0 失败，2 项原有跳过**；其中新增文件事务与恢复测试 25 项全部通过。编译后的插件、onboarding、Ground Truth、纠偏预算、原生工具 hook、SessionEnd、报告、交互控制、取消和监督执行均包含在全套检查内。真实运行环境为本机 macOS；瞬时重命名错误用故障注入验证，未在 Windows 实机运行全套。

调用链复查额外修复了三个兼容边界：`readReport` 在新提交发布但投影未完成时按日志版本读取证据；纯时间戳刷新和投影确认不增加业务 revision；决策计算内的 `ensureTask` 继续暂存，取消时丢弃候选状态。它们均有单独的并发或恢复测试。

恢复测试覆盖提交落盘未发布、发布后任务/文件投影未完成、输出失败及重试、残缺尾部、审计归档/检查点发布/回收各中断点、检查点损坏回退、迁移中断、并发重复操作和取消/过时守卫。另覆盖其他 JSON 历史的增量与回收后旧版本读取，以及按字节触发检查点。

关闭测试暴露禁用轮询重复排队取消写入的竞态；取消入口现只排队一次，避免结束后再创建锁文件。测试使用状态更新接口模拟关闭，并等待异步工作开始和发布锁释放，避免仅依赖固定 20 ms 等待。
