# TodoList 实验发现的插件问题修复

原实验与原始结论见 [TodoList M16 端到端实验](todolist-m16-e2e-20261025.md)。本轮在 `codex/m16-production-implementation-coverage` 分支修复插件；原会话、原 Gateway 配置、原业务源码及原评审结果均保持原样。

## 修复内容及必要边界

### 手动检查的调用身份

OpenClaw 工具工厂上下文没有当前 `runId`。`entry.mjs` 现在将执行时的 `toolCallId` 和取消信号传给 `manualCheck`，后者只从 PreToolUse 保存的对应绑定恢复运行身份、项目指纹和取消信号。缺失、歧义、跨会话、不匹配或过期绑定会立即返回明确错误，不再进入自己的 Stop 等待链。不会使用工作目录或“最近的运行”猜测身份。

注册入口回归通过真实 `entry.register → tool.execute → manualCheck` 验证工厂上下文缺少 runId 的情况；另有纠偏子运行回归证明自己的检查正常返回、Stop 等待门仍然保持，外部后续任务并未被提前放行。

### 中断后的回执与任务收尾

只允许当前运行的终止事件，在自身无效化后写入 `STOPPED_UNVERIFIED`。围栏仍核对运行、等待链、项目作用域及任务取消/完成状态；新运行会清除旧运行的终止标识。取消时捕获原等待链，避免异步清理误取消后来创建的链。

`CANCELLED` 回执可以补写结束时间和未验证原因，但保留取消身份，拒绝迟到的 PASS 或业务裁决。两种等待模式 `until_pass`、`assessment` 都有相应收尾回归。原评审证据保留在 `previousVerification`，中断不会伪装成通过。

### M16 的数据流审查与重复工作

六项通过条件保持合取关系。策略新增：追踪合法输入、所有相关写入和最终消费者，核实真实返回类型与后续读取，不从变量名、帮助函数名称或“存在调用”推断正确性；可配置资源必须比较主数据与辅助数据的实际目标身份，检查覆盖和路径别名。合法输入导致必要消费者确定性失效，即构成偏差，普通样例或测试通过不能抵消它。

真实复验发现，仅增加文字提示仍会漏掉辅助写入。当前目录版本更新为 `vp-m01-m16-v7-production-trace`，提示版本更新为 `scoped-review-prompts-v9-production-trace`，旧缓存因此失效。原生策略与单项 SDK 策略仍由相等性回归保证一致。

单项 SDK worker 现在对 M16 PASS 强制要求 `productionTrace`：实际入口、输入、生产者到消费者的关系、持久/共享状态目标及其读写内容，以及每对目标在合法输入下的重合尝试和数据流影响。状态目标与关系引用必须绑定已读取的当前目标源码 citeIds；未知身份、未知效果、已知破坏或缺少目标比较均不能构成 PASS。无状态路径需要说明实际输入如何被消费，不新增持久化义务。

这是一层可审计的证明协议校验，不是能自动证明任意代码语义的静态分析器。最终语义结论仍由模型负责；它不能保证发现所有遗漏。明确的源码反例可直接支持 DEVIATION，无需先补齐完整 PASS 证明；非 PASS 的可选 trace 不作为已验证证明发布。SDK 保存证明并在结束时再次校验，Stop 适配器也拒绝缺少有效证明的 M16 PASS。其它原生/CLI 传输沿用各自现有输出协议及增强后的 M16 策略，本轮没有将它们冒充成同一 SDK 协议的真实模型复验。

同一次 Stop 已获得完整读取证明、当前源码引用的 M16 PASS/DEVIATION，不再重复交给可选实现审查。该结论保留 Stop 审阅者归属，复用对象 ID 记录在 `implementationReview.reusedStopSourceObjectIds`。UNVERIFIED、无读取证明或伪造 PASS 仍进入实现审查；已有偏差不会被覆盖成通过。普通 Stop 在实现审查关闭时仍负责 M16。

### 调度与冻结义务

文件质量作为独立职责先执行，避免在大量指标后只剩很短的共享窗口。共享截止时间和单项上限没有增加；剩余未运行对象仍显式记录为 UNVERIFIED，质量检查结果不能代替指标覆盖。

仅交付代码且未指定文档指标时，明确标注 IMPLEMENTATION/PROCESS 的义务不再展开成文档视图；混合基线里的真实 ARTIFACT 义务仍保留。每条尚无相应履约对象的 HARD 实现义务补入 M12，不以 M16 覆盖证明冒充履约执行。不会删除或修改冻结需求来消除未知项。

## 离线验证与交付边界

相关范围回归覆盖 M16 分母、混合基线、证明所有权、真/伪源码证明、可选实现审查开关、偏差保留、缓存、收尾和注册入口。测试替身只验证机制，不作为模型准确率证据。具体结果见工作区 `.runtime-correction/m16-fix-*.log` 和验证清单。

- 指标、实现审查、混合基线、缓存与项目注册入口等相关回归：222/222 通过，记录于 `m16-fix-regressions.log`。
- 最终生命周期、等待链、回执、collector、证明边界和 SessionEnd 批次：191/192 通过。唯一失败是已有 SessionEnd 看门狗的 1200ms 计时断言，当轮实测 1221.3ms；未放宽阈值或修改该测试，单独串行复查该文件 7/7 通过，记录于 `m16-fix-session-end-serial.log`。不把原批次写成全绿。
- 当前修复的取消回执、自等待和两种中断收尾模式另行隔离复核：6/6 通过，记录于 `m16-fix-terminal-isolated.log`。
- 三个宿主插件构建成功；逐个加载确认 16 指标、M16 两处策略相等、目录/提示版本正确，并核对构建源码字节与工作区相等。当前源文件、构建和日志哈希保存在 `.runtime-correction/m16-fix-validation-manifest.json`。

本轮没有重跑全量套件；初次接入的全量结果及原有环境失败记录仍保留在 M16 接入文档。本轮未替换正在运行的宿主插件。

`experiments/todolist-e2e-20261024/validate-m16-repair.mjs` 准备了 7 项真实模型输入：原缺陷两次、使用单文件原子信封的修复副本、固定成功结果、丢弃关键返回值、不可达调用，以及需求明确允许的 Mock。独立修复副本通过原 10 项验收，路径冲突反例改为返回数组；原缺陷两份副本仍复现反例，原实验源码 SHA256 保持不变。修复副本不是修改后的原实验结果，也不是新的自主开发端到端实验。

输入已通过 `--prepare-only` 保存于 `experiments/live-m16-repair-validation-prepared-20261025/report.json`，该模式不读取模型认证配置或调用外部服务。真实复验会使用上次实验的 `custom/deepseek-v4-flash`，向配置的同一服务发送各项源码和对应需求，不发送认证配置文件或密钥。

第一次真实复验调用被自动审批拒绝，理由是这批具体源码外发授权不够明确；随后用户明确允许按上述七项范围向指定服务复验。授权后的调用及每次修复迭代保留独立输出目录，不覆盖先前漏报或超时记录。它们属于同组输入的单项源码复验，不是完整 Gateway 自主开发端到端重跑。

## 授权后的真实模型结果

同一组业务源码和需求保持不变，模型始终为授权的 `custom/deepseek-v4-flash`。输出目录依次为 `experiments/live-m16-repair-validation-20261025-01` 至 `-05`：

- `-01`：受限环境连接失败。保存的 5 个 worker 结果均无源码工具读取或模型用量，中止后换获准的网络执行方式；不将它们作为模型准确率结果。
- `-02`：v4 数据流提示，5/7 符合预期；原 TodoList 缺陷两次仍错误 PASS。
- `-03`：v5 补强反向数据来源追溯，仍为 5/7；模型开始检查业务写入，但仍忽略可能覆盖业务数据的辅助写入。这轮证明单纯继续加提示不足以解决该漏报。
- `-04`：v6 加入强制生产读写证明后，6/7 符合预期。原缺陷两次均正确 DEVIATION；修复副本因目标关系端点使用说明文字而非声明 ID，错误提示又不够具体，重复提交至 120 秒超时，不能算通过或业务偏差。
- `-05`：v7 明确 ID 引用与字段错误，明确反例无需完整 PASS 证明。最终 **7/7 符合预期**，没有放宽共享期限或单项超时。

最终判定逐项为：原缺陷 A、原缺陷 B、固定成功值、丢弃返回值、不可达调用均为 DEVIATION；单文件原子信封修复副本、需求明确允许的 Mock 均为 PASS。两次原缺陷都指出同一个可达的合法输入反例：主存储和辅助元数据目标重合，后写的元数据对象覆盖条目数组，后续 list 返回错误类型。修复副本在所选文件内一起保存业务数据和元数据，消费者提取条目数组，因此同一反例恢复为正确输出；原 10 项验收也通过。

最终轮耗时 205.299 秒，单例 10.327–63.764 秒，27 个模型回合、43 次工具调用、83,675 字节读取；保存的 SDK 累计输入 178,439 tokens（含缓存读取/写入）、输出 19,615 tokens。无提交协议错误、提交前提供方错误、上下文越界或压缩失败。每例在确认 `submit_review` 保存成功后有一次 SDK 中止尾消息，符合引擎保存后关闭的既有流程；它们单独记录为 7 次 `postSaveCancellations`，不冒充提供方失败或额外业务纠偏。

同任务修复期间所有已保存 SDK 结果合计输入 625,046、输出 65,079 tokens，包含前面漏报及超时轮次；最终轮用量不能当作整个修复过程用量。用量均为 SDK 累计记录，不是精确计费或 HTTP 请求数。更完整的数据流审查比最初只看读取分支的错误 PASS 更耗时，本轮没有消除大型完整 Stop 的总预算风险。

最终源码输入及冻结需求逐例与已授权的准备副本相等，原实验源码哈希不变；每个结论均有实际读取的当前 SOURCE 证明，两个 PASS 的 `productionTrace` 均经过再次程序校验。最终工作区核心代码哈希与本轮审阅版本一致，三个构建的核心文件也逐字节相等。

当前证明协议、SDK 提交、取消和 M16 适配回归 94/94 通过，见 `.runtime-correction/m16-trace-regressions-final.log`。前一证明版本的集成/缓存/打包回归 216/216 通过，见 `m16-trace-integration.log`；最终版本三个宿主重新构建并通过版本/字节核对，见 `m16-trace-build-final.log` 和 `m16-trace-validation-manifest.json`。
