# Stop 审查、预算与状态

1.10.0 的新项目模板使用原文 Stop 与仅偏差模式（B12）。除原文要求外，审查对照原有代码或原有测试和当前实现，报告本次改动破坏的既有行为。反证缺失时不提交偏差。基线路径沿用原有提示。已有配置仍按旧缺省值生效。切换基线路径需要打开 dynamicGroundTruth.enabled 并关闭 stopCorrection.originalRequirementsBasis。需要完整逐项审查时同时关闭 stopCorrection.deviationOnly。文档纠偏的切换见 [配置参考](configuration.md#新项目模板与旧配置)。

每轮结果的 `review.scopeSelection` 记录实际分类、基线版本、全量对象数、范围内对象数，以及各开启指标的原始对象、选择状态和排除原因。`review.metricObjectJudgements` 才是正式保存的指标判断；findings-only 的扫描任务完成数不代表指标通过数。

回归分流只豁免任务开始时已确认失败的条目。整套失败但单独重跑通过的条目保留为 `REVIEW_REQUIRED`，记录 `isolationObserved` 和原因；它可能是本次改动引入的共享状态或顺序依赖，不能仅凭单跑通过认定无关。分流版本进入检查缓存身份，旧 `TEST_ISOLATION` 记录可读取，但不会继续从待审失败清单中自动排除。

授权判断须区分原始断言、测试准备及后续操作。补 mock 后通过不能授权原始失败；调用方单测不执行被替代的被调用方实现，是正常的测试范围。对原要求约束的调用入口，分别核对实际依赖结果与第一次可观察副作用；下层拒绝不能代替调用入口自己的保证。上述判断使用原要求和源码，不新增引用门槛或整体未验证条件。

分类提交协议 v2 要求说明原回复是否声明完成，以及必要的用户决策或外部阻塞。完成后提供可选建议仍选择完成范围；只有真实未解决的必要输入才能选择等待用户。纯实现义务不提供 proposal/design/tasks 文档阶段供分类器选择。仅偏差模式下，proposal、design、tasks 等前置阶段完成时不审查原始生产实现义务（`verificationTarget: IMPLEMENTATION`），这些义务留给编码阶段或任务完成时审查；程序自有的回归义务仍在范围内，排除后为空的范围记录 `NO_APPLICABLE_STAGE_OBJECTS`。合法阶段没有声明指标时记录 `STOP_STAGE_METRICS_UNDECLARED`；合法空对象范围记录 `NO_APPLICABLE_STAGE_OBJECTS` 或 `NO_APPLICABLE_METRIC_OBJECTS`，保持未验证，不能以 `NO_CURRENT_DEVIATION` 冒充已检验。独立文件质量审查仍可在无指标对象时工作。

新增实现义务可携带结构化 `implementationRole`：`PRODUCTION`、`TEST` 或 `SUPPORT`。测试源码义务保留在 M12 的原始分母，明确标为 TEST 的义务不投射到 M16 生产实现覆盖。实际运行测试应另作为 PROCESS 义务保留。旧账本没有此字段时沿用原归属，不根据名称、描述或文件是否存在悄悄删除历史义务。

生产 Stop 由 `orchestrator.mjs` 进入 `production-stop.mjs` 与 `assessStopCorrection()`，由 `stop-workspace-review.mjs` 的单一私有会话完成分类、指标、findings 和文件质量审查，`stop-review-round.mjs` 结算逐项回执。没有静默回退旧 Stop 核心。显式只读验证复用审查机制，不领取业务续作准入，也不终止已有自动流程。

明确要求在本次任务交付的具体文件路径以 `expectedFiles` 保存到对应 Ground Truth claim，并进入指标对象。例如 `text: "生成 docs/report.md"` 对应 `expectedFiles: ["docs/report.md"]`。初始抽取、后续刷新和紧凑抽取均支持此字段；它不从当前已存在文件反推，也不把输入、引用代码、示例、通配符、目录或未来运行产物自动升级为必交文件。没有明确路径时不猜测名称；旧账本缺少该字段时保持原行为。

当审查选择 `TASK_COMPLETE` 时，程序对已开启 M12/M16 中具有可信来源、HARD 且 `CURRENT_TASK` 的文件义务逐个检查存在性。确认不存在或目标不是普通文件时，保存程序生成的缺失证据和 `DEVIATION`，沿原有额度、宿主启动协议和反馈链触发主 Agent 补写；不需要读取不存在文件，也不依赖文件质量开关。存在文件不会自动得到 PASS，仍需内容或实现审查。条件、未来、未知范围及中间/阶段输出不自动判缺；权限或 I/O 错误保留为未验证。结算、反馈和报告均重新核对观察状态；文件补齐或原路径状态改变后，旧缺失证据失效。

M16 的条件性失败保证必须保留原要求中的准确失败操作与触发条件。审查按顺序核对失败前后的写入，并区分内存、持久化及外部系统状态；返回失败或捕获异常不表示此前写入已撤销。“状态不变”或“已回滚”需要实际补偿写入的源码证据，涉及别名时还须核对快照是否独立。理由和 productionTrace 都不得扩大未经证明的保证，例如派发失败不保存，不能推出持久化失败也没有状态变化。原要求的具体路径被反例推翻时判 DEVIATION，证据不足时判 UNVERIFIED，不额外添加原任务未要求的失败原子性义务。该约束加强审查依据，程序仍只验证见证协议与来源，不宣称自动证明任意程序语义。

## 配置

```yaml
version: 2
artifacts: []
dynamicGroundTruth:
  enabled: true
stopCorrection:
  enabled: true
  waitMode: until_pass
  maxCorrectionsPerSession: 3
  maxCorrectionsPerFlow: 3
  assessmentTimeoutMs: 1200000
  feedbackReserveMs: 180000
  reviewGroupSize: 3
  fileQualityReviewEnabled: false
```

指标默认值与全关行为见 [指标开关](stop-metric-switches.md)。两层次数可以为零；分组大小和时间为正整数，预留必须小于总时限。默认 20 分钟包含 3 分钟结算/交付预留；缩短总窗口时需要显式缩短预留。

旧 `maxCorrectionsPerEpoch` 只映射为 `maxCorrectionsPerFlow`；旧 `waitTimeoutMs` 只映射为本次 `assessmentTimeoutMs`，均产生弃用提示。新旧同义字段同时出现时报错。需求变化不清零会话额度，业务修复不占已经结束的审查窗口。

Stop 将已确认的完成类型及阶段与审查范围一起持久化。`STAGE_COMPLETE`、中间输出、等待用户或外部阻塞的完整审查若没有当前偏差，只结束本次 Stop；同一范围、同一阶段的旧修复等待也可结束。这类非最终 Stop 的审查正常结束但没有结论时（例如范围为空、没有声明适用指标或多数要求未验证），当前 Stop 仍为 `UNVERIFIED`，只结束本次 Stop，不关闭 flow，也不结束尚未确认修好的旧偏差。后续 coding 等阶段仍在同一用户 flow 内进行完整审查，沿用会话及 flow 的已用次数、未决预约和上限，不创建新额度。已结束阶段的旧定时器不再终止后续阶段。`TASK_COMPLETE` 没有当前偏差时（包括未验证）关闭整个 flow；未记录完成类型的旧调用保持原来的关闭行为。审查执行失败（准备或审查过程抛出错误）、取消、超时、依据过期及实际额度耗尽仍遵循原来的终止保护，已关闭的历史 flow 不自动重开。

## 单会话审查

Stop 使用一个私有 task 会话。它先完整读取原始依据，再通过 `review_checklist` 的 `stopClassification` 同时确定停止类型并取得原始清单，自行规划审查顺序、读取原文并逐项提交。最后一项可用 `submit_review(finish: true)` 一并结算；复杂流程也可单独调用 `review_scope` 和 `finish_stop_review`。提前请求结算不能跳过剩余条目。必要的 Ground Truth 更新仍由独立的来源提取协议负责；基线未变化时复用已有基线。旧 `stopReviewEngine: native` 仅作为配置兼容值归一到 task。Stop worker 使用 200 个累计助手响应轮次及 32768 单次输出 token 上限；首次运行后最多在同一会话续跑一次，沿用原截止、已读凭据和已保存结果。最终自然语言不能替代提交回执。

OpenClaw 使用宿主原生工具和持久化回执。Claude / CodeAgent 使用私有 MCP 工具连接同一引擎，程序只接受所属 CLI 会话真实输出的、与原文页完全一致的工具结果；执行了 MCP 调用或持有引文编号都不足以证明模型读到了内容。首次会话不继承业务对话，续跑恢复相同私有会话。CLI 内置写入、命令执行和派生 Agent 工具关闭，计划与笔记仅由程序写入 RC 自有目录。此工具权限与源码可读路径是两回事。

生产模型入口仅接受 `workspace-stop`，旧的独立分类、指标分组和复制源码 Stop 请求会在启动模型前被拒绝。安装包不再包含旧 worker、TypeBox 或它们的依赖清单；三种宿主的 RC 运行代码只使用 Node 内置模块。旧组件通过仓库中的显式测试或开发对照入口使用。来源基线提取与非 Stop 角色保留各自的核验流程。

编排层同样只请求完整工作区审查，工厂的旧分类、分组或补充文件能力标志不能切换流程。候选交付文件在同一会话确定任务/阶段完成范围后收集，通过范围结果与清单交给审查者；中间输出、等待用户和外部阻塞不触发这次交付内容扫描。指标、findings 和已开启的文件质量在同一会话内完成；程序随后验证完整输出，并按独立条目结算。旧的逐项 PASS 缓存不代替本次已选清单的检查。

直接读取当前工作区的原始文件，无需预先复制代码仓。`source_read/grep/find/ls` 接受绝对路径、父目录和链接文件；源码清单与候选文件是导航提示，不是读取白名单。读取权限由操作系统和宿主决定。递归导航默认跳过 `.git`、`node_modules` 和 RC 输出目录，可用 `includeGenerated` 显式搜索；直接读取这些路径没有 RC 目录禁令。

递归 grep/find 从当前项目或相关源码子目录开始，单次最多访问 4096 个路径条目、读取 16 MiB 搜索内容。达到扫描预算会明确返回 `scanIncomplete: true`，此时零命中或 `nextOffset: null` 都不表示搜索完成；应缩小目录或直接读取已知文件。条目预算也涵盖空目录，防止无命中遍历长时间占用审查。该预算限制单次导航工作量，不限制外部来源或具体文件的读取权限，也不授予缺失判断证据。

审查者可使用以下工具组织工作：

- `review_changes`：Git 状态、文件 diff、宿主编辑过的路径及修改片段。支持原生 `edits[]` 批量修改和 CRLF 补丁，逐处分页并标明预览截断。它们是调查入口，不能直接充当验收证据。新建未跟踪文件也会列出。
- `semantic_graph`：终审会话启动前，RC 用有限预算从当前 Git 工作区建立索引，优先处理本任务改动的文件。用 `search` 按关键词找符号和测试，用 `definition` 定位确切符号，用 `outline` 查看文件定义，用 `context` 查询方法的调用、写入和现有测试引用。文件级关系仍由 `dependencies` 提供。索引覆盖 JS、TS、ArkTS 可静态解析的关系，路径和行号引导 `source_read`。图不可用时，审查继续使用原有导航工具。
- `review_plan`：保存和更新审查计划，不改变原始验收项。
- `review_checklist`：选定停止范围，分页查看原始义务、每项证据归属（`proofOwners`）、已保存结果和未完成项。`processEvidence` 提供原始用户记录、实际执行结果及匹配调用的有界样例和总数，支持直接定位较长历史中的记录；这些指针不授予引文。纯过程执行项还标明 PASS / DEVIATION 所需的结果证明。PROCESS 要读取原始过程文件，SOURCE 要读取生产代码；必读基线和 Skill 条件不代替过程证据。
- `review_notes` 与 `review_history`：保存笔记，压缩后恢复观察记录、回执和原有引文。笔记不获得原文证据资格。
- `submit_review`、`submit_finding`、`finish_stop_review`：逐项保存经校验的结论，全部条目完成后结算；最后一项可直接携带 `finish: true`。

M16 的一个原始条目可能包含多个效果和失败分支。PASS 必须分别追到各适用分支的实际消费者，区分返回失败与抛出异常；`await` 后的代码不覆盖拒绝路径，`finally` 也只证明其中实际执行的操作。回滚或清除忙标志不能代替独立要求的状态刷新。若依赖下层把异常转为失败返回，需要核对相关调用边界的完整源码契约；原要求未覆盖或明确排除的异常分支不额外增加义务。

其他 RC 模块可直接从 `lib/semantic-graph.mjs` 导入 `buildSemanticGraph(projectRoot, options)`，再调用返回值的 `query({ operation, symbol, file, offset })`。`incoming` 找调用者和测试，`outgoing` 找调用、写入及控制语句位置。不能解析的调用保留调用点。查询使用项目相对路径，`partial` 表示索引有遗漏，`unavailable` 表示无法建立索引。图记录是静态导航线索，结论仍以原始源码和正常引文为依据。

`context`（包括 `incoming` / `outgoing`）还会返回有界的 `testBoundaries`：关联调用者、依赖调用点、把该依赖作为参数传入测试辅助函数的位置，以及之后的调用或写入位置。测试的 `beforeEach` 等钩子保留自己的行号范围。结果轮流覆盖不同调用者，优先关联实际调用该入口的测试文件，避免单一测试夹具占满首屏。Stop 的 `currentSemanticLinks` 也携带这些关系。图不推断辅助函数是否真的替换依赖，也不证明后续调用在同一分支可达；澄清和终审共用的代码理解 skill 引导模型读取源码、测试设置和返回值，再判断各入口的保证。

启用程序回归检查或实现验证时，范围选择使用协议层已有的交接：先结束当前原生 Reviewer 调用，再执行程序检查，随后沿用同一会话、清单、读取回执和剩余预算续审。长时间测试不再占用 `review_checklist` 工具调用，以免被宿主误判为工具停滞。交接不构成完成结论，不重置终审 deadline、纠偏次数或取消与过期保护。

过程义务还要核对执行者和原始事件顺序。修改前的读取不能证明修改后回读，私有审查者自己的 `source_read` 只能证明当前内容，不能替代业务执行者此前的操作。文件整体的编码/语言适用性不能从一页 ASCII 片段反推；证据范围不足时保留 UNVERIFIED，不虚构执行或豁免。条件性项目规范须按原触发条件设置逐项 applicabilityKind，不能仅因属于当前仓库就全部设为无条件当前任务。

M16 见证中的写入指生产程序初始化及运行时操作；开发者编辑源码不是应用对存储状态的写入。资源引用须为本次提交顶层 citeIds 中的当前生产源码引用。校验错误会指出具体 stateTargets 下标和字段，保留原证据边界；有状态见证仍须显式带 `statelessReason: ""`，结构继续使用 version 1。

GT 自动条目 ID 同时区分原文来源与证明范围，包括 verificationTarget、implementationRole、适用条件和显式输出，避免同一段原文的过程与实现条目互相覆盖。已有 ID 不迁移、不重写，相同语义的重复 ADD 保留原 ID；ADD 不得通过推导 ID 替换已有或已撤回条目，修改旧要求仍需明确的修订操作。

程序仍可在分类后运行已配置的确定性能力检查和设备验证，将实际结果交给同一审查者；不会为此再启动一个实现审查 Agent，也不为没有缓存消费者的设备验证预先计算全仓源码清单。源码与进程证据的归属规则仍分别执行。

已保存的部分结果保留原始分母和未完成项；完整输出中的未知、重复条目不能在分组筛选时消失。缺少文件质量判断会明确留下该文件的 `UNVERIFIED`，未通过证据校验的文件结论也不能继续显示为已确认偏差。没有进展的旧过程偏差由本次完整审查及仍有效的旧证据共同核对，不另起一个只查旧失败项的 Agent。

Stop 启用且有审查对象时，先准备 GT、分类、收集源码并启动 reviewer。发现当前偏差后，才根据会话和流程额度预留修复名额。审查冻结原要求、条件、例外、公共约束和证据版本；中间输出、等待用户、外部阻塞、阶段完成和任务完成分别确定适用范围。

审查者跨指标复用已经读取的原文，自行决定调查顺序。`reviewGroupSize` 继续控制结算时的回执分组，不决定模型会话数量。条目身份、指标分母和逐项验收保持独立；不能用一个总体 PASS 替代成员判断。未完成的审查保留已保存的条目、笔记及未完成清单，不能冒充完整验收。

原文工具、字节分页、单次披露边界、程序引文和 M16 生产链证明见 [读取边界](stop-review-bounds.md) 与 [M16](m16-production-implementation-coverage.md)。取消累计字节中止条件不改变原文读取回执、哈希、完整覆盖及截止与取消校验。同一会话续跑可复用仍有效的逐项结果；新 Stop 重新检查清单。配置、模型、指令、绑定或证据变化不能复用失效判断。额外文件质量审查由独立开关控制。

同一审查者可以查看测试源码、生产源码和过程记录，但这些证据不能相互冒充。M09/M16 的生产实现不能仅由测试代码证明；源码也不能证明实际执行成功。M12/M13/M15 的纯执行义务要求读到可对应的原始调用与结果，或程序实际产生的构建/设备结果。仅有完成声明或缺少执行记录只能得到 `UNVERIFIED`，不能据此认定执行成功或失败。已读文件、检索过的目录与检索输入变化后，旧结论失效；未访问的无关文件修改不会触发全仓重扫。可变 RC 日志和审查笔记可读，但不授予业务证据，也不会因自身继续写入而使业务证据失效。

M08 的原始 Skill 按宿主默认目录和 `skillCorrection.skillRoots` 定位，生产 Stop 将配置目录传给同一会话；这些目录可以在项目之外。清单提供必须完整读取的原始文件及传递依赖条件。Skill 的条件不适用只能影响对应条目，不能豁免独立的用户执行要求。真实 Claude CLI 与原生宿主均已验证同一会话分别保存 Skill 不适用、执行未验证、源码实现通过四项结论，整体仍保持 UNVERIFIED。

## 额度、启动与等待

会话额度跨任务、需求修订和项目作用域累计；流程额度只限制本条纠偏链。只有宿主可信地确认实际开始一次业务修复才同时扣一次，两者不因审阅或通知次数增加。未知在途请求保留预留待核对，不自动重发，也不直接当成未开始。

`assessment` 等审查结算和有效反馈交付，然后解除等待；流程最多实际纠偏一次。MA 的 `until_pass` 使用[运行结束后的独立调度](until-pass-dispatch.md)：本轮正常结束后才审查，反馈另起一轮纠偏，用户待办独立保留。各轮有独立审查窗口，及时开始的修复不受旧审查计时限制。

次数已用完或缺少可信历史时，Stop 仍按本轮证据发布结论，并放行本轮。遇到已确认偏差时，回执说明为何暂缓自动修改。MA 适配对已经实际执行的最后一次修复保留有时限的只读复验，不再授予修复额度；审查和修复仍有各自有限等待窗口，漏终态不能无限挡住后续任务。没有可信逐次启动历史的旧会话进入迁移核对，不能默认累计次数为零。两种等待模式的适用范围、跨运行交接及异常处理边界见 [MA 适配](openclaw.md)。

## 取消、依据与恢复

实际内置 OpenClaw 2026.7.1-2 的隔离 Gateway 已验证自动派发、可信启动后扣量一次、业务模型真实修复与新 Stop PASS，并验证额度用尽后的最终只读复验。完成后在新进程重启同一隔离宿主，验收身份与计数保留且没有重放模型；审后修改已读源码会使官方报告变为 STALE。另一次正常首轮通过实际鉴权的 `sessions.create` / `chat.send` 执行业务模型与真实宿主钩子，取得一个 Stop 会话、三个原始验收对象逐项 PASS、纠偏用量为 0；该轮没有预置完成事件。离线审计交叉核对真实用户消息、成功业务终态、原分母、诊断、私有运行和官方报告。自动修复案例的初始错误交付仍是程序夹具，正常首轮独立提供了实际业务入口证据。Electron 桌面操作、执行中断恢复及真实上下文压缩仍未实测；独立嵌入实验的进程清理限制一并记录。开发期复现入口和原始记录保留在源码仓库的 Stop 简化进度文档，发行包不携带实验进度材料。

取消、关闭、项目切换、总截止和反馈发布均有身份与当前性围栏。有效偏差子集可以重新筛选，不能生成新条目或悄悄修改旧条目。检查器失败属于基础设施状态，不能伪造成业务违规；同一轮不会因此反复重派。

业务执行结束与其后复验分别结算。复验期间取消或超时，必须关闭准确的父执行和子审查归属，失效对应回执并保存未验收原因，不能因已有 `endedAt` 而停留在 `STARTED`。已发生的实际启动计数保留；已经完成的有效最终审查作为历史保留，不被后来的取消改写。

结束流程释放同一流程内旧 Stop 的等待，保留原评估事实。恢复必须确认原拥有进程已退出，保留逐项回执并关闭旧审查轮；缺少拥有者时沿用原绝对截止。迟到事件只影响所属 Stop，不能取消后来的独立运行或待办。

宿主必须提供经过验证的启动门、真实开始观察和精确运行取消能力；否则返回 `HOST_START_PROTOCOL_UNSUPPORTED`，保存偏差、解除等待且不自动续作。MatrixAssistant 和不同 OpenClaw 版本的具体边界见 [宿主指南](openclaw.md)。离线回归覆盖单会话派发、CLI 的真实 MCP 传输协议、外部读取、证据凭据和并发失效。真实 Claude CLI 与本机内置 OpenClaw 2026.7.1-2（GLM-5.3-flash）分别验证了正确实现、外部依赖缺陷和缺少执行证据三种结论；另有原生生产 Stop 入口的只读验收，以及真实业务修复后新 Stop 再验收通过的案例。后者使用两次只读验收，不证明自动派发与启动额度；原生模型仍有偶发超时。这些小样本不证明普遍准确率。CodeAgent 目前验证的是受控 CLI 协议；桌面长时流程、执行中断恢复与真实上下文压缩仍需实测。

## 流程闭合补充

- 旧公开断言被原始需求合理推翻后，单独运行通过仍不足以豁免其它失败。RC 可以用自己的回归入口在一次性副本排除这些精确用例，再跑完整剩余测试树；只有基线、排除集、运行回执及所有剩余用例都核对完整，消失的失败才标为 `COLLATERAL_FAILURE`。实际回归及仍失败的项照常阻断。原测试树与原回执不改。
- 纯历史顺序偏差需由审查员提出，并由程序绑定同一原义务与两次成功、严格倒序的原始调用/结果。缺事件、并发调用、重复调用身份、当前可修复残留不符合此规则。同一流程中相同事实只通知一次；纯通知没有业务准入、不扣额度。只有历史偏差且其余验证完整时，终态为 `COMPLETED_WITH_HISTORICAL_DEVIATIONS`（带历史偏差结束）；原 `DEVIATION` 保留，不能称为 PASS 或未发现偏差。
- 原命令的“环境不可执行”例外要求宿主实际生效工具清单、会话身份及当前工具策略均可由程序验证。当前仅支持已核实的固定版本原生文件工具；任何执行、构建、测试、委派、未知自定义工具或策略变化均不能证明不可执行，仍保留 UNVERIFIED。业务自述无工具不构成证明。获准例外逐项写入 `environment-unexecutable.json` 及终审结果，不合并成验证不完整。
- 大于 8 KiB 的语义导航改为无损文件指针，仍可按需读取；它只用于导航，不能代替实际源代码或执行证据。

### 流程偏差的修复性质

原始义务中的 PROCESS 偏差必须在 `finish_stop_review` 明确分类：`historicalOrders` 绑定两次成功且倒序的原调用；`processRepairs` 绑定义务 ID、当前仍存在的影响和有用的后续修复动作。缺失事件不能证明顺序违规。仅说明历史无法补救不构成当前残留；未分类的候选在完整结果、部分结果和额外 finding 通道均保留为 UNVERIFIED，不派发续修，也不代表通过。真实当前缺陷经明确分类后仍按原规则纠偏。纯历史偏差使用既有独立终态和一次通知规则。

回归判定兼容 `cases` 与旧版 `explanations` 同时提交：两份列表分别校验 ID 归属和唯一性，同 ID 以 `cases` 的显式判定为准，不能用旧解释覆盖 UNVERIFIED 或已证明的 REGRESSION。`REVIEWED` 混合模式下，未列入 `cases` 的旧解释只有明确填写原文授权 `authorization` 才记为 AUTHORIZED_CHANGE；整体 UNVERIFIED 的旧解释仍未定。授权后仍需程序绑定的完整控制整套运行，才可确认其余失败属于连带失败；单独通过不构成豁免。
