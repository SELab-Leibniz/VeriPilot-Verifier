# Stop 纠偏重构需求

- 文档版本：1.1
- 整理日期：2026-10-25
- 性质：依据本次需求讨论整理的目标需求，供实现、审阅和验收使用。
- 实现状态：尚未按本文完成重构。本文中的目标配置、状态和流程不得表述为当前代码已经支持。
- 适用范围：Stop 自动审查、偏差反馈、业务纠偏续作及其复验。其他插件功能继续遵循各自规则。

本版补充：未开始纠偏时的有界退出与迟到事件、按结论区分的 M16 保存门槛、跨 Stop 的公平调度游标、历史偏差与当前有效结论的分离。相关流程图和验收场景同步更新。

## 1. 目标与范围

### 1.1 重构目标

将现有 Stop 中分散、重复或相互耦合的审查、重试、计数和等待逻辑，整理为一条可配置、可追踪的流程：

1. 沿用原有 Stop 进入条件。
2. 在启动审查前检查会话和流程额度。
3. 按开启的 M 指标，跨 M 轮换处理审查组。
4. 用一份组合任务书执行一组审查，逐项取证、判定和持久化。
5. 在共享时限内统一结算，只将已确认、可交付的偏差打包交回宿主。
6. 根据 assessment 或 until_pass 决定等待到哪一步。
7. 仅在宿主实际接入反馈并开始纠偏时，扣减业务纠偏额度。
8. 明确区分“允许停止”“单项通过”和“整体验收通过”。

K 分组的目标是减少 Agent 启动及必要材料的重复读取。实际收益必须通过实验验证，不能仅凭分组数量下降宣称提速或准确性不变。

### 1.2 本次不扩大范围

- 不修改用户冻结的业务要求、条件、例外、来源权限或验收标准。
- 不扩大 Stop 自动纠偏的原有触发范围。
- “继续”等普通用户交互不因本次重构被强制转换为 Stop 纠偏入口。
- 不把检查器故障、证据不足、未审完自动转成业务缺陷。
- 不因某个 M 关闭而把其完整职责暗中转派给其他 M。
- 不重新引入之前讨论、现已撤销的“宿主完全不等待的非阻塞式 Stop”方案。
- 不要求修改已关闭的文档纠偏、独立 Skill watcher 等功能的行为。
- 不以文档交付代替代码重构、真实链路验证或性能实验。

## 2. 术语与身份边界

以下概念必须分开管理，不能共用一个计数器或一个“完成”状态。术语定义同步维护在 [CONTEXT.md](../CONTEXT.md)。

| 概念 | 定义 |
| --- | --- |
| 会话 | 宿主实际业务会话。会话总纠偏额度属于该会话，不属于某个任务或 GT 修订。 |
| 纠偏流程 | 一个初始 Stop 及其反馈引起的业务续作、后续 Stop 构成的关联链。 |
| 单次 Stop | 宿主的一次停止信号及对应的审查、结算和反馈交付。 |
| 一轮审查 | 单次 Stop 中、共享本次时间窗口的整体检查。多个 Agent 或审查组不等于多轮 Stop。 |
| 审查条目 | 某个 M 下可独立取证和判断的冻结单位，保留原要求的条件、例外及适用约束。 |
| 审查组 | 同一优先级、同一个 M 的最多 K 个待审条目，由一个审阅 Agent 处理。 |
| 组合任务书 | 程序为审查组生成的执行载体，包含成员引用、原要求及共享材料；不是新的 GT 要求。 |
| 偏差反馈包 | 单次 Stop 结算后，向宿主交付的已确认、可交付偏差集合。 |
| 业务纠偏续作 | 宿主实际接入偏差反馈，并开始处理对应任务的一次执行。 |
| 单项结果回执 | 插件确认某条结果已经通过提交校验并完成持久化的凭据。 |

身份要求：

- 会话身份、流程身份、单次 Stop 身份、组身份和条目身份必须可区分、可关联。
- 插件自己的反馈或续作消息即使采用 user role，也不能被识别为新的真实用户输入。
- 同一个 Stop 的重复回调不能创建新的流程、重新领取额度或重复交付。
- 同一会话内切换任务、项目作用域或模式，不能借用新的存储位置恢复已消耗的会话额度。
- 不同会话不能共用已用次数、等待状态或审查结果。
- 宿主重启后仍属于同一会话时，已确认的消耗与交付身份不能仅因进程重启而丢失。

## 4. 等待模式

两种模式都需要等待本次审查结果及应交付反馈，不再使用“阻塞／非阻塞”作为这两种模式的名称。

### 4.1 assessment

- 后续任务等待本次审查结算和反馈交付。
- 本次反馈交付后，解除 RC 对后续任务的等待。
- 可以交付一次有效纠偏反馈；单次阈值为任何正数时，本流程最多实际启动一次业务纠偏续作。
- 不因单次阈值大于 1 而连续追修多轮。
- 不继续等待本次修复或复验结束才放行后续任务。
- 修复引起的再次 Stop 沿用原流程身份；达到本模式一次限制时，在入口跳过自动审查。

### 4.2 until_pass

- 默认模式。
- 在等待审查和反馈交付的基础上，进一步等待关联的宿主纠偏及后续 Stop 流程结束。
- 有有效偏差且两层额度允许时，宿主可以继续纠偏，再进入 Stop。
- 反馈交付不等于已经开始纠偏；只有在有效启动准入期限内确认宿主实际开始，才转入后续修复等待。
- 每次符合额度条件的后续 Stop 拥有独立的审查与交付时间窗口。
- 宿主修复耗时不计入某一次 Stop 的 20 分钟。
- 完整通过可以提前结束流程。
- 额度耗尽、无有效偏差但未完成审查、整体检查无法继续等情况，也可以按本文规则结束等待。
- 名称 until_pass 不意味着遇到故障、额度用尽或未核验时必须无限等待，更不意味着放行时自动具有 PASS 结论。

### 4.3 等待与状态分离

宿主取消、会话关闭、RC 显式关闭或当前工作失效时，必须解除对应等待，拦截迟到结果。不能为了简化流程删除原有身份、取消和作用域检查。

解除等待不能撤回宿主已经实际开始的业务执行；已发生的有效纠偏消耗也不能因此清零。

### 4.4 反馈已交付但纠偏没有开始

启动准入的最晚期限为本次 Stop 已确定的总截止，即默认开始后第 20 分钟，不另加等待时间。最后 3 分钟的整理和交付预留也覆盖必要的接入确认。

- 宿主明确拒绝、请求已确定取消或准入已经失效，且尚未开始纠偏时，立即结束本次启动等待，不必等满总时限。
- 宿主一直排队、只返回“已接纳”，或者启动状态不明时，until_pass 最多等到本次总截止，不能无限停在“等待宿主开始”。
- 到截止仍未确认开始，必须关闭本次启动准入、解除后续任务等待，记录“反馈存在，但业务纠偏未确认开始”；审查偏差与交付／启动故障分别保留，不生成验收 PASS。
- 只有截止前已确认实际开始的有效纠偏，才进入 until_pass 的宿主修复及后续 Stop 等待。此时本次启动等待计时已经完成，不能到第 20 分钟又把正在进行的宿主修复按审查超时误杀。
- assessment 仍在反馈交付后解除后续任务等待；它的在途启动请求同样受准入期限和失效围栏约束，不得为等启动确认重新阻塞后续任务。
- 在途名额的释放、状态不明及迟到启动，按第 5.5 节处理；核对这些状态不能延长本次等待或重新打开已经结束的 Stop。

## 5. 两层业务纠偏额度

### 5.1 会话总额度

- 默认上限为 3。
- 整个会话累计计算实际开始的业务纠偏续作。
- 不在启动审查时预扣，也不按配置上限一次性扣满。
- 需求基线更新、HARD 要求变更、任务变化、重复 Stop、模式切换和配置重读，都不清零会话已用次数。
- 不能再沿用“硬性要求变更被采纳 → 新纠偏周期 → 次数清零”来实现会话额度。
- 新用户输入不会恢复会话已消耗额度。

### 5.2 流程局部额度

单次 Stop 纠偏阈值用于限制当前纠偏流程，不表示每次 Stop 都能重新领取 N 次。

- until_pass：最多实际纠偏 N 次，默认 N＝3。
- assessment：N＝0 时不纠偏；N 大于等于 1 时最多实际纠偏一次。
- 同一流程中的宿主返修、Stop 复验和内部消息继续使用已有计数。
- 新的真实用户输入之后，后续符合原进入条件的新流程可以获得新的局部额度。
- 领取新局部额度不等于强制触发审查，也不恢复会话总额度。
- 模式或配置变化不能把当前流程已用次数归零。

有效模式上限可表示为：

~~~text
until_pass：effectiveFlowLimit = N
assessment：effectiveFlowLimit = 0（N = 0），否则为 1

会话剩余 = 会话配置上限 - 会话已用次数
流程剩余 = 有效模式上限 - 当前流程已用次数
可准入会话名额 = max(0, 会话剩余 - 会话在途预留)
可准入流程名额 = max(0, 流程剩余 - 流程在途预留)
~~~

### 5.3 扣减点

以下行为不消耗业务纠偏额度：

- 审查、读取证据、保存单项结果。
- Agent 启动、审查组完成、复验或检查器内部处理。
- 发现偏差、准备反馈、发送通知或反馈排队。
- 宿主拒绝接入且未实际开始纠偏的情况。

只有宿主实际接入有效偏差反馈并开始业务纠偏续作，才同时增加会话和流程已用次数各 1。

正常续作遵循上述扣减点。若宿主违反启动准入、实际执行了本应被拦截的过期续作，按第 5.5 节单列异常并据实计账，不能用准入失效为理由隐去已经发生的自动执行。

一包反馈包含多少个 M、多少个偏差、启动多少个审阅 Agent，都不改变本次业务续作只计 1 次的规则。

扣减不能以“真的修改了文件”作为唯一依据：宿主开始处理反馈后，经检查决定无需修改，也已经发生一次业务纠偏执行。

### 5.4 可靠性约束

- 额度校验和本次有效启动的记账必须避免并发超发。
- 同一业务续作的重复事件、重复回执或宿主重放，只能扣减一次。
- 必须保留会话、流程、Stop、反馈包和业务续作的关联证据。
- 宿主请求被接受、反馈落入消息记录、业务续作真正开始，是不同阶段，不能仅凭前两个阶段断言已开始。
- 如果开始状态尚不确定，必须记录不确定，核对宿主记录；不得把相同的不确定请求自动重发成第二次纠偏。
- 在途准入可以由程序防重及约束可用名额，但不能在统计中伪装成已经实际消耗。

### 5.5 在途名额、启动失效与迟到事件

每个偏差反馈包至多关联一次逻辑启动请求及其准入标识。该标识绑定会话、流程、Stop、反馈包和最晚启动期限，不能由模型自行创建或延长。

- 在途预留是为这一个可能发生的纠偏占住可用名额，不是业务扣减；会话和流程都要考虑该预留，避免并发超发。
- 只有确认实际开始时，才以同一幂等身份把预留转为一次已用；不得先增加已用次数，再把不确定状态当成失败退款。
- 明确拒绝，或经可信取消／终止确认确实未开始且已不能再开始时，释放预留，不扣业务额度。
- 总截止到达时，先使准入失效并阻止新的启动，再取消或撤销尚未开始的排队请求。不能一边恢复名额，一边允许同一排队请求后来继续执行；也不能按审查超时盲目终止可信记录证明已在有效期内开始的执行。
- 截止时仍不清楚是否已经开始的，持久化为“待核实的在途名额”，不算已用，也不自动恢复为可用；本次等待照常释放。后续可信宿主事件或明确核对结果再结算，不能自动重发同一逻辑请求。
- 在途占用导致暂无可准入名额时，必须记录“接入状态待核实／名额在途占用”，不能谎称已消耗相同数量的会话额度。
- 宿主适配必须在真正处理偏差前校验准入仍有效。过期、已取消或被新作用域取代的请求不得开始新的自动纠偏。
- 若启动确认在截止后才到达，但可信宿主记录证明实际开始发生于准入有效期内，追溯记账一次并保留迟到确认事实；不得重复扣减、恢复旧等待或自动开启新一轮。
- 若实际开始发生在准入失效之后，应阻止执行；如果宿主已经违反准入约束、真正开始处理了反馈，则终止该插件所属的失效续作，将原预留幂等转为一次已用并单列准入违规原因。不能以“已超时”为由隐去执行，也不借此继续追修；仅创建请求或仍在排队不转为已用。此类情况必须作为宿主接入协议缺陷验收，不能因记账完成而视为链路合格。
- 无论哪种迟到情况，历史事实可更新，已结束的 Stop 控制决定不被迟到事件改成 PASS 或重新等待。
- 迟到对账绑定原会话和原流程，不把原流程消耗误记到后来新建流程的局部计数中。

宿主适配需要提供可信的实际开始观察点及过期启动拦截。能力不足时须明确补齐或公开不支持，不能用“请求返回成功”假装完成该约束。

## 6. 审查入口与额度耗尽

仍先遵守插件、项目、会话、Stop 功能及原有业务进入条件。额度检查应在新自动审查及其模型工作开始前完成。

出现任一情况，跳过本次自动审查和纠偏：

1. 会话额度已经耗尽。
2. 单次 Stop 阈值为 0。
3. 当前流程已达到本模式限制。

处理要求：

- 直接放行对应 Stop，解除本流程应结束的等待。
- 记录明确原因，例如“会话纠偏额度耗尽，本次未审查”。
- 不启动新的自动 GT 刷新、审阅 Agent 或额外实现复核来完成这次被跳过的 Stop。
- 保留历史结果和未解决问题，不删除原证据。
- 不生成验收通过结论。
- 全部审查职责被关闭时，沿用关闭状态语义，不冒充 PASS。

因在途名额占用而暂时无法准入时，记录第 5.5 节定义的独立原因；不得把预留误写成已经扣减，也不得在未决请求仍可执行时重新分配同一名额。

示例：until_pass 阈值为 2、会话额度足够。

~~~text
第一次 Stop：审查 → 交付偏差 → 宿主开始第 1 次纠偏
第二次 Stop：审查 → 交付偏差 → 宿主开始第 2 次纠偏
第三次 Stop：流程额度已用完 → 不再审查 → 记录原因并放行
~~~

第三次 Stop 不自动复验最后一次返修。因此该退出不能表述为“最终修复已通过验收”。

## 7. 审查职责与 GT 兼容

### 7.1 按 M 统一组织

- 以开启的 M 及其适用条目作为审查职责清单。
- M16 已承担真实实现覆盖审查，不再追加独立的一整轮“实现专项复核”。
- 其他 M 继续按各自定义检查，不因重构被弱化或合并。
- 共享同一份源码或需求材料，不等于共享同一个通过结论。
- M16 PASS 不能替代 M12 需求履约、M13 验收闭环或 M15 旅程通过的证据。
- 取消重复编排层时，原有确属其他开启职责的标准检查、运行证据及平台能力应归入相应职责，不能随整个旧模块一并误删。
- 可用的构建／设备验证能力不因源码审查被合并而自动消失，也不得凭能力不可用把源码判断升级为运行 PASS。

### 7.2 组合任务书

采用“一份组合任务书＋多个原始条目的独立结果”：

- GT 账本仍是唯一的要求来源。
- 原条目的编号、修订、权限、条件、例外、适用性和验证目标不变。
- 组合任务书引用原条目，并可将其原文放入同一份执行文本。
- 公共材料可以共享呈现，但必须说明对哪些条目适用，不能省略必要约束。
- 不让模型用一句摘要替换多个原要求。
- 不生成一个新的“大 GT 条目”来替换原成员。
- 不改变原有指标分母、引用关系或修订语义。
- 组身份只用于执行与追踪，不得成为条目身份或 PASS 有效性的唯一依据。

例如，组 G 包含三个 M16 条目，允许分别得到 PASS、DEVIATION、UNVERIFIED。不能只返回一个“G 通过”来代替三个判断。

## 8. M16 生产实现覆盖要求

M16 以本次任务冻结的需求及实现范围为准。每个实现单元同时满足全部必要条件，才能 PASS：

1. 真实存在：位于目标产物实际使用的代码、配置或资源中。
2. 生产可达：规定入口能够到达，没有缺失配置、错误前置条件或确定性的提前返回阻断。
3. 核心处理真实：要求的业务逻辑或平台能力确实接入，不以固定结果、成功提示或模拟数据冒充。
4. 数据流有效：真实输入参与处理，必要返回值、状态或数据被对应消费者使用。
5. 必要分支完整：原范围内必要的授权、拒绝、异常、持久化及安全处理有对应实现。
6. 证据可追溯：能够定位当前版本的文件、符号、配置及调用关系，并说明如何满足条件。

只有页面、按钮、接口声明、SDK 导入、依赖安装、TODO、成功 Toast 或测试替身，均不足以证明覆盖。关键调用不可达、必需结果被丢弃或后续处理断开，也不能 PASS。

需求明确允许预留、Mock 回退或其他替代方式时，只在该授权范围内判断，不扩张为完整生产能力。

当前 M16 的生产链路及读写关系证明要求应继续保留，并按结论分别适用：

- PASS：必须有完整的、满足该实现单元全部必要条件的证明，包括所需生产链路和读写关系；每个实现单元独立绑定证据，不能以组级 trace 代替。
- DEVIATION：必须绑定冻结要求，并给出足以确认违反必要条件的具体反证。例如实际入口必需的实现缺失、固定结果冒充处理、关键返回值被丢弃或数据流确定性中断。只要反证和范围成立，不要求再补齐一份“通过所需的完整生产链路”。
- UNVERIFIED：必须如实说明核验缺口，例如必要源码不可得、配置关系无法确定、读取或时间不足；有可用的部分证据就保留，不强制提供完整通过证明或确定偏差反证。

声称“实现缺失”仍须有足够的范围和定位依据，证明相关必要实现或入口确实缺失；一次搜索未找到、清单不完整或材料不可读，只能支持未核验。不能因为没有完整 PASS 证明而拒绝保存已有具体反证的 DEVIATION。

保存协议和结构校验不能自动证明任意代码语义，模型仍可能误判；准确性必须通过正反例及真实实验验证。

## 9. 轮换、优先级与 K 分组

### 9.1 待审集合

- 先加载并校验已有逐项结果。
- 有效、未受变更影响的 PASS 直接复用，不重新交给 Agent。
- 需要重审的失效项回到待审集合，并保留其历史记录及失效原因。
- 优先级由程序根据已保存的条目状态、调度记录和依据变更确定，不由 Agent 自报优先级，也不通过修改 GT 严重程度生成。
- 优先级按同一逻辑条目的已有评审和调度历史确定，并绑定当前 GT 修订；局部修订不会仅因版本号变化抹去派发历史。以下三类互斥，先排除可直接复用的当前有效结果。
- P0：没有可继承的有效 PASS／DEVIATION 评审历史，且从未获得组派发机会的未审条目，包括上轮因截止而尚未派发的尾部条目。
- P1：没有已形成的有效 PASS／DEVIATION 结论、但此前已经获得派发机会的未完成条目，包括失败、超时、无有效提交，以及已保存但仍未核验的 UNVERIFIED。
- P2：已有 PASS／DEVIATION 评审结论，因必要依据变化而需要重新核验，或用户明确要求重审的条目，包括修复后的偏差项及受影响的旧 PASS。其旧结论在等待复验时不得当作当前有效结果使用。
- 先处理 P0，再处理 P1，最后处理 P2，体现“先补未完成项、再复验修复项”。某优先级本轮没有可调度项时，才进入下一优先级；本轮失败后已延后的项目不通过反复重派阻塞后续优先级。
- 每个优先级内部跨 M 轮换，并沿用第 9.4 节的持久化继续位置，不能每次 Stop 重新从最小编号的 M 开始。
- “获得派发机会”以程序已记录该组派发尝试为准；即使启动失败或组内尚未读到某成员，也不能撤销这次机会、让同一个 M 原地反复重占队首。

### 9.2 分组规则

- K 默认 3，允许配置为大于等于 1 的整数。
- 一组只能包含同一优先级、同一个 M 的最多 K 个待审条目。
- 一个审阅 Agent 处理一组，按需共享必要材料。
- 不足 K 项处理剩余项；没有待审项的 M 直接跳过。
- K＝1 等价于逐条跨 M 轮换。
- K 是组大小，不是并发数，不隐含增加并发。
- 初版按已确认的轮换顺序组织工作；如未来引入并发，必须另外定义并发限制，并验证不会改变额度、截止和公平性。

~~~text
M12 前 3 项
→ M13 最多 3 项
→ M16 前 3 项
→ M12 后续 3 项
→ 继续轮换
~~~

### 9.3 组与结果解耦

- 不能因同组某项失败，丢弃其他已经有效保存的条目。
- 不能因重新分组、K 变化、移除已复用成员或改变调度顺序，直接清空其他有效 PASS。
- 单项完成、有效证据和缓存资格按条目判断，不要求整组全 PASS 才保留结果。

### 9.4 跨 Stop 的持久化继续位置

固定的 M 环顺序为 M01 → M02 → …… → M16 → M01。默认开启项形成的有效顺序为 M08 → M09 → M12 → M13 → M15 → M16，关闭、无适用条目或该优先级无待审项的 M 跳过。

同一仍适用的冻结审查范围需要保存：

1. 每个优先级的下一个 M 位置。
2. 每个 M 在该优先级内的条目队列及继续位置，以条目身份定位，不依赖易变化的数组下标或组编号。
3. 已完成项、从未派发项、本轮已派发项及失败后延后项。
4. 队列所对应的 GT 条目及修订，和最近一次调度尝试的恢复记录。

更新与恢复规则：

- 首次建立队列时，使用 M 环顺序；同 M 的成员使用冻结条目清单的稳定顺序，必要时以条目编号确定同序项先后。
- 每派发一个组，就持久化本组成员和“下一个 M”的位置；不能等整组成功后才推进 M 游标。
- 当前组中未完成的成员进入延后集合，本轮不重派；下次符合条件的 Stop 中属于 P1，而上轮从未派发的尾部成员仍属于 P0。
- 同一优先级再次开始时，从保存的下一个 M 继续，环形寻找有资格的条目，不重置为 M01 或第一个开启的 M。
- 审查截止、组失败、进程恢复、K 改变或重新分组，都不能仅凭这些调度事件清空继续位置。
- 仅因额度不足而跳过审查的 Stop 不推进游标，不能记录为已经给条目提供了审查机会。
- 开关或范围局部变化时，增量移除不再适用的条目、保留仍适用条目的相对位置；新条目加入相应队列尾部。保存的 M 被关闭时，从该位置沿环向后寻找下一有效 M，不退回环首。
- 真正切换到不同审查范围时使用独立调度状态；旧范围记录保留，不能把旧任务未审项目混入新任务。仅全局 GT 版本变化但条目及范围仍适用时，不一律重置调度。

示例：K＝3，本轮先派发 M12 的 A、B、C，A 保存成功后到达截止，M13 还未派发。应保存下一个 M 为 M13，B、C 延后；下一次先给 M13 等 P0 条目机会，再处理 B、C，而不是再次从 M12 的失败组开始。

公平性验收以“同一有限冻结范围、持续获得合规 Stop 审查机会”为前提：某个 M 持续失败或超时，不能使其他尚未获得机会的 M 无限停在其后。

## 10. 程序托管的逐项结果保存

### 10.1 权限与保存职责

审阅 Agent 负责读取、判断和结构化提交；插件程序负责校验、持久化、状态汇总及回执。

- Agent 不拥有任意写文件或指定结果保存路径的权限。
- Agent 不能通过文本自行声明新条目、成员、GT 版本或保存位置。
- 插件依据可信任务上下文绑定会话、流程、Stop、组、M 和条目。
- 模型口头声称“已保存”、输出一个 JSON 文件名或给出组级完成提示，均不计为保存成功。

### 10.2 单项提交校验

每次提交至少应校验：

1. 条目属于当前组和当前 M，且未越权。
2. 绑定的 GT 修订、审查身份和任务上下文正确。
3. 判断枚举、理由、证据字段及必要专属证明满足格式要求。
4. 引用确实来自允许读取的当前来源，不是模型杜撰的编号或位置。
5. 证据与所判条目绑定，并满足对应结论的保存门槛；M16 仅对 PASS 要求完整必要条件及实现链路证明，不能把这个门槛统一施加给 DEVIATION 或 UNVERIFIED。
6. 本次提交仍处于有效截止、作用域及取消状态内。

错误提交不计为有效结果。插件返回具体原因，原 Agent 可以在剩余审查窗口内修正提交；这不等于重新启动失败组，也不消耗业务纠偏额度。

M16 的具体保存门槛：

| 结论 | 必须具备 | 不得额外强求 |
| --- | --- | --- |
| PASS | 对应冻结实现单元全部必要条件的有效证明，以及规定的完整生产链路、读写关系和真实引用 | 不得凭结构合法就免除语义取证 |
| DEVIATION | 冻结要求及适用条件、可定位的具体反证，以及反证如何违反必要条件 | 不要求把缺失或错误实现补成完整通过链路后才能保存 |
| UNVERIFIED | 正确条目身份、明确核验缺口、已有部分证据或无法取得证据的说明 | 不要求完整通过证明，也不要求虚构确定反证 |

三类结论都接受身份、版本、结构、引用真实性及作用域等公共校验。非 PASS 附带的不完整 trace 不得被发布为完整通过证明，也不得仅因不满足 PASS trace 完整度而拒收有效偏差或如实的未核验结论；伪造引用和越权仍须拒绝。

### 10.3 顺序、重复与冲突

- 允许先保存 B、再保存 A；按条目编号关联，不按提交顺序或数组位置关联。
- 相同提交的重复请求返回相同结果或回执，不重复累计完成数。
- 同一冻结条目、依据版本和审查快照内的相互矛盾提交，不得使用“最后一次覆盖”静默替换。
- 保留原记录和冲突证据，标记冲突；冲突本身不能产生 PASS。已经有效确认的偏差不能被同版本的后到 PASS 无依据抹掉。
- 历史偏差记录不可删除，不等于它永远作为当前确定偏差。必要依据变化后，应按第 11.3 节转为历史待复验。
- 新版本的有效复验结果可以更新当前有效结论：例如修复后证据完整的 PASS 可以关闭当前缺口，同时保留原 DEVIATION 及其与复验结果的关联。这不是同一快照内的冲突覆盖。
- 需要更正原错误裁决时，同样必须有新的有效核验、支持更正的证据和可追踪记录，不能只凭结果到达顺序改写历史。

### 10.4 完成与恢复

- 完成一项即校验并持久化一项，成功后返回插件生成的回执。
- 只有程序确认有效保存的条目才进入完成集合。
- 保存中断或只写了一部分不能当成完成。
- 单项提交成功后，Agent 可以继续组内下一项，不因第一项保存成功就结束整个组。
- 组结束与单项提交是不同事件。
- 组故障、停止或取消时，从有效单项记录恢复结果，不能只依赖 Agent 最后一条总结。
- 迟到结果不得重新打开已经结束的 Stop，也不能覆盖新一轮或新版本结果。

## 11. 逐项结论有效性、PASS 复用与偏差更新

### 11.1 复用原则

PASS 表示指定条目的必要条件已有有效证据支持，不等于“没有搜到问题”。

- 已有效通过的条目默认复用。
- 用户明确要求重审时可以重审指定范围。
- 相关需求、生产代码或必要配置改变时，仅让受影响的 PASS 失效。
- 在下一次原本就会触发、且额度允许的 Stop 中处理这些失效项，不额外强制触发新流程。
- 复用仍须满足原条目、适用范围、GT 修订和证据有效性。
- 日志增加、进入新一轮、重新分组、模式变化等调度变化，不能成为清空全部 PASS 的理由。

### 11.2 影响范围与证明范围

- 失效要有可解释的依据，例如要求修订变化、必要文件或依赖变化、原证据不再有效。
- 同一个源码文件可能影响多个条目；不得把“仅受影响项失效”简化为只重审一个任意编号。
- 源码证明、实际运行证明和过程执行证明具有不同适用范围。
- 同一版本的有效源码证明可以复用；旧任务中的流程执行或运行记录不能冒充新任务尚未发生的执行事实。
- 仅因 GT 总版本或组编号变化，不能不加区分地丢掉所有条目结果。
- 不能通过强行沿用无法验证的旧 PASS，掩盖依赖追踪不完整的问题。

### 11.3 历史偏差与当前有效结论

逐项评审记录作为追加的历史事实保存；面向当前审查和反馈的有效结论另外维护。记录曾经是有效 DEVIATION，不代表它对后来所有版本一直成立。

| 情况 | 历史记录 | 当前有效视图及反馈处理 |
| --- | --- | --- |
| 原要求和相关证据仍有效，未出现影响反证的变更 | 保留原 DEVIATION | 可以继续作为当前确认偏差，但仍须满足原进入条件、交付有效性和额度约束 |
| 相关需求、代码或必要配置已变更，尚未复验 | 保留原 DEVIATION 和失效原因 | 标为历史待复验／当前未核验；不把旧偏差直接作为当前确定偏差反馈 |
| 新版本有效复验为 PASS | 原 DEVIATION 保留并关联新结果 | 当前视图更新为通过／缺口已复验关闭，不再发送原偏差 |
| 新版本有效复验仍为 DEVIATION | 保留前后两次记录 | 使用本次当前反证及理由作为有效偏差，关联原问题 |
| 新版本复验为 UNVERIFIED 或被跳过 | 原 DEVIATION 不删除 | 当前状态仍未核验／待复验，不声称已修复，也不继续发送失效的旧反证 |
| 原要求撤回或条目退出当前范围 | 历史记录保留并说明范围变化 | 不再作为当前应修偏差；“退出范围”不等于“实现修复通过” |

- 对偏差的失效检查同样按实际必要依赖进行，不能因不相关日志变化把所有偏差都作废。
- 标为待复验只改变当前有效视图，不恢复会话或流程额度，也不强制启动新的审查。
- 有额度且满足原进入条件时，受变更影响的旧偏差进入 P2 复验队列；本轮来不及复验则如实保持待复验。
- 反馈组包前，以及宿主实际接入前，均需以程序检查现有依据和作用域是否仍有效；不能把排队期间已经失效的偏差继续作为有效启动理由。
- 如果整包偏差都已经失效，关闭本次启动准入，不触发返修、不扣额度，保留“历史存在偏差、当前尚未复验”的状态。
- 上述交付有效性检查不得在反馈预留阶段重新启动 Agent 做一轮语义审查；发现依据变化就降为待复验，后续按正常规则处理。

### 11.4 偏差更新示意

~~~mermaid
flowchart TD
    A["当前有效 DEVIATION"] --> B{"必要要求或证据依据改变？"}
    B -->|"未改变且仍有效"| C["保留当前偏差<br/>按原进入条件和额度决定是否反馈"]
    B -->|"改变"| D["原偏差转为历史待复验<br/>当前未核验，不发送旧反证"]
    D -->|"条目仍适用"| E{"新的有效复验结果"}
    E -->|"PASS"| F["当前缺口复验关闭<br/>历史偏差及关联证据保留"]
    E -->|"DEVIATION"| G["以本次当前反证更新有效偏差<br/>历史前后记录都保留"]
    E -->|"UNVERIFIED 或尚未复验"| H["保持待复验<br/>不声称修复，也不发送失效反证"]
    D -->|"要求撤回或退出范围"| I["保留历史，不作为当前应修偏差<br/>不生成实现修复 PASS"]
~~~

## 12. 总时限与反馈预留

### 12.1 时间模型

默认配置：

~~~text
总时限 T = 20 分钟
反馈预留 R = 3 分钟
最晚审查截止 = 本次审查启动时刻 + T - R = 第 17 分钟
最终结算／交付截止 = 本次审查启动时刻 + T = 第 20 分钟
~~~

- T、R 都允许在项目配置文件中设置。
- R 是 T 的一部分，不额外延长总时限。
- 必须校验 T > 0 且 0 < R < T；非法值不能被静默修正为另一套时限。
- 基线准备、必要分类、材料准备、逐项审查、程序校验、汇总和反馈交付，共享单次 Stop 的总窗口。
- 不再将基线、Stop、实现审阅和设备预算简单相加为总时间。
- 各角色或工具内部限制只能更早结束相应工作，不能延长外层共同截止。
- 宿主取消或更短的硬限制可提前结束工作，记录实际原因，不把提前结束伪装成通过。

### 12.2 审查截止

- 最晚到 T-R 停止审查，包括正在处理的组。
- 不能只停止派发新组，却等待当前组全部做完后才整理。
- 不在反馈预留阶段启动新的 Agent 或业务证据审查。
- 停止时保留已有效保存的项目，其余条目记录为未核验。
- 必须预先持久化单项结果，使结算不依赖 Agent 最后成功退出。
- 分组中一项耗尽剩余时间时，不能丢失已完成兄弟项。

### 12.3 统一批量交付

- 发现第一个偏差不立即中止本轮。
- 继续检查，直到提前完成、审查截止或整体无法继续。
- 随后统一归集有效结果，优先整理和交付已确认偏差。
- “优先交付偏差”不表示必须等所有条目完成，也不表示每发现一项就触发一次宿主返修。
- 提前审完立即进入结算，不必等到第 17 或第 20 分钟。
- 最晚在总时限结束时完成本次收尾并解除应结束的等待，不得无限等待清理或通知。
- 未确认开始的交付故障不能被记为已经消耗业务纠偏额度；保留反馈及故障证据。
- 宿主启动确认同样受本次总截止约束；until_pass 的未开始退出、在途名额及迟到事件按第 4.4、5.5 节处理，不能在 20 分钟之外另加一段隐含接入等待。

### 12.4 与 until_pass 的关系

20 分钟约束一次 Stop 的审查与交付，不是整个纠偏链的总时长。

宿主修复后再次进入 Stop：

- 沿用原流程已用次数。
- 先检查会话及流程额度。
- 额度不足则跳过，不再启动新的 20 分钟审查。
- 额度足够才启动本次独立时间窗口。
- 不能将第一次 Stop 的审查截止直接继承为所有后续复验的截止。

## 13. 故障隔离与终审结果

### 13.1 单个组失败

例如一组有 A、B、C：A 已有效保存，处理 B 时 Agent 崩溃。

- 保留 A。
- B、C 中尚无有效保存结果的项目记为未核验。
- 本轮不重试该失败组，也不通过换组编号立即重派相同失败条目。
- 时间仍允许时，继续审查其他 M 的组。
- 后续符合入口及额度要求的 Stop，再按未完成项优先规则接续。
- 审查故障本身不扣业务纠偏额度。

### 13.2 整次审查无法继续

- 保留已有效保存的条目。
- 有已确认、可交付偏差时，按剩余交付窗口整理并交付；宿主实际开始纠偏才扣一次额度。
- 没有有效偏差时，放行，不要求宿主为检查器故障返修，不扣额度。
- 不因为检查器失败就重新从第一项启动整轮审查。
- 不将旧的固定基础设施重试两次机制隐藏保留为第二条 Stop 主流程。

### 13.3 已审部分全部通过

已经完成的条目都 PASS，但整体检查没有完成时：

- 保留单项 PASS。
- 整体仍记录未完整审查或未核验。
- 不因尚未完成审查就要求宿主返修。
- 没有有效偏差就放行，不扣业务纠偏额度。
- 不写“全部通过”“完整验收成功”等超出证据范围的结论。

## 14. 反馈内容与状态分离

### 14.1 业务纠偏反馈包

- 一个 Stop 将已确认、可交付的偏差统一打成一包。
- 反馈要包含对应条目、原要求定位、偏差说明、当前证据及可追踪位置。
- 不用 PASS 清单或大量未核验理由充当返修指令。
- 历史待复验或依据已失效的 DEVIATION 可以出现在历史报告中，但不得混入当前有效偏差包；报告必须明确它的历史版本和待复验状态。
- 缺证据、未审完或检查器故障，不能单独生成业务修复要求。
- 未核验范围、故障、跳过原因可如实出现在状态记录和完整报告中，但必须与业务偏差分开。
- 宿主仍按原用户要求、已有约束和权限判断如何处理；反馈不是新的用户授权。

### 14.2 至少分开记录的事实

1. 控制决定：放行、继续等待或存在一次业务续作。
2. 审查结果：完整通过、存在偏差、未核验、跳过或职责关闭。
3. 反馈交付及准入：待交付、已交付、被拒绝、排队、准入失效或尚不确定，关联期限和请求身份。
4. 业务执行：可信的实际开始／结束事实及其观察时间，迟到确认与迟到实际启动分开记录。
5. 额度：会话与流程各自上限、已用、在途预留和本次变动，预留不得混入已用。
6. 时间：启动、审查截止、交付截止、实际终止及原因。
7. 进度：各 M 的条目数、完成数、复用数、当前偏差数和未核验数，以及优先级和跨 Stop 调度游标。
8. 历史与当前视图：历史偏差记录、当前有效结果、依据变更与待复验原因、关闭或退出范围的关联证据。

不得把这些事实压成一个容易产生歧义的“成功”字段。

### 15.2 校验与快照

- 两个业务次数配置必须允许 0，并拒绝负数或非整数。
- K 必须为大于等于 1 的整数。
- 时间配置拒绝不合法的类型和预留大于等于总时限等冲突。
- M 开关必须为布尔值，未写的指标继承已确认默认值。
- 单次审查使用启动时配置快照。
- 本次期间修改模式、K、时限等配置，不能在中途改变本次审查；修改从下一次 Stop 生效。
- 配置重读不重置会话或流程已用次数。
- 显式取消和 RC 关闭仍需及时解除等待、阻止旧工作继续提交；这不是普通参数热更新。

### 15.3 兼容注意事项

- 原 maxCorrectionsPerEpoch 名称及其“新周期清零”语义不能直接继续充当会话总额度。
- 原 waitTimeoutMs 或旧等待链计时不能暗中把“每次 Stop 独立 20 分钟”变回整个链共用一个审查窗口。
- 原 implementationCorrection 开关不能变成隐蔽的第二套 M16 审阅入口。
- 新字段、旧字段优先级及迁移提示必须明确；不允许配置看似启用新规则，实际静默回退旧流程。
- 对没有本轮专门重定义的功能，保留现有开关及职责，不以重构名义扩大检查范围。

    P -->|"只跟踪，不重新阻塞"| W
    Q --> W
    W --> X{"准入有效且截止前<br/>已确认宿主实际开始？"}

## 18. 验收场景

验收同时覆盖程序机制和宿主实际链路，不能只以测试替身通过宣称生产流程已接通。

### 18.1 额度与模式

- AC-01：默认值为 until_pass、会话 3、流程 3、20 分钟、预留 3 分钟、K＝3。
- AC-02：until_pass 阈值为 2，两次有效纠偏后第三次 Stop 不启动审查，不生成 PASS。
- AC-03：until_pass 阈值为 3，实际纠偏两次后，仍有额度的第三次审查完整通过，提前结束，会话仅扣两次。
- AC-04：assessment 阈值为 3，本流程最多一次有效纠偏，交付后解除后续任务等待。
- AC-05：任一模式局部阈值为 0，入口跳过审查，记录原因。
- AC-06：会话额度用完，新用户输入或新任务不能恢复；后续自动 Stop 跳过审查。
- AC-07：新真实用户输入可开启符合原条件的新局部流程，插件反馈消息不能领取新额度。
- AC-08：基线／HARD 要求变化、重复 Stop、模式切换、配置重读均不清零已用次数。
- AC-09：只做审查、复验、通知或排队不扣业务额度；实际开始一次才扣一次。
- AC-10：重复宿主事件或回执只扣一次；被拒绝且未开始的续作不扣。
- AC-11：单包有多个 M、多个偏差时，宿主一次续作只计一次。
- AC-12：会话重启恢复仍保留已确认消耗，两个会话互不串账。

### 18.2 时间与故障

- AC-13：默认第 17 分钟停止当前组，不等待整组完成，在原 20 分钟内结算交付。
- AC-14：提前完成立即交付，不等满窗口。
- AC-15：所有角色及准备工作共享总截止，没有角色时间相加或隐蔽延长。
- AC-16：until_pass 中宿主修复不占单次审查时间；额度足够的下次 Stop 有新窗口，已耗尽则不启动。
- AC-17：只有检查器故障、没有有效偏差时放行，不返修、不扣额度。
- AC-18：已审项目全部 PASS 但整体未完成，记录未核验，不声称整体验收通过。
- AC-19：组内首项保存后 Agent 崩溃，该项保留，其余未核验，继续其他 M；本轮不重派失败项。
- AC-20：取消、关闭或新作用域使旧工作失效后，迟到结果不恢复等待，不产生迟到 PASS 或错误派发。

### 18.3 分组、GT 与结果协议

- AC-21：K＝3 按同 M、同优先级分组并跨 M 轮换；不足 K 和空 M 正确处理。
- AC-22：K＝1 等价于逐条跨 M 轮换，不能将 K 当并发数。
- AC-23：有未完成项和修复待验项时，先补未完成项。
- AC-24：组合任务书不改变 GT 条目、修订、条件、例外、来源、指标分母。
- AC-25：Agent 无任意结果写入路径；提交错条目、错版本、越权或错误格式时被拒绝。
- AC-26：B 先于 A 提交仍正确归档；重复提交不重复计完成数。
- AC-27：同一条目、依据版本和审查快照内的冲突结果不静默覆盖、不生成 PASS；已有确认偏差不被同快照后到的 PASS 无依据抹掉，跨版本有效复验按 AC-54 更新当前视图。
- AC-28：只有有效保存回执计为完成；模型口头宣称保存成功无效。
- AC-29：一项保存成功后 Agent 可以继续组内下一项；部分完成不依赖组最终成功。
- AC-30：K、组身份、日志或调度变化不会清空其他有效 PASS。
- AC-31：相关要求或必要代码依赖变化，仅使受影响项失效，记录原因；未影响项复用。
- AC-32：M16 每个实现单元仍具备独立证明，不能用一个组 PASS 覆盖未审成员。
- AC-33：M16 PASS 不代替 M12 运行验收或 M13／M15 闭环结论。
- AC-34：指标关闭不生成该指标审查或把其完整职责转给其他 M；全部职责关闭不冒充 PASS。
- AC-35：不存在第二套独立实现审阅或自动回退旧链路导致的重复审查。
- AC-36：运行中修改配置，本次保持快照，下一 Stop 应用新配置，计数不重置。

### 18.4 启动退出、调度恢复与结论更新补充

- AC-37：宿主明确拒绝且未开始时，until_pass 立即释放等待；不扣额度，确认已不能启动后释放在途预留，保留偏差和拒绝原因。
- AC-38：宿主一直排队，到本次第 20 分钟仍未确认开始时，关闭准入并释放等待，不追加接入等待、不生成 PASS。
- AC-39：截止时启动状态不明，在途名额保留待核实、不算已用，不自动恢复或重发；该核对不拖住本次已结束的等待。
- AC-40：可信取消确认未开始且不能迟到启动时，预留可释放；重复取消／拒绝事件不重复恢复名额。
- AC-41：准入失效后到达的排队启动被宿主适配拦截，不实际进入业务纠偏，不重新打开旧 Stop。
- AC-42：截止前已实际开始、但确认迟到的情况，按可信历史事实幂等记账一次；已释放等待不重开，不再派发第二次。
- AC-43：宿主违反准入期限而真正开始处理反馈时，被识别为协议缺陷并停止该失效续作；原预留只转为一次已用并单列异常，实际发生记录不得抹去，不借此继续追修。仅创建或排队不扣，记账完成也不能把协议缺陷判为合格。
- AC-44：截止前已确认开始的有效纠偏，until_pass 继续等待修复及后续 Stop；原第 20 分钟审查计时不能误杀已开始的修复。
- AC-45：M16 PASS 缺少必要完整证明时被拒绝；DEVIATION 有冻结要求和具体反证、但没有完整生产链路时，仍可有效保存。
- AC-46：以实现缺失为反证时，范围不完整或仅搜索未找到不能升级为确定偏差；应保存 UNVERIFIED 及核验缺口。
- AC-47：M16 UNVERIFIED 可在没有完整通过证明或确定反证时保存，但条目身份、结构、范围和真实引用的公共校验仍然生效。
- AC-48：M12 的组跨截止未完成、M13 尚未派发时，保存下一个 M 为 M13；下一 Stop 从 M13 等 P0 项继续，不再次先跑 M12 失败组。
- AC-49：跨 Stop 时 P0 未获得机会的条目优先于 P1 失败未完成项；本轮失败项不得换组编号反复重派。
- AC-50：P1 内某个 M 持续超时，也在派发时推进并保存 M 游标，下一次同优先级从后续 M 继续，防止固定环首饥饿。
- AC-51：K 调整、局部 GT 变化或游标 M 被关闭时，增量恢复条目位置并沿环向后寻找，不一律清空游标或有效结果。
- AC-52：额度不足而跳过 Stop 不推进调度；不同审查范围使用独立队列，旧任务条目不能串入新任务。
- AC-53：历史偏差的必要代码或配置改变但未复验时，转为历史待复验，不作为当前确定偏差交付；整包均失效时取消启动准入、不扣额度。
- AC-54：新版本经有效复验 PASS，允许当前缺口关闭，同时保留原偏差历史；不能因“旧偏差不可覆盖”而永远拒绝关闭。
- AC-55：新版本复验未核验、被跳过或额度耗尽时，旧偏差不丢失，但不声称已修复，也不继续发送失效的旧反证。
- AC-56：必要依据未变且旧反证仍有效时，可在原规则与额度允许下作为当前偏差；同快照冲突提交与新版本有效复验必须区别处理。

### 18.5 真实端到端与性能实验

至少进行一次隔离 TodoList Python 应用开发和 Stop 纠偏实验，并覆盖可控的真实偏差。

应核对：

- 冻结需求、生产源码和验收材料的实际来源及版本。
- 真实调用链、Agent 启动次数、每组成员、单项回执与恢复记录。
- 宿主实际收到的反馈与实际开始纠偏的次数。
- 等待模式是否按定义释放。
- 跳过、故障或超时是否误标 PASS。
- 是否只复核需要重审的条目，是否继续遗漏尾部 M。
- 17／20 分钟边界及取消后是否存在迟到写入或反馈。
- K＝1 与 K＝3 在同等模型、冻结要求和时间边界下的对照。

至少报告 Agent 启动数、有效完成条目数、读取量、模型用量、耗时、复用数、偏差检出情况和未核验范围。

不能用减少检查分母、降低 M16 证据要求、修改业务测试或把未核验改成通过来制造提速。实验数据外发及外部模型调用仍遵循已有明确授权范围，本文不扩大授权。

## 19. 交付要求

1. 一套明确的新 Stop 主流程，避免新旧两套编排并行或相互回退。
2. 两层额度及真实启动事件的持久化、幂等和审计。
3. K 分组执行与逐项结构化保存、故障恢复。
4. 统一时间控制及反馈预留。
5. 指标职责、GT、结果身份和 PASS 复用的兼容。
6. 配置 Schema、默认值、示例和迁移说明一致。
7. 与宿主的等待、续作、取消和关闭链路实际接通。
8. 对现有共享核心和宿主适配运行必要回归，明确真实验证覆盖哪些宿主，不能将一个宿主的结果外推为全部支持。
9. 真实实验、轨迹分析和性能结论，保留失败与未核验事实。
10. 文档和报告使用本文术语，避免再混用 Stop、审查轮、组、反馈次数与业务续作次数。

## 20. 实现前需明确的兼容边界

本节区分已确认需求与尚未选定的迁移方案，不将建议伪装成已确认行为。它们不改变前文默认值及核心规则。

### 20.1 旧字段兼容策略

尚未确认是保留旧字段映射，还是要求一次性迁移到新字段。

建议：旧字段仅在配置入口做显式映射和弃用提示，规范化后只运行新核心；字段冲突明确报错，不保留旧调度器作为回退。

### 20.2 已有活跃会话的会话额度初始化

历史代码主要按任务／纠偏周期计数，不能直接把某个任务计数当成整个会话已消耗次数。

建议：定义可审计的升级边界，已有活跃流程不在中途被静默转换；优先从可追溯的真实续作记录核对。无法可靠重建时明确迁移状态，不凭空生成准确历史，也不未经确认把已有会话视为全新会话。

### 20.3 流程已经结束后修改配置

已确认的是“本次快照、下一次 Stop 生效、已用次数不清零”。

建议补充：已经因次数限制或正常收尾结束的流程，不仅因为配置读取或模式切换就重新成为新流程；需要原有规则下的新用户输入与流程身份。模式和上限变更对仍在进行的流程怎样应用，应在实现说明和对应验收案例中明确，不能通过重置计数解决。
