# until_pass：运行结束后的多会话调度

## 范围与实施步骤

只修改 runtime-corrector-toy。MatrixAssistant 与其内置 OpenClaw 的文件只读；RC 页面在浏览器打开，不注入 MA 原生前端。

1. 验证公开 reply_dispatch 接管返回及 agent.wait 终态契约。
2. 实现按 agentId、sessionKey、sessionId、项目、激活任务与作用域版本隔离的持久化调度器。
3. until_pass 移除原轮 revise 与跨运行挂起请求；宿主终态确认后才启动独立审查。
4. 接入多会话 RC 页面、带身份与待办版本校验的查询/编辑/删除接口。
5. 验证纠偏优先、有限并发、故障退出、未知启动结果恢复和多会话隔离。
6. 完成定向回归、全量回归、安装包构建及文档核对。

## 行为契约

业务运行正常结束并显示回复。RC 通过 agent.wait 等待宿主终态，不能把 agent_end 当作回复交付与运行收尾均已完成。结束钩子只登记候选，不等待模型审查、不请求原轮 revise。

需要审查时暂存后续用户输入。reply_dispatch 将输入交给 RC 后及时返回一条收件说明，审查和修复不会占据该输入请求。宿主已显示的收件说明不回写；待办编辑与删除只作用于 RC 状态。

有当前有效、且额度与宿主准入允许的纠偏反馈时，通过现有可信启动协议发起新运行。修复正常结束后重新进入本流程。无需继续时领取队首用户待办；没有待办则空闲。多个输入按加入顺序保存，不静默覆盖。每个会话最多保留 100 个待办，单条文本最多 200000 字符。额度耗尽、基础设施故障、取消和超时保留真实未通过或未验证状态；放行不等于 PASS。

每个会话有自己的当前运行、审查、纠偏请求和待办队列。跨会话审查使用共享 FIFO 并发池，默认上限 3，可用宿主插件 config.stopReviewConcurrency（1–32）配置；等待资源计入本轮审查窗口。业务执行并发仍由宿主管理。共享项目文件的证据在启动修复前重新核对。

调度意图在宿主调用前持久化；响应未知时不重投。重启先通过可信宿主终态核对在途运行。无法确认的请求显示需要核对，保留待办，不因浏览器刷新自动再发。关闭浏览器不停止后台任务。

## 控制页与接口

“添加后续任务”上方显示完整目标会话与项目，目标始终是控制页自身的选择。列表只显示 RC 已登记会话，不自动导入宿主所有历史会话。新增任务返回带目标和任务 ID 的回执；每个会话持久化最近 50 个任务的历史状态，长正文显示截短标志。待办被领取后仍可查看其提交、未知回执、实际开始、结束或移除状态；执行结束与 Stop 验收结果分别显示。未知提交结果不标成已执行，不重发。历史跨 Gateway 重载保留。

最近一次审查范围显示基线版本、全量/选中/已审定对象数及按指标展开的对象，空范围和仅扫描偏差有明确原因。历史轮次只作历史展示，不自动修改旧验收结果。

浏览器打开当前 Gateway 的 `/plugins/runtime-corrector/`，通过宿主原生浏览器客户端认证。后台查询与待办提交在第三方插件无权使用直接 Gateway 接口时，使用公开 Gateway CLI 客户端及宿主既有认证；仅在明确的派发前权限拒绝时切换连接，响应未知绝不换连接重投。只列出本 RC 状态目录已登记的会话，按页查询摘要，选中会话后加载详情。MA 当前窗口选择不会自动同步，页面始终显示会话与项目。

审查期间第一行显示“任务完成情况审查中。”，等待并发资源时附带原因。第二行为当前选中的用户待办，可编辑、删除；无待办时为空。多个待办可逐个选择；添加任务的收件 ID 在响应未知时复用。

新 RPC：`runtime-corrector.dispatch.list/get/add/edit/remove`。读方法需要 operator.read，写方法需要 operator.write（或 operator.admin）。操作绑定会话记录 ID、agentId、sessionKey、sessionId、scopeFingerprint；待办编辑/删除还校验任务 ID 与 revision。界面切换后忽略旧响应。原有监督执行控制页模块不整体恢复注册。

## 验收

- 终态前不审查，不改最终回复，不延长已结束的运行。
- 无待办时仍能连续审查、纠偏；最终进入空闲。
- A 审查不阻塞 B；多会话公平排队，队列等待受截止限制。
- 修复优先，用户任务保留；编辑后执行最新内容，删除后不会执行。
- 审查结算与编辑/删除竞态只产生一个确定结果。
- 重复结束事件、迟到回执、会话 reset 和项目切换不串扰。
- 已持久化的未知派发不重发，恢复保留待办。
- assessment 及其他宿主既有行为回归。

真实模型与完整 Electron 桌面验收单独记录，不能用无模型契约测试替代。

## 多状态补充验收

`test/post-run-scenarios.test.mjs` 对真实调度器执行完整状态转换，检查后续运行的内容、顺序与次数；`test/stop-host-integration.test.mjs` 再从生产钩子、纠偏准入和用户运行入口验证放行。审查结果与宿主终态在测试中受控，避免把模型随机性当作调度正确性的依据。

- 正常结束、等待宿主终态、等待审查资源、审查、等待纠偏启动、纠偏执行、取消收尾期间，都检查待办不会提前执行。取消时等待实际纠偏运行的终态，不能把中止回执或已结束的父运行当作证明；终态未知时继续保留待办，重启后继续核对同一运行。
- PASS、不需要 Stop、关闭 Stop、关闭全部指标、无有效反馈、额度耗尽、不支持纠偏启动、准入拒绝、审查失败、审查取消、审查超时和业务运行失败，检查放行后只执行一个队首任务；该任务结束后才执行下一条。生产入口在额度为零、尚未开始审查时记录 UNVERIFIED，不伪造 DEVIATION 或 PASS。
- 连续两轮纠偏时保持用户待办；没有用户待办也继续纠偏，PASS 后空闲。删除全部待办不会取消纠偏，纠偏期间新加入的任务仍能正常接续。
- 编辑使用最新文本，删除不再执行，重复收件不恢复已删除任务，开始执行后编辑或删除会冲突；编辑/删除与放行同时发生时只有一个有效结果。
- 24 个会话同时运行，审查并发上限为 3，各自的两条用户任务严格按加入顺序执行；同一项目的不同会话不会串任务。
- 重启先核对未确认的旧运行，不重发已经提交的任务。会话重置和项目重新激活保留独立的历史记录，关闭会话只能查看。
- 浏览器检查两行列表从审查、等待纠偏、纠偏、第一条用户任务、第二条用户任务到空闲的变化，同时验证 103 个会话的分页、跨页搜索、直达链接、过期编辑、保存响应迟到时的新草稿保留、关闭会话只读及收件回执丢失后的幂等重试。

补充测试发现并修复了七个问题：旧启动超时处理误伤新纠偏窗口；重置期间的慢校验仍派发待办；旧纠偏回调释放新用户运行；迟到启动事件把审查退回纠偏执行；慢保存响应清除切换前的新草稿；RC 故障或纠偏中止回执在宿主终态前提前放行；Windows 临时占用导致私有状态原子替换失败。这些场景均有回归断言。已确认的终态可以用于后续故障放行，不因重新查询失败而丢失这份证明。
