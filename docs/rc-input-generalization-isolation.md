# RC 输入泛化融合隔离实验（2026-10-11）

基线为当前分支 `codex/openclaw-2026.7.1-2` 的 `b0138f5`；候选在 `codex/rc-input-generalization`。只改 RC，保留现有监督执行、交互、上下文恢复、Stop 分类、预算、取消及 HARD 逻辑。最终预定门槛通过，采用 F2 输入融合措施。收益限于完整输入、合法来源修复与准确需求边界；本轮未观察回归，业务完成度和 Stop 通过率没有提高。

## 改动范围

- 需求提取和合并获得原始 transcript snapshot。原 4,000 字展示保留为预览，完整真实用户消息写入 Reviewer 私有来源文件并带原 catalog 身份、字数及哈希；按需读取，既不解析文本中的 JSON 为宿主角色，也不以内容相同把材料提升成用户来源。
- 模型选择来源与行范围，程序从原始文本获取引用。未知身份、错位行范围和错误来源标注在入库前处理，避免丢掉部分要求后冻结成完整需求。
- 原来的一次修复机会与同一会话/截止不变。来源修复只返回坏索引的 source，程序保留完整操作、文本、类别和 HARD。错误 USER_EXPLICIT 只能在原已被拒绝、前后同一真实 MATERIAL 时纠正为 MATERIAL_DERIVED；也可引用实际采纳附件的用户消息，并保留材料为支持依据。
- 提醒 Reviewer：生产代码清单用于导航，清单未列出文件不能证明该文件不存在。没有加入 App 专属判断、额外总结模型或新任务调度器。

## 真实流程与条件

使用真实 OpenClaw Main/Reviewer，模型 `zhipu-rc/glm-5.3-flash`。每个案例复制相同原始应用起点，输入原需求，建立全新账本，再让宿主实际工作；对第一轮真实 transcript 进行新 Stop，最后同一宿主会话续改。未复制旧纠偏证据或旧审查进度。并非从空仓重写，也不是冻结旧 Stop 重放；普通宿主自动纠偏在隔离探针中被屏蔽，探针调用正式需求入口、正式工具契约和 Stop 方法，不代表整个监督生命周期测试。

Todo/花店分别直接输入 7,275/9,955 字原文；厨房为真实用户明确采纳附件，附件原文 8,985 字。A/F 输入形式、起点、测试适配器和时限相同。Reviewer 独立上限 20 分钟，原需求提取阶段 18 分钟、共享 29 分钟预算仍约束有效截止；隔离 Main 调用窗口另设，不改变宿主全局配置。

预定门槛为完整来源身份/字节、无权威来源丢弃后成功冻结、具体尾部需求恢复、三个 App 保留 A 原通过场景、原宿主与 RC 控制契约保持不变。

## 已观察的输入收益

A Todo 明确把截断后的 CSV/验收/交付要求记为不可见；A 花店将 R32–R50 记为只能推测；A 厨房丢弃一项 NON_USER_AUTHORITY 后仍冻结。第一版候选厨房因过严的修复比对失败，已否决；F2 改成来源选择回填，不删除需求。

F2 Todo 的 CSV 编码/转义/空表头、损坏数据保护、T01–T22/真实 CLI、README 和最终交付均在新账本中具体恢复。F2 花店 R32–R50 的具体功能和交付合同恢复；R32 的一条归还前置条件没有显式重述，不能宣称无遗漏。厨房真实 source-only 修复保留全部 89 操作与 87 HARD，84 个错误索引通过实际采纳用户来源修正，修复报告内原附件支持位置保留，并非内容/哈希赋权。后续普通合并输出省略这些 supportingRefs，最终账本只保留真实采纳用户的 primary；不能声称逐项材料支持位置已稳定保存。另一提取路普通 JSON 修复后来源仍无效被拒绝，沿用原 panel 容错，由单个完整有效报告及合并完成入库。厨房 R41–R50 的多数尾部需求 A 已保留，不能称整段新恢复；实际恢复的是 A 丢弃的应用总体目标（F2 goals-56b5eb656a8f1827）。
