一句话理解
它不是替你做决定的“自动修理工”，而是每次写入后的独立质检回路。

客户真正需要的不是一个声称永不犯错的 Agent，而是一套能及时发现偏移、解释为什么、保留检查记录，并把修改权留在正确角色手中的机制。

Part 01 · Why drift happens

为什么运行过程中仍然需要纠偏

生成不是一次性动作，而是一串不断改变上下文的写入。越长的链路，越需要在每个关键落点重新确认“我们写下的，仍然是最初答应交付的吗？”

01

产物为什么会在生成过程中逐步偏离

目标在任务开始时通常很清楚，但每一次补充、重写和跨文件传递都会引入新的局部上下文。Agent 可能为了完成当前段落而弱化早先约束，也可能把一个合理推断逐渐写成“已确认事实”。这种偏移通常不是突然发生，而是像航线误差一样逐轮累积。

常见表现包括：遗漏必须保留的能力、把“可选”写成“必需”、新增没有上游依据的范围，或修改一个文件后忘记同步另一个交付物。单看当前段落往往都说得通，放回完整链路才会显出问题。

客户关心的答案：Runtime Corrector 关注的不是 Agent 有没有完成动作，而是关键约束在连续生成中有没有被保真地传下去。

02

“已经生成成功”为什么不等于“内容正确”

文件写入成功，只能证明路径存在、写入动作完成；Markdown 能渲染、JSON 能解析，也只能证明形式合法。业务正确性还包括：必需信息是否齐全、范围有没有被改变、上下游决策是否一致、关键标识是否可追溯。

  • 写入成功
    文件落盘，没有 I/O 错误。
  • 结构正确
    格式、字段与 Schema 合法。
  • 语义正确
    内容满足本阶段业务标准。
  • 链路正确
    没有遗漏或扭曲上游事实。

Runtime Corrector 把“成功”的判断从一个写入事件，提升为可配置的内容与关系检查。

03

为什么不能只依赖生成者自我检查

生成者自检当然有价值，但它仍然带着刚才做决定时的同一组假设。若原推理已经误解了“离线运行”，自检很可能继续沿用这个误解；若会话中的文件副本已经过期，自检甚至可能审查一个已经不在磁盘上的版本。

Runtime Corrector 在写入完成后，重新从磁盘读取当前文件，并在需要语义判断时使用隔离会话。它不是假设隔离审查一定正确，而是通过“独立上下文 + 具体证据”降低原有推理自我强化的风险。

信任来源：不是换一个更自信的结论，而是换一个检查视角，并要求结论可以被用户复核。

04

Runtime Corrector 是什么

它是一个面向产物的写后诊断与反馈插件。Claude Code 的 Write 或 Edit 命中项目已启用的受保护产物后，插件编译项目策略、读取当前快照、执行确定性规则，并在条件允许时发起隔离语义审查。

最终返回的是状态、诊断、证据和可选候选 Diff。插件不负责替业务方选择方案，不擅自补充尚未决定的语义值，也不会自动把补丁应用到文件。

最准确的角色定义：它是“独立质检与纠偏建议回路”，不是第二个拥有最终编辑权的主 Agent。

05

Runtime Corrector 适合哪些场景

它最适合有明确产物边界、可描述质量标准，并且需要经过多次写入或多阶段交付的工作。产物可以是 Markdown、JSON 或纯文本，也可以是同一阶段内必须共同成立的一组文件。

  • 多阶段文档
    需求、设计、测试逐级传递约束。
  • 结构化交付
    字段、编号、引用和 Schema 必须稳定。
  • 上下游链路
    下游不得遗漏、矛盾或扩张上游。
  • 并行变更
    项目同时保留多个 change，需要严格隔离。

它不适合“项目里的所有文件都自动判断好坏”这种无边界期待。保护范围与检查标准必须先由项目清楚声明。

06

什么才算一次纠偏成功

成功不等于插件自动改完文件。一次可信的纠偏应当满足四件事：偏差被准确描述；结论附有足以复核的文件与内容证据；建议修改只触及必要范围；主 Agent 修订后，新一轮检查不再报告已经解决的问题。

如果问题涉及新业务决策，例如“离线时究竟缓存多久”，安全结果可能是诊断明确、候选 Diff 为空，并提示转交用户决定。这不是失败，而是插件守住了权限边界。

成功标准：发现得准、解释得清、建议得克制、复查能闭环。

Part 02 · The review model

先理解 Runtime Corrector 的工作对象

插件不预设你的业务流程。项目通过几个简单但边界清楚的概念，告诉它“检查谁、和谁比较、哪些文件属于同一次变更”。

07

什么是受保护产物

受保护产物是项目在 .runtime-corrector/config.yaml 中显式声明的 artifact，并且其路径命中已启用 Stage 的 patterns 或 pathTemplates。它不是“仓库里碰巧存在的文件”，也不是安装插件后自动扩张到全项目的隐形范围。

每个 artifact 还可以声明格式、规则文件、Reviewer、相关文件、是否允许成为候选 Diff 的目标，以及持久化结果时使用的输出标识。

可控性：文件是否受保护，能够从项目配置和实际路径得到确定答案。

08

什么是 Stage

Stage 是一个具有特定产物、格式、规则和审查标准的业务阶段，例如“需求报告”或“测试设计”。这些名称来自项目自己的 artifact 定义；核心插件的 Stage 目录为空，不内置 IR、Planning、PRD 等业务假设。

同一个通用运行时因此可以服务完全不同的流程。新增 Stage 的主要工作是补充项目 YAML、规则、Reviewer 和可选 Schema，而不是在核心代码里复制一套分支。

客户拥有标准：Stage 是项目语言，不是插件强加的产品术语。

09

什么是节点检查

节点检查聚焦当前 Stage 自身：文件是否完整、结构是否合法、内容是否符合该阶段标准。确定性规则可以检查必填章节、字段类型、编号和 Schema；节点 Reviewer 则判断清晰度、可执行性、是否存在内部矛盾等语义问题。

节点检查不要求一定存在上下游。一个独立设计文档也可以仅凭自己的规则接受保护。

要回答的问题：“只看这个阶段现在的产物，它本身能不能作为可信交付？”

10

什么是上下游边检查

Workflow 中一条 from → to 的有向边，表示目标节点需要以来源节点为事实依据。边检查默认关注五类风险：违背、遗漏、无依据扩张、决策失真和追溯标识断裂；项目还可以为这条边增加自己的 Reviewer 标准。

例如，需求说明“必须离线运行”，方案文档没有提及离线行为。两个文件单独看都可能结构完整，但边检查会把这种跨文档丢失识别出来。

要回答的问题：“这个下游交付，是否忠实承接了它有责任承接的上游事实？”

11

什么是 Bundle

Bundle 是一个节点在当前实例中需要作为整体读取的一组文件。比如“测试设计”可能由用例正文和机器可读清单共同组成；修改任意成员，都可能改变整组产物是否完整、引用是否一致。

因此，触发文件只是本轮检查的入口，不一定是唯一被检查的内容。插件会重新收集该节点的匹配文件；缺少预期成员时，与缺失成员相关的判断保持 pending，已有内容仍执行可完成的检查。

为什么重要：质量属于交付整体，而不只属于最后一次被编辑的那一个文件。

12

什么是 Workflow

Workflow 是项目定义的有向无环图：artifact 是节点，审查关系是边。配置编译时会拒绝未知节点、重复边、自连接和环，避免运行时在含混的流程关系中猜测。

检查当前节点时，只收集它配置的直接入边来源，而不是把整个仓库或整条历史链路都塞给 Reviewer。这样既减少无关信息，也让“这条诊断依据哪一段关系”更容易解释。

边界清楚：Workflow 告诉插件应当比较什么，也同时限制它不应当比较什么。

13

什么是 Change 实例

Change 实例是同一项目中某一次需求或变更的稳定身份。例如路径 spec/2026-07-29-模块设计报告-flower-eshop.md 可以通过 Path Template 提取 changeName=flower-eshop。不同 Stage 复用同一 key，插件才能把它们归入同一条链路。

Change 实例解决的不是文件命名美观，而是并行工作时的事实隔离。没有稳定实例标识，“最新的需求文档”很可能属于另一个任务。

隔离原则：关系来自显式、稳定的业务标识，不来自修改时间、目录顺序或文件名猜测。

Part 03 · The correction loop

一次自动纠偏是如何运行的

从写入到反馈，Runtime Corrector 把一次检查拆成可解释的阶段。任何一层无法安全完成时，都有明确状态，而不是静默跳过或假装已经验证。

14

纠偏在什么时候被触发

插件注册的是 Claude Code PostToolUse Hook，匹配 Write|Edit。也就是说，文件写入或编辑已经结束后，Runtime Corrector 才接到触发信息并开始工作。

它不会在用户每次输入时持续添加工作流提示，也不会在文件尚未落盘时审查一份想象中的结果。失败反馈中只有在需要进一步恢复信息时，才会按条件补充 spec 和 help 的命令导航。

体验边界：正常生成上下文保持干净；质量回路发生在实际写入之后。

15

系统如何判断一个文件是否需要检查

运行时先加载项目配置并编译统一的 RuntimePlan，再把写入路径与当前已启用 Stage 的 artifact matcher 比较。artifact 必须选择 patterns 或 pathTemplates 之一；没有命中的路径返回 unmatched-artifact，检查到此结束。

Stage 开关先过滤保护策略，路径匹配再确认具体文件。这意味着“仓库中定义过”不等于“当前启用”，“扩展名相同”也不等于“自动受保护”。

可预测性：客户可以通过 stages、explain 和路径模板，在写入前知道检查是否会发生。

16

系统检查的是哪一个版本

Hook 只提供触发路径，检查器随后从项目目录重新收集并读取文件。诊断、哈希、候选 Diff 和持久化记录都建立在这次写入完成后的磁盘内容上，而不是会话早先读过的文本副本。

候选补丁还记录基线内容的 SHA-256；即使检查后文件再次变化，后续应用前的基线与 git apply --check 校验会阻止把旧建议生硬套到新内容上。

事实基线：当前磁盘快照是内容依据；会话记忆不是。

17

系统如何收集相关上下游文件

检查器根据当前 artifact、Bundle 路径、Workflow 的直接入边与项目声明的 relatedPatterns 建立路径计划。启用 correlation 时，候选文件还必须与触发文件提取出的 Change key 相同；不属于本实例的文件会被排除。

收集数量受 limits.maxRelatedFiles 等限制约束，配置目录与结果目录也会被保护性排除。最后形成的 artifact 列表写入本轮 metadata，便于用户知道审查实际看了哪些文件。

审查范围可解释：不是“把仓库全喂进去”，而是按节点、边和实例构造本轮快照。

18

第一层检查：确定性硬规则

确定性检查用于回答能够机械判定的问题：必填章节是否存在、字段是否符合 JSON Schema、编号是否唯一、引用能否解析、标题层级是否跳跃，以及项目规则文件声明的其他结构约束。

同一输入应当得到同一结果，因此它适合成为稳定门槛。错误会带上规则 ID、严重级别、文件、可用时的行号、证据和建议，而不是一句笼统的“格式不对”。

价值：把可复现的问题交给规则引擎，减少语义模型在简单事实上的漂移。

19

第二层检查：隔离语义审查

当节点或入边显式设置 review.enabled: true，自动写后检查会基于原会话创建一次性 fork。隔离会话只允许读取与检索，不具备写入目标文件的工具；它接收本轮请求、规则结果、Reviewer、规范和 Workflow 快照，并返回受 JSON Schema 约束的 findings 与 edits。

fork 使用独立执行环境并设置递归保护，结束后不持久化会话。若 Hook 输入没有可用的 session_id、无法 fork 或超时，结果会明确记录语义审查失败，而不会把“没审”包装成“通过”。

独立性不是口号：审查上下文、可用工具、返回格式和生命周期都受代码限制。

20

语义审查会检查什么

节点 Reviewer 关注当前产物是否清晰、完整、可执行、内部一致；边 Reviewer 则比较来源与目标，寻找遗漏、矛盾、无依据扩张、范围变化、决策失真和追溯断裂。项目可以把领域特有标准写入对应的 *.reviewer.md。

每条 finding 必须引用当前目标产物中的合法路径和具体 evidence。上游可以作为证据来源，但诊断落点与修改目标受当前节点的可编辑列表约束。

它审的是“当前产物应该承担的责任”：不是泛泛评价文笔，也不是重新替用户设计业务。

21

为什么硬规则和语义审查必须分开

若把“是否有必填字段”交给语义模型，结果可能不稳定；若把“是否忠实承接离线要求”硬编码成字符串搜索，又会错过同义表达和上下文。两层检查分别承担自己擅长的判断，最后再合并成同一轮结果。

  • 硬规则
    稳定、快速、可复现，适合结构事实。
  • 语义审查
    理解语境与关系，适合内容责任。
  • 统一诊断
    同一状态模型，同一证据表达。
  • 统一落盘
    诊断与候选 Diff 保持同轮身份。
22

上游文件不完整时如何处理

如果当前节点有一条已启用入边，但同一 Change 实例中尚未找到来源文件，插件会加入 WORKFLOW-EDGE-SOURCE-MISSING 的 pending 诊断。它不会因为流程自然尚未完成就判定业务错误。

与此同时，当前节点自己的硬规则、节点语义审查，以及其他已经就绪的入边仍然可以执行。只有依赖缺失来源的判断保持待完成；当上游补齐后，后续写入会自动升级为完整跨文件检查。

区别很重要：pending 表示证据尚未齐备，不等于违规，也不等于已通过。

23

系统如何形成候选修改

确定性规则若能给出安全修复，或语义 Reviewer 能把问题表达为最小、明确的行级操作，结果处理器才会尝试生成候选 Diff。语义 edit 必须指出目标文件、行号、期望原文和替换内容，且每轮操作数量受上限约束。

如果修复需要编造尚未决定的值、存在多种业务方案，或无法精确命中当前原文，正确输出就是诊断存在而 Diff 为空。插件明确把“没有安全补丁”与“没有问题”区分开。

候选的含义：它是可供主 Agent 审核的最小机械改写，不是自动生效的业务答案。

24

候选 Diff 如何保证基本安全

生成前，行级操作会检查行号有效且 expect 与当前原文完全匹配；目标路径必须在项目内，并且在 Workflow 场景下必须属于当前节点的 editableArtifactFiles 白名单。

生成后，补丁头部与声明路径要一致，代码会解析真实目标并运行 git apply --check。候选记录还包含基线与建议内容的哈希。任一验证失败都会阻止这份 Diff 成为可交付建议。

安全是多道门：原文命中、目标白名单、补丁目标解析、可应用性检查，缺一不可。

25

为什么插件不会自动应用补丁

即使补丁在技术上可应用，也不代表它在业务上应该应用。主 Agent 掌握用户最新要求、正在进行的其他修改和更完整的任务意图；Runtime Corrector 只掌握为审查构造的受限快照。

自动应用还可能掩盖真正需要用户选择的问题。因此代码与反馈都把候选补丁标记为 diagnostic only，并明确要求应用前再次确认基线和 git apply --check。

权限边界：发现问题与作出业务修改决定，是两个不同角色的责任。

26

诊断结果如何返回原 Agent

最终反馈回到产生写入的会话，包括整体状态、触发文件、配置来源、规则 ID、具体诊断、建议、候选 Patch 数量，以及持久化开启时的 Round 与 Latest 文件路径。

如果隔离语义审查已完成，反馈会说明其状态并合并语义 findings；主 Agent 不需要自己再次加载同一 Reviewer。若审查失败或仅被请求，也会明确显示，避免用户误认检查覆盖范围。

反馈目标：让主 Agent 能直接围绕真实偏差做最小修订，而不是收到一个无法行动的质量分数。

27

修订后如何形成反馈闭环

主 Agent 审阅诊断与候选 Diff，决定修改、忽略、转人工或停止当前阶段。只要它再次通过 Write 或 Edit 写入命中产物，就会以新磁盘快照启动新一轮检查。

每轮诊断重新计算，不把上一轮 finding 当作本轮事实。已修好的问题自然消失，新产生的问题单独出现；若开启持久化，历史 Round 仍保留，Latest 则更新为当前结果。

闭环不是“循环报错”：每轮都从新快照重建证据，直到当前状态真实通过或由责任人明确处置。

Part 04 · Change isolation

多阶段、多变更情况下如何避免串线

当仓库同时保留 feature-a、feature-b 和历史交付时，最危险的错误不是“找不到文件”，而是悄悄找到了一个看似合理、实际属于别的任务的文件。

28

为什么不能自动选择“最新文件”

修改时间只说明文件最后何时被写入，不能说明它属于哪个业务意图。一个昨天继续维护的旧 Change，可能比今天新建 Change 的上游文件更新；按目录排序取第一个也同样没有业务依据。

Runtime Corrector 不保存一个会被暗中切换的“当前 active key”，也不通过时间、目录顺序或近似名称推断实例。没有可证明的关联，就不会把历史产物提升为正式上游。

可信选择的最低条件：来源文件必须与当前路径提取出的显式实例标识一致。

29

Path Template 如何识别同一条变更

Path Template 把稳定的路径结构写成带占位符的声明，例如 spec/{YYYY-MM-DD}-模块设计报告-{changeName}.md。编译器把占位符转换为路径匹配器，写入命中后提取 YYYY-MM-DD 与 changeName 等值。

模板不允许混用 glob 的 * 或 ?，占位符必须合法且不能重复。这样，一个路径究竟能提取出什么实例信息，在配置加载时就可以被验证。

pathTemplates:
  - "spec/{YYYY-MM-DD}-模块设计报告-{changeName}.md"

# 命中后：
# { "YYYY-MM-DD": "2026-07-29", "changeName": "flower-eshop" }
30

Correlation 如何保持上下游一致

workflow.correlation.keys 指定哪些占位符共同定义 Change 身份，例如只使用 changeName。所有参与 Workflow 的 artifact 模板都必须覆盖这些 key，否则配置编译直接失败。

收集文件时，插件对 key 做规范化比较；只有值相同的节点产物才会进入同一快照。日期可以存在于路径但不参与 correlation，从而允许同一 Change 的不同阶段在不同日期生成。

强约束：不是 Reviewer “尽量分清”，而是在审查前就把不同实例从文件集合中隔离。

31

新变更与继续旧变更如何区分

继续现有变更时，各阶段路径必须复用原 correlation key；新建变更则使用新的 key。插件可以验证 key 是否一致，却不能从一句含糊的任务描述判断用户想“继续旧的”还是“开始新的”。

因此，意图不明确时应由主 Agent 在写入前询问用户。Runtime Corrector 的职责从文件落盘后开始，它不会重命名 key、迁移历史产物或替用户决定业务身份。

把不确定性留在正确位置：实例选择是用户意图问题，不应该被文件时间戳替代。

32

历史产物如何安全地作为参考

新 Change 可以由主 Agent 显式读取历史文件，复用写作结构、领域知识或经验教训。但“被读取作为参考”与“成为当前 Workflow 的事实来源”是两件事。

除非历史文件的实例 key 与当前 Change 一致并匹配正式入边，它不会自动进入当前上游快照。这样既允许经验复用，也避免把旧项目结论不经确认地继承到新需求。

安全复用原则：历史可以启发新内容，不能静默替代新变更的正式依据。

33

为什么语义审查不能反向修改上游

检查下游时，上游承担的是证据角色。如果 Reviewer 发现冲突后直接修改上游，就等于让下游的解释反向覆盖事实来源，破坏责任顺序，也可能同时影响依赖该上游的其他节点。

代码因此把当前目标节点文件列为 editableArtifactFiles。语义 finding 必须落在目标列表，候选 Diff 也只能指向该白名单；若 artifact 设置 editable: false，本轮可编辑列表为空。

单向责任：上游可用于举证，不因一次下游纠偏而被越权改写。

Part 05 · Evidence & trust

用户凭什么信任纠偏结果

信任不是来自“AI 说它检查过了”，而来自可区分的状态、可复核的证据、不可变的轮次记录、同轮补丁，以及能直接打开查看的实现与配置。

34

检查状态分别代表什么

整体状态由当前诊断的最高优先级推导：出现 error 即 failed；没有 error 但有待完成依赖则 pending；再其次是 warning；没有这些诊断才是 passed。

passed

当前已执行的规则与审查没有发现偏差。

warning

存在提醒，是否阻断由主流程与责任人决定。

pending

依赖尚未齐备；已具备条件的检查仍然执行。

failed

发现 error 级偏差，需要明确处置后再继续。

不要误读：passed 只覆盖当前已加载并完成的标准；pending 不是失败；warning 也不会被伪装成成功。

35

每条问题为什么必须附带证据

没有证据的结论无法被独立判断，也无法指导最小修订。Runtime Corrector 的诊断结构要求规则 ID、严重级别、目标路径、信息；可用时还包含行号、evidence 和 suggestion。语义审查的返回 Schema 对 finding 路径和 evidence 列表也有约束。

AGENT-UPSTREAM-CONSTRAINT-OMITTED
docs/solution.md:18
目标文档描述在线同步，但没有承接上游“必须支持完全离线运行”的约束。
Evidence: requirements.md:12 ↔ solution.md:18–25

ERROR

证据的用途：用户能验证结论，主 Agent 能定位修改，团队也能在事后解释为什么当时判定失败。

36

为什么每轮检查都保留独立记录

开启 output.persist: true 后，每次快照检查获得独立 Round ID，并写入 runs/<stage>/<artifact-key>/<run-id>/。后续检查不会覆盖这一轮。

latest/<stage>/<artifact-key>/ 则提供稳定入口，始终指向当前最新结果。历史 Round 回答“纠偏是怎样演变的”，Latest 回答“现在是什么状态”，两种需求互不牺牲。

.runtime-correction/
├─ runs/solution/design-flower/20260729T101112Z-a1b2c3d4/
│  ├─ diagnostic.md
│  ├─ patch.diff
│  └─ spec.md          # 仅 failed 且有规范时
└─ latest/solution/design-flower/
   ├─ diagnostic.md
   └─ patch.diff
37

诊断和候选 Diff 为什么必须属于同一轮

诊断与补丁描述的是同一个磁盘快照。若把旧诊断与新补丁混用，补丁可能修复已经变化的行，甚至对应另一个 Change。Runtime Corrector 在结果合并、Diff 校验完成后，统一持久化同一 Round 的 diagnostic.md 与 patch.diff。

Round metadata 包含时间、Stage、artifact、触发文件和文件集合；Diff 还带基线哈希。Latest 更新时也是成对写入，不允许用户只看到一个来源不明的“最新补丁”。

配对原则：建议永远随它所依据的证据一起交付。

38

检查失败时如何获得完整规范

当状态为 failed 且该 Stage 有规范包时，持久化结果会额外保存 spec.md。它聚合全局格式契约、当前 artifact 映射、硬规则、引用的 JSON Schema、Reviewer 与恢复说明，避免修复过程中只看到一条错误却不知道完整边界。

用户也可以运行 /runtime-corrector:spec <stage> 主动查看同一类权威规范。这个命令适合首次作者、复杂失败恢复或怀疑规则之间存在矛盾时使用。

恢复不是猜测：失败现场与完整规范都能落盘，主 Agent 可在下一次编辑前读取原始依据。

39

如何知道当前真正执行了哪些规则

/runtime-corrector:explain <stage> 展示该项目实际加载的 artifact 策略、规则文件、Schema、Reviewer 和执行顺序。它回答的是“现在运行的是什么”，而不是一份可能已经过期的产品宣传。

explain 适合快速核对日常运行；需要精确语法、全部 Schema、完整 Reviewer 或失败恢复图时，再使用 spec。两者都以项目自有配置为主要事实来源。

透明性：团队能够把一次运行结果追溯到当前有效的具体配置文件，而不是隐藏规则。

40

项目如何拥有自己的质量标准

项目在 .runtime-corrector/ 中维护 config.yaml、*.rules.yaml、*.reviewer.md 和可选 schemas/*.json。Stage 开关、路径、Workflow、correlation、输出与限制同样显式存在于项目配置。

这些文件可以像其他工程资产一样评审、版本控制和演进。规则或 Reviewer 修改后，下一轮加载即生效；核心插件只提供通用编译、执行、隔离与安全机制。

治理归属：业务标准由项目团队拥有，Runtime Corrector 负责忠实执行和公开结果。

41

理念分别落实在哪些代码和产物中

下面的连接以当前 HTML 文件为起点，直接打开仓库中的真实配置或实现。每张卡片先说明客户可见的承诺，再给出承担该承诺的代码位置；这样既能从理念追到实现，也能从运行结果反查责任模块。

Part 06 · Configure & operate

如何配置和使用 Runtime Corrector

安全启用的顺序是：先建立项目模板，再定义真实标准，核对实际加载结果，最后逐个启用 Stage。插件不会因为“已经安装”就自动接管全部产物。

43

如何安全初始化项目

在 Claude Code 中运行 /runtime-corrector:init，会创建项目自有的 .runtime-corrector/，其中包含带中文注释的 config.yaml、示例规则、示例 Reviewer 和 README。若目录已经存在，初始化会拒绝覆盖。

模板的 enabledStages: [] 是刻意设计的安全默认值：初始化完成后，没有任何业务文件立即被看护。团队可以先评审模板、改成真实业务定义，再显式启用。

/runtime-corrector:init
/runtime-corrector:help

# 初始化 ≠ 启用
# 先确认 .runtime-corrector/config.yaml，再打开真实 Stage

零惊喜启动：不覆盖、不默认开启、不把示例 Stage 当成你的正式流程。

44

启用前需要定义什么

每个真实 Stage 至少需要确认 artifact 名称、路径识别方式、格式、硬规则是否启用、语义审查是否启用及其标准。多阶段流程还要确认节点边、边 Reviewer 和 Change correlation。

  • 保护谁
    artifact、Stage、format、patterns/pathTemplates。
  • 如何检查
    rules 文件、Reviewer、可选 JSON Schema。
  • 与谁对齐
    Workflow 入边与边审查标准。
  • 属于哪次变更
    稳定 Path Template 与 correlation keys。

最后再决定输出是否持久化、目录位置、相关文件数量、Reviewer 长度、反馈长度和语义审查超时。建议先在少量代表性产物上运行，再逐步扩大 Stage 范围。

45

如何查看和控制 Stage

/runtime-corrector:stages 显示项目已安装的全部 Stage 及 on/off 状态；追加 <stage> on 或 off 可以切换单个 Stage。Stage 名只来自项目的 artifacts[]，没有隐藏目录。

关闭 Stage 只是把它从当前 RuntimePlan 的受保护 artifact 集合中移除，不会删除规则、Reviewer 或业务产物。重新启用后，原项目标准仍在。

/runtime-corrector:stages
/runtime-corrector:stages solution-design on
/runtime-corrector:stages solution-design off

可逆控制：开关影响执行，不破坏项目已经定义的质量资产。

46

自动检查与手动检查有什么区别

自动检查来自 Write/Edit → PostToolUse，拥有原会话的 session_id，因此在 Reviewer 开启时可以创建隔离 fork，最终合并硬规则与已完成的语义结果。

/runtime-corrector:check <artifact> 或终端 CLI 主要执行确定性检查。它会把已配置 Reviewer 作为 agentReview: requested 返回，但不会自己创建隔离会话。需要完整“硬规则 + 隔离语义审查”时，应以自动写后结果为准。

  • 自动写后
    硬规则 + 可用时的隔离语义审查。
  • 手动 check
    硬规则 + 待完成 Reviewer 任务。
47

如何查看规则和完整规范

日常核对使用 explain：它简洁展示命中的 artifact、项目规则、Schema、Reviewer 和执行顺序。首次编写复杂产物，或失败后需要理解精确格式与恢复路径时，使用 spec 获取完整原子规范包。

/runtime-corrector:explain solution-design
/runtime-corrector:spec solution-design

推荐顺序是：先看当前诊断做最小修改；只有当诊断不足以确定正确格式，或多次失败怀疑规范矛盾时，再展开完整 spec。这能兼顾上下文效率与恢复完整性。

两个入口，两种深度：explain 回答“正在执行什么”，spec 回答“完整地应该怎样做”。

48

使用前提与运行限制

运行需要 Claude Code、Node.js 18+ 和项目配置。语义审查依赖可从当前会话创建隔离 fork；主会话若使用阻止会话持久化的启动方式，或 Hook 输入缺少 session 信息，语义审查会明确失败或保持 requested。

项目可以限制相关文件数、反馈长度、Reviewer 长度和语义审查超时。默认语义超时为 240 秒，可配置范围为 1 秒至 20 分钟；Hook 外层上限为 1260 秒，用于容纳最长审查和结果落盘。过长或过多内容应通过更精确的 artifact 和 Workflow 边界治理，而不是盲目提高上限。

实施提示 先用代表性 Change 试运行，观察一次真实快照包含哪些文件、耗时多久、哪些 Reviewer 最有价值，再决定团队级默认限制。
49

哪些文件不会受到保护

未命中当前已启用 Stage 的 patterns 或 pathTemplates 的文件不会检查；已定义但关闭的 Stage 不执行；项目未初始化时，插件默认没有业务 artifact，也不会主动看护文件。

此外，不符合 correlation 的历史或其他 Change 文件不会被纳入当前 Workflow 快照；结果目录与策略目录也有保护边界，避免一次诊断触发新的递归检查。

安装不等于全仓保护：只有“配置存在 + Stage 已启用 + 路径命中 + 实例关系成立”的产物，才进入相应检查。

50

用户最终应当如何理解 Runtime Corrector

Runtime Corrector 是一个可配置、可追溯且不越权的写后反馈回路。它把项目标准编译为可执行计划，对当前磁盘快照做确定性与隔离语义检查，为偏差保留证据，并把经过安全验证的候选修改交还给主 Agent。

它不替代业务流程、不替用户选择 Change、不声称检查之外的内容已经正确，也不自动应用补丁。它真正提升的是错误被发现和被纠正的概率，以及团队解释每次决策的能力。

最终承诺 Runtime Corrector 不承诺“自动把所有内容改对”，而是让偏差能够在写入后被独立检查、具体说明、留下证据，并以受控方式反馈给真正负责修改的 Agent。

独立检查，受控反馈，持续对齐。

本文以当前仓库实现与项目配置为依据。Runtime Corrector 的可靠性来自边界清楚、证据可查、规则可改和每一轮结果都能追溯。
