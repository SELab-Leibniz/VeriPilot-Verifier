## 交付边界

核心事务、仅验收/授权修正、独立 Gateway 控制、状态页、CLI 和确定性报告已实现。此次只安装到 `/tmp/rc-openclaw7-acceptance`，使用独立端口 19877；没有替换用户 18789 Gateway、已安装插件或项目配置，没有宿主补丁。

原生网页的 Queue 会把查询留在客户端队列；固定版本 `reply_dispatch` 没有 `userTurnTranscriptRecorder`，排队成功不能当作独立回复的历史持久化回执。因此**不宣称原生网页、TUI 和独立控制入口完全等价，不宣称 A01–A29 全部通过**。详细边界列在下表；未验证不是通过。

## 实际修复及证据

- `.6` 核心会在返回适配层前扣内容修正次数。现在两条阻断分支均支持 `verify_only`，问题与评审保存，预算不扣；有效明确授权以唯一意图扣一次。
- 取消检查原在核心返回之后。现在计算/模型等待在事务外，提交前统一校验 generation、需求版本/摘要、pending revision、cancelEpoch、期限及文件证据。过期 PASS、偏差和基础设施失败仅入审计。
- 固定提示曾丢失有用解释。现在报告从持久化记录生成，区分反馈送达、实际文件修改、复验确认；不重新交给 reviewer。
- 真实测试发现“评审误读拼错的可选路径”导致无关缺失文件被当作必需证据。现在失败的探索读取保留审计，必需文件缺失仍阻断。
- 真实测试发现原生 heartbeat 进入纠偏控制器，覆盖待授权状态。现在使用宿主 trigger 与内部执行身份隔离。关闭受控执行和系统事件通过原生 attempt 衔接，官方认证 API 配合独立内存凭据存储，保留 provider 认证；不重复创建同一会话的队列或生命周期。`HEARTBEAT_OK` 有真实原生记录，任务 generation、GT 版本、预算和验证状态保持不变。
- 原核心对“故障注入任务已按要求执行”判 PASS，不等于故意写坏的文档合格。新增独立 `fileAssessments`，绑定实际评审证据；旧记录缺证据仍为未验证。受影响文件在归因记录中保留；旧记录仅从同一 evaluationId、deviationKey 的保存评审恢复路径，不按文本猜。
- 终端真实测试进一步发现 worker 读取不存在的 `workflow.yaml` 也被误列为必需成果。现在仅把成功读取的普通文件加入使用证据，失败读取/目录探索不冒充必需交付物；必需文件仍由配置与任务决定。
- 取消或过期的评审不再提前发布最新诊断；诊断输出和任务状态一起提交，崩溃后仅恢复已提交清单。

## 真实三文件任务

网页提交了原始故障注入任务，工作模型 `work/ark-code-latest`，独立 reviewer `review/glm-5.3`；使用已授权 Coding Plan 接口。密钥只来自临时子进程环境，不进入安装包或报告。

第一阶段实际写入唯一目录 `openspec/changes/test-guard-memory-notes-4f7a2c/`：proposal 持久化矛盾被检测，收到反馈后最小修正；design 的内存/重启丢失冲突和 tasks 的登录、云同步越界及持久化遗漏被检测。初次 artifact 评审没有完整指出编辑、删除、完成状态的遗漏，**不能声称原始检测覆盖全部通过**。

随后通过独立状态页明确更新最终合格要求（GT 版本 2），先只验收：GLM 明确发现 design 冲突、tasks 越界及全部所需遗漏，内容修正次数仍为 0。一次 `fix-after-heartbeat` 授权提交后次数变为 1，真实 worker 修改三份文档并复验。原核心 PASS，历史交付 ACKED。新构建的 `final-quality-window` 再次只验收，三份文档分别 PASS，任务、GT 版本 2、epoch 2 和 1/3 预算保留。

[网页任务完整脱敏证据](openclaw-acceptance-7-web-evidence.json)保存 8 个写入快照、反馈事件、逐项问题、评审和指令时间窗。故障检测覆盖、完整纠偏闭环、文档质量是三种不同结论。当前最终文档质量通过；初始注入全覆盖仍不满足，不用后续补充要求后的检测替代。

## 终端与控制入口补充记录

真实 TUI 在 `agent:main:rc7-terminal` 提交相同原始任务，保存 5 份文件版本。proposal 矛盾被发现并修改两次；design 的内存存储冲突和 tasks 的遗漏、越界有实际评审。初次最终验收因不存在的探索读取路径被误收进证据而 UNVERIFIED，此失败保留在[初次记录](openclaw-acceptance-7-tui-evidence.json)。修复后以 `tui-recovery-final` 创建新的有界窗口，仅评审当前文件：原核心对故障注入任务 PASS，proposal PASS，design 和 tasks 均 DEVIATION；内容修正次数仍为 0，未重复写文件。见[重验记录](openclaw-acceptance-7-tui-recovery-evidence.json)。不能将此结果描述为三份文档全部合格。

两次原始任务的写入均通过 Write/Edit；TUI 模型另外调用了 Read 读取技能、配置和探索目录。如果把“只用 Write/Edit”解释为禁止任何 Read，此严格工具约束未通过，不能隐藏这些调用。

- 状态页在评审过程中停止，真实回执依次为 STOPPING、STOPPED；之后新指令重验通过，仍为 GT 2、内容修正 1 次，保留 cancelEpoch 历史。
- 原生网页另一个测试会话点击“停止生成”后显示 Interrupted，控制器最终 CANCELLED；TUI 独立会话按 Escape 后显示 `run aborted`、`connected | aborted`。两次都在实际写文件前停止，没有宣称成功；这不替代每个取消竞争点的夹具测试。
- 原生网页忙碌时查询先落到客户端 Queue；点击 Steer 后获得持久化记录生成的只读解释，没有启动评审。独立状态页能立即查询与重连；这两种体验不能宣称等价。
- 关闭受控执行后，真实模型回复 `NATIVE_LIFECYCLE_OK` 和新会话的 `FRESH_NATIVE_OK`，输入区不再残留“正在响应”。宿主会话查询为 `done / hasActiveRun:false`，但网页侧栏曾残留活动图标与禁用的新会话按钮，重新进入页面后恢复。残留状态的具体归因未验证，仍不宣称已修复。
- 无效 Gateway token 被真实拒绝；20 次原生客户端状态请求和接收/取消回执见[交互证据](openclaw-acceptance-7-interactions.json)。用户项目配置 SHA-256 与测试开始时一致。
