# Review 模块第2轮：独立审查、修复与验证

2026-10-24。生产仓库保持20ec5b5、工作区干净；只改隔离实验，未接入Stop，未运行或修改原项目与原session。最终可执行代码在 `experiments/review-task/v2/`，准确冻结版本为 `source-snapshot-03/`。目录中的v2是实验代码位置，不是声称所有实测都用同一版。

## 审查结论

这轮改善的重点是把三个不同问题分开：**任务是否说清、证据是否真实、判断是否正确**。结构化结果合法只能回答其中一部分，不能自动证明语义正确。

最小可复用单位仍是一个明确的证明问题。程序给问题、适用条件和证据版本；模型使用现成只读工具查证并选择cite；程序取得原文并保存结果。不需要另建规划模型、总结agent或调度框架。本轮观察到模型往返和累计输入减少，且正反对照没有因此出现语义误判。

## 1. 实际找到并修复的问题

1. **任务可没有问题文本。** 旧检查只要求ID和文件列表，甚至空问题也能启动。现在必须有非空requirement；调用方用scope明确源码实现与运行验收，不从合法JSON推导业务完成。
2. **引用依赖模型抄写位置。** 上一轮厨房通过项把R04引成R02/R03；复杂案例又多次搜索已读材料找行号。现在read成功后发本次可用的UUID，模型只选citeIds，程序从冻结原始字节取得路径、区间、原文及哈希。需求锚点由程序附加。
3. **登记已读早于真正成功交付。** wrapper内部先记全文，随后回调抛错时，SDK给模型的却是错误。现在只有原生tool_execution_end成功后才确认披露；错误工具结果不能满足必读条件。
4. **同批读取与提交可提前判断。** sequential只保证程序先读再提交，模型可能尚未看到新条件就已决定结论。现在含source工具的同一assistant批次不能提交；须收到取证结果后另起一轮。独立读取仍用SDK原生并行。
5. **引用标记有歧义。** 初次真实实验中，模型多次省略`cite_`前缀，另一次把需求路径当ID。程序正确拒绝，但增加了重试。定向小修改为纯UUID，头部明确`citeId="UUID"`，说明基线位置自动附加，不新增模糊匹配或容错parser。
6. **统计低估重复取证。** 旧repeatedLines只统计read-read，漏掉grep重返已读内容。现在分别报告read、grep、全部工具返回，以及实际提交错误；对比以持久化sessions为准，避免混用新旧toolCalls口径。

对应关键实现：`review-task.mjs:25`任务合同、`:100`引用发放、`:108`校验、`:230`混批拒绝、`:291`成功交付登记、`:342`短反馈。源文件位置均在本轮v2目录，冻结03可复核。

## 2. 子任务和输出怎样保持小

本轮工程工作只有三个独立任务：引用/保存机制、审阅语义对照、复杂长材料查证。每个都有自己的结果与验收，不要求一个agent提交一份大报告。

业务Review也按证明目标分开，例如“R04的源码实现”与“R04的实际运行验收”。原条件和例外仍作为约束完整保留，不拆成条件×文件×指标的组合。不同指标只有共享同一证明时才可关联证据，不能复制一个结论充当多项覆盖。

每次模型仅调用一次合法提交：任务ID、状态、一句机制与影响、最多6个cite ID。没有逐条重述通过条件，也没有最后整包JSON。**本轮真实提交参数最大499字节**；较长的原文与详细证据文件由程序生成，宿主短反馈397–498字节（最终受影响三例及复杂例）。长原因的机制测试也验证了完整留档、反馈只给位置。

范围引用保持诚实：读整文件取得的ID就指向整文件，不把它包装成精确到根因几行。需要精细定位时仍可读取窄区间换取新ID；不为了格式强制增加模型往返。

## 3. 预先固定的对照及结果

### 第一轮，冻结02，五个厨房案例

完整requirements、候选源码及真实Git差异进入输入；变异说明、预期和独立verifier均在模型输入外。源码正例和运行证明是不同scope。

- **C01，正确实现＋注释diff**：源码PASS，独立verifier21场景通过。2轮、16.789秒。
- **C02，删除扣库存循环**：DEVIATION，指出检查后直接保存旧库存，独立persisted-consumption失败。5轮、24.176秒；有1次ID前缀错误。
- **C03，can-cook写查询记录并保存**：DEVIATION，指出只读查询产生写副作用，独立shortfall确认store字节变化。5轮、26.446秒；有1次把需求路径当cite的错误。
- **C04，基线已含扣减缺陷，候选仅注释diff**：仍为DEVIATION，正确检查现行源码。6轮、33.371秒；有2次ID前缀错误。
- **C05，正确源码但问题要求运行验收，且无运行记录**：UNVERIFIED，未把源码分析或外部不可见verifier提升为已运行证据。4轮、15.134秒。

这不是五个业务PASS：四个有结论的源码判断正确，一个运行验收正确保持未验证。逐项人工检查了诊断与原件，未仅凭verdict匹配计分。

## 4. 验证层次与边界

- **40/40机制测试**：正式SDK＋脚本provider，含截断、未知/跨run/篡改引用、源变化、取消、提交后异常、混批提前判断被拒、真实工具交付前错误、长原因留档。注入provider overflow后原生compact恢复，引用仍从原件取。
- **独立原文核验10/10正反控制**：Unicode、BOM、CRLF、篡改文字/偏移、伪造ID、跨任务、未披露尾部及scope变化。独立实现不复用worker提取函数。
- **真实模型**：五个不同厨房对照、三个有定位依据的格式复测、一个复杂源码义务；原件准确性与语义支持分别核验。

没有将机制测试冒充模型质量样本，没有将9次执行当9个独立项目，也没有将正确UNVERIFIED当业务完成。原生产四指标0/4记录不变；本次f1实现反例不能替代M01/M02/M05或完整M12。

## 5. 保留的限制与不增加的架构

引用ID能证明来源与范围，不能证明模型选择对了。读取全部条件不等于条件全部合规。当前引用多为整个已披露文件，诊断已指出函数/机制，但精确定位质量仍弱于窄区间证据。

复杂原因中“anywhere in main source”比必要反例更宽；本轮结论只依赖已经直接证明的首页卡片缺图与加载占位，不能由此推断全项目。原始模型理由未被改写成完美结果。

原生compact保留为退路；本轮没有真实overflow，因此仍不能声称所有too-long场景都会完成。任务失败应保留未验证，不能为通过删条件、增加分母豁免或宣称不崩溃保证。

继续不引入summary agent、模型分组/总评、向量库、多agent投票、新执行loop、额外batch调度或生产缓存。本轮新增主要是有实际反例支撑的引用/交付校验和隔离验证脚本。生产仍保持20ec5b5，不进入Stop接入工作。
