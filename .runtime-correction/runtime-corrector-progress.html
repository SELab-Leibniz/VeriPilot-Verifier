Runtime Corrector 运行时纠偏器

Runtime Corrector is an OpenClaw plugin that reviews coding work in progress. It compares the original request and OpenSpec plan with what the current code and checks show. When it finds a specific problem that can be fixed, it can ask OpenClaw to correct it before the task ends.

The target coding workflow

General usefulness is the first priority. Correct work should finish with little extra effort. When evidence shows an unmet requirement, the plugin should request a specific repair and check it again. Benchmark scores, passing guard tests and additional review activity cannot establish that benefit on their own.

OpenClaw writes the code and runs checks. OpenSpec fixes the order of work: Proposal, Apply, then Archive. Runtime Corrector is an OpenClaw plugin that checks whether the plan and implementation still satisfy the original request.

The plugin reviews configured document writes and handles OpenClaw’s Stop event. Its private reviewer has read-only access to the workspace; OpenClaw performs the edits. The evaluation configures deepseek-flash for coding and deepseek-v4-pro for review.

The installable package reads each project’s requirements and verification settings. Benchmark cases, task-specific checks and grading logic stay in the evaluation workspace. The benchmark freezes code before Archive so it can grade the delivered patch independently.

目标编码工作流

首要目标是对一般编码任务有帮助。正确的工作应以较少额外负担完成；有证据的需求缺口应得到可执行的修复，并重新核验。基准分数、防护测试通过或审查次数增加，都不足以单独证明这种帮助。

Carry the original requirements through to the code

Start with the original request and the existing behavior that must keep working. Split the request into independently checkable requirements, give each a stable ID, and cite its original wording.

  1. Before approval, trace each requirement into the OpenSpec proposal, design, specification scenarios and implementation tasks. Check for omissions, contradictions and tests that cannot establish the promised behavior.
  2. At completion, use the same IDs to trace each requirement through the actual production path and fresh check results. Passing helper tests cannot establish that the user-facing path works.

Ordinary sessions can review document writes and run Stop review and native correction without an operator-staged inventory. The stronger sealed approval currently requires a trusted operator to call the Gateway APIs; a plain-language approval does not create that binding. A public chat command for this stronger path remains a usability gap. OpenSpec itself must also be available in the coding environment; RC initialization does not install its CLI.

Operator authentication does not prove human presence. The host must protect Gateway operator credentials from the coding agent; stock shell execution can inherit those credentials.

With strict coverage enabled, the operator supplies the requirement inventory before Proposal. Approval seals that inventory with the exact plan and binds it to Apply. Stop must check every sealed item, including any item the reviewer leaves out of its own checklist. The operator still needs to check the inventory against the full request, including negative constraints and regression expectations; process and conditional duties need explicit checks.

For projects already using strict Proposal coverage, an opt-in PlanReadiness check is implemented and source-tested. It is disabled by default. The host lists every actual Apply checkbox, and the reviewer must return one READY, BLOCKED or UNVERIFIED row per item, backed by acknowledged reads of the current plan. When enabled, strict approval requires every row to be READY. This checks whether the planned work and verification can proceed, separately from coverage of the requested behavior.

The installable package includes this check. Unsupported indented checkbox syntax stays unverified. An earlier plugin revision passed three scripted controls on stock OpenClaw: approval denial, healthy completion and one native repair. An earlier graded trial joined full-plan readiness to approval and final plan preservation, but exposed an unsupported process warning and an origin-parser limit. A readiness judgment proves neither execution nor SDK capability.

A document integrity failure and a code defect need separate judgments. Under a sealed exact-plan policy, replacing a verification note can break that policy while leaving every task and requirement intact. Ordinary wording changes need review of their meaning and authority. Missing evidence stays UNVERIFIED; it does not by itself establish a defect that warrants a confirmed-deviation repair.

The current default has a completeness gap: the reviewer can omit an original obligation from its checklist without creating an unverified item. An existing generic control confirms this behavior. A clean Stop therefore does not establish complete request coverage. A supplied inventory keeps known items from disappearing, but still needs its own completeness check. Mentioning every feature also does not make a weak verification plan adequate.

把原始需求一直核对到最终代码

先明确原始请求，以及必须继续正常工作的既有行为。把请求拆成可独立核验的需求，为每项分配固定编号，并引用原文。

  1. 审批前，逐项查找对应的 OpenSpec 提案、设计、规范场景和实施任务，核对是否遗漏、互相矛盾，或安排了无法证明目标行为的测试。
  2. 完成时，沿用相同编号，逐项追踪实际运行路径和新鲜的检查结果。辅助函数测试通过，还不足以证明用户实际走到的路径正确。

普通会话无需操作员预先提供清单，也能审查文档写入、执行 Stop 审查和原生纠偏。更强的封存审批目前需要可信操作员调用 Gateway API；一句自然语言“批准”不会建立这条绑定。为这条更强路径提供普通聊天命令，仍是易用性缺口。编码环境也需自行具备 OpenSpec，RC 初始化不会安装其 CLI。

操作员认证不能证明人类在场。宿主必须隔离编码模型对 Gateway 操作员凭据的访问；标准 Shell 执行可能继承这些凭据。

启用严格覆盖检查时，操作员在 Proposal 前提供需求清单。审批把清单与确切的方案版本一同封存，再绑定到 Apply。Stop 必须核对全部封存条目，审查器自己列漏的项目也不能跳过。操作员仍需对照完整原文检查清单，核对否定约束与既有行为的保留要求。流程及条件性义务还需明确的检查。

对于已启用严格 Proposal 覆盖检查的项目，可选的 PlanReadiness 检查已实现并通过源码测试，默认关闭。宿主列出 Apply 的每个实际勾选项，审查器须逐项返回 READY、BLOCKED 或 UNVERIFIED，并引用已确认读取的当前方案。启用后，严格审批要求所有条目均为 READY。这项检查核对计划中的工作和验证是否具备执行条件，与功能需求覆盖分别判断。

可安装的插件包已包含这项检查。不支持的缩进勾选语法保持待验证。先前版本的插件通过了三项标准 OpenClaw 脚本对照：拒绝审批、正常完成和一次原生修复。此前一轮已评分的试验连接了完整方案就绪、审批及最终方案保留，但暴露了缺少依据的流程警告和来源解析限制。就绪判断不能证明检查已经执行，也不能证明 SDK 具备相应能力。

When and how the plugin intervenes

  1. During Proposal, the private reviewer compares drafts with the original request. Strict approval needs a clean review of the complete current plan and coverage evidence for every required item. Covered rows cannot override a blocking semantic finding. A clean recheck can recover without rewriting the files.
  2. During Apply, a write to an approved document triggers an immediate plan comparison. OpenClaw can act on that feedback within its existing run.
  3. At Stop, a confirmed plan change can request native restoration within the correction budget. The admitted run can read the sealed approved text. A genuine scope amendment needs operator approval.
  4. A confirmed code defect can trigger a separate native repair. After either kind of continuation, Stop checks the original requirements against the current code again. Restoration alone does not prove the implementation correct.

The host records admission, dispatch and actual model start. A request alone is not a completed intervention. Only a started correction consumes the repair allowance. Each run has a fixed repair allowance. Earlier development walkthroughs allowed one corrective start; the shipped default and benchmark trials allow two. When strict approval is enabled, a continuation must retain its authenticated approval and requirement inventory; an independent evaluator checks that chain.

During an active Stop review, the plugin can now offer one proof retry when a carried defect receives a PASS without its current origin receipt and the host confirms that a supported, current scope is available. The reviewer must supply genuine fresh reads and an ordinary origin receipt in the same worker, within the original deadline. This does not authorize code changes. Once Stop has completed as unverified, missing evidence alone still does not start a native follow-up.

Usefulness needs a comparison on healthy and defective coding tasks that were not used to tune the plugin. For healthy work, measure completion, unnecessary holds or repairs, and added time and requests against OFF. For defective work, measure missed defects, successful requirement-preserving repairs and new regressions with independent checks. An unverified result must be counted separately from a confirmed defect. Scripted controls verify dispatch and requirement continuity; real-model usefulness remains unproven.

The supplied plugin has an optional origin check, disabled by default. When enabled, it lists observed upstream callers before production coverage is accepted. Each candidate needs a current read and a traced handoff or a source-based exclusion; missing, stale or incomplete evidence stays unverified. Controls on earlier plugin revisions verified the gate, healthy completion and one native repair on an exporter example in stock OpenClaw. Relevance and actual propagation still require semantic judgment. Automatic discovery currently covers JavaScript, TypeScript and ArkTS; strict mode keeps unsupported or incomplete indexes unverified. An earlier graded trial reviewed five original items with this check; the sixth remained unverified because the parser could not bound valid unbraced statements in an upstream callback.

Current citation validation checks source locations, file revisions and bindings. It cannot establish that every diagnostic is true. The recent-history view improves access to evidence, but a reviewer can still make an unsupported execution allegation. Host checks of execution ownership and freshness are proposed work. An unverified review still holds strict approval without establishing a confirmed defect.

插件何时介入，如何纠正

  1. Proposal 阶段，私有审查器把草稿与原始请求对照。严格审批要求当前完整方案的审查通过，并为每项必需需求提供覆盖证据。覆盖记录不能覆盖语义审查中的阻断错误。不改写文件，也可以通过一次干净的复查恢复审批条件。
  2. Apply 阶段，写入已批准文档后立即核对方案。OpenClaw 可以在现有回合内根据反馈自行恢复。
  3. Stop 阶段，确认方案改动后，可在修正额度内请求原生恢复。获准回合可以读取封存原文。主动调整范围仍需操作员批准。
  4. 确认代码缺陷后，可以另行启动原生修复。两类续跑结束后，Stop 都要沿用原始需求重新核对当前代码。方案恢复本身不能证明实现正确。

宿主分别记录准许执行、请求送达和模型实际启动。发出请求还不等于完成干预。只有已经启动的修正才占用额度。每次运行都有固定的纠偏额度。较早的开发走查允许启动一次纠偏；交付默认配置和基准试验允许两次。启用严格审批后，续跑必须保留经过认证的审批和需求清单，并由独立评估器核验这条执行链。

Stop 审查仍在进行时，如果对沿用缺陷提交的 PASS 缺少当前来源回执，且宿主确认当前范围支持核验，插件现可提供一次补证机会。审查器必须在同一回合、原定时限内重新读取真实源码，并取得普通来源回执。这项机会不授予代码修改权限。完整 Stop 已以待验证结束后，仅缺少证据仍不会启动原生续跑。

是否有用，需要用未参与插件调优的健康任务和缺陷任务做对照。健康任务要与 OFF 比较完成情况、不必要的阻断或修复，以及增加的耗时和请求。缺陷任务要用独立检查测量漏检、保留原需求的成功修复，以及新增回归。待验证结果与已确认缺陷分别计数。脚本对照已验证调度和需求延续，真实模型的实际帮助仍未证明。

当前交付的插件已加入可选的上游来源检查，默认关闭。启用后，宿主在接受生产覆盖前列出观察到的调用者。每个候选都需要读取当前源码，并给出传递链或基于源码的排除理由；证据缺失、过期或发现不完整时保持待验证。先前版本在标准 OpenClaw 的导出器对照中验证了该约束、正常完成和一次原生修复。相关性和实际参数传递仍需语义判断，自动来源发现当前覆盖 JavaScript、TypeScript 和 ArkTS；严格模式下，不支持或不完整的索引保持待验证。此前一轮已评分的试验用这项检查审查了五项原始需求；第六项因解析器无法界定上游回调中的合法无花括号语句而保留为待验证。

当前引用校验会核对原文位置、文件版本和绑定关系，但不能证明每项诊断都属实。近期历史视图改善了证据访问，审查器仍可能提出缺少依据的执行指控。由宿主核对执行证据归属和新鲜度，目前仍是拟开展的工作。待验证的审查仍会阻止严格审批，但不足以认定存在已确认缺陷。

What must improve next

  1. Make the ordinary workflow dependable. The evaluation must record harmless plan wording changes without treating them as broken sealed approval. It must also recognize a legitimate native corrective successor through trusted host records; accepting only the original Apply run would reject a successful correction. Both fixes belong to the evaluator, and neither changes the original failed result. The plan-change guard passed 14 independent controls, and native successor handling passed 31. Live qualification is still required.
  2. Demonstrate a real repair. Preserve the failing candidate, the specific evidence that triggered RC, the corrective run and the independently checked result. Ordinary Apply repairs receive no RC credit. A separate evaluation fixture is prepared to inject one declared fault before final review, leaving the installable plugin unchanged. Fresh setup and configuration checks passed, and the test is running. This can test the mechanism; it cannot estimate how often RC catches natural mistakes. The shipped plugin must contain no task-specific logic.
  3. Check completeness against the original request. A supplied inventory can keep known obligations from disappearing. It cannot prove the inventory was complete. The latest default-policy run had no prepared inventory, and its nine reviewer-selected rows do not establish exhaustive coverage. Evaluate both missing plan obligations and missing implementation behavior, including regression duties and required user paths.
  4. Measure useful work against added effort. The latest healthy case used 34 Pro and 30 Flash requests with zero native corrective starts. We still need a matched baseline to measure added time, requests and unnecessary interruptions. Keep successful repairs, missed defects, false alarms, workflow completion and independent code quality visible separately.
  5. Test transfer and reliability. Use coding tasks held out from development, varied project structures and supported languages before expanding benchmark claims. Optional mechanical origin analysis remains off by default; unsupported analysis stays unverified. The latest completed remote CI passed five matrix jobs and failed Windows Node 24. Ubuntu passed its full suite after the cooldown test fix; the Windows failure log is under investigation. Formal benchmark comparisons remain 0/39, with no demonstrated real-model quality gain.

下一步必须改进什么

  1. 让普通工作流可靠运行。评估需要记录无害的方案措辞变化，避免误当成封存审批被破坏；也需要通过可信宿主记录识别合法的原生纠偏后续回合。只接受原始 Apply 回合，会把成功纠偏也拒绝。这两处修正属于评估器，都不改变原先失败的结果。方案变化检查已通过 14 项独立对照，原生后续回合识别已通过 31 项，仍需实际运行验证。
  2. 证明一次真实修复。保留失败候选、触发 RC 的具体证据、纠偏回合及独立核验结果。普通 Apply 自行完成的修复不计为 RC 收益。独立评估夹具已准备好，在最终审查前注入一个明确声明的故障，可安装插件保持不变。全新环境的安装和配置检查已通过，测试现正运行。这可以检验机制，但不能估计 RC 对自然错误的检出率。交付插件不能包含任务专用逻辑。
  3. 对照原始请求检查完整性。提供需求清单能防止已知义务消失，但不能证明清单没有遗漏。最新默认配置运行没有预备清单，审查器选择的九条记录也不代表穷尽覆盖。需同时评估方案遗漏和实现缺失，包括回归义务及必需的用户路径。
  4. 衡量实际帮助与额外负担。最新健康任务使用了 34 次 Pro、30 次 Flash 请求，没有原生纠偏编码启动。仍需匹配基线，才能测量额外时间、请求和不必要的打断。成功修复、漏检、误报、工作流完成及独立代码质量应分别呈现。
  5. 验证迁移与可靠性。先用未参与开发调优的编码任务、不同项目结构和受支持语言验证，再扩大基准结论。可选机械来源分析仍默认关闭，不支持的分析保留为待验证。最近已结束的远程 CI 五项通过、Windows Node 24 失败。冷却测试修正后，Ubuntu 全套检查已通过；Windows 失败日志仍在调查。正式基准比较仍为 0/39，尚未证明真实模型质量收益。
