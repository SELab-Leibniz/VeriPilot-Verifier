Method and evaluation 方法与评估

Runtime Corrector 运行时纠偏器

Runtime Corrector is an OpenClaw plugin that reviews coding work in progress. It compares the original request and OpenSpec plan with what the current code and checks show. When it finds a specific problem that can be fixed, it can ask OpenClaw to correct it before the task ends.

运行时纠偏器是 OpenClaw 的一个插件，用于检查正在进行的编码任务。它把用户的原始请求和 OpenSpec 方案与当前代码及检查结果对照。发现可以修正的具体问题时，插件可要求 OpenClaw 在任务结束前处理。

The target coding workflow

OpenClaw writes the code and runs checks. OpenSpec fixes the order of work: Proposal, Apply, then Archive. Runtime Corrector is an OpenClaw plugin that checks whether the plan and implementation still satisfy the original request.

The plugin reviews configured document writes and handles OpenClaw’s Stop event. Its private reviewer has read-only access to the workspace; OpenClaw performs the edits. The evaluation configures deepseek-flash for coding and deepseek-v4-pro for review.

General usefulness is the priority: healthy work should finish with few interruptions, and a confirmed deviation should receive a specific correction whose result can be checked. The installable package reads each project’s requirements and verification settings. Benchmark cases, task-specific checks and grading logic stay in the evaluation workspace. The benchmark freezes code before Archive so it can grade the delivered patch independently.

目标编码工作流

OpenClaw 负责写代码和运行检查，OpenSpec 固定工作顺序：先 Proposal，再 Apply，最后 Archive。运行时纠偏器是 OpenClaw 插件，用于核对方案和实现是否仍满足原始请求。

插件审查配置范围内的文档写入，并处理 OpenClaw 的 Stop 事件。私有审查器以只读方式检查工作区，代码改动由 OpenClaw 执行。当前评估配置 deepseek-flash 编码，配置 deepseek-v4-pro 审查。

首要目标是在通用编码任务中有用：正常工作应尽量少受打扰；确认偏离后，应给出具体修正，并核验修正结果。可安装插件读取当前项目的需求和验证配置。基准任务、任务专用检查和评分逻辑保留在评估工作区。基准测试在 Archive 前冻结代码，独立评估最终交付的补丁。

Carry the original requirements through to the code

Start with the original request and the existing behavior that must keep working. Split the request into independently checkable requirements, give each a stable ID, and cite its original wording.

  1. Before approval, trace each requirement into the OpenSpec proposal, design, specification scenarios and implementation tasks. Check for omissions, contradictions and tests that cannot establish the promised behavior.
  2. At completion, use the same IDs to trace each requirement through the actual production path and fresh check results. Passing helper tests cannot establish that the user-facing path works.

With strict coverage enabled, the operator supplies the requirement inventory before Proposal. Approval seals that inventory with the exact plan and binds it to Apply. Stop must check every sealed item, including any item the reviewer leaves out of its own checklist. The benchmark list selects production behaviors. The operator still needs to check that list against the full request, including negative constraints and regression expectations; process and conditional duties need explicit checks.

For projects already using strict Proposal coverage, an opt-in PlanReadiness check is implemented and source-tested. It is disabled by default. The host lists every actual Apply checkbox, and the reviewer must return one READY, BLOCKED or UNVERIFIED row per item, backed by acknowledged reads of the current plan. When enabled, strict approval requires every row to be READY. This checks whether the planned work and verification can proceed, separately from coverage of the requested behavior.

The installable package includes this check. Unsupported indented checkbox syntax stays unverified. An earlier plugin revision passed three scripted controls on stock OpenClaw: approval denial, healthy completion and one native repair. An earlier graded trial joined full-plan readiness to approval and final plan preservation, but exposed an unsupported process warning and an origin-parser limit. A readiness judgment proves neither execution nor SDK capability.

A document integrity failure and a code defect need separate judgments. Replacing a verification note can violate the current exact-plan rule while leaving every task and requirement intact. Missing evidence stays UNVERIFIED; it does not by itself establish a defect that warrants a confirmed-deviation repair.

Coverage is only one part of correctness. A plan can mention every feature yet prescribe weak or contradictory tests. The operator’s inventory also needs an independent completeness check: a requirement omitted from that inventory can still escape review.

把原始需求一直核对到最终代码

先明确原始请求，以及必须继续正常工作的既有行为。把请求拆成可独立核验的需求，为每项分配固定编号，并引用原文。

  1. 审批前，逐项查找对应的 OpenSpec 提案、设计、规范场景和实施任务，核对是否遗漏、互相矛盾，或安排了无法证明目标行为的测试。
  2. 完成时，沿用相同编号，逐项追踪实际运行路径和新鲜的检查结果。辅助函数测试通过，还不足以证明用户实际走到的路径正确。

启用严格覆盖检查时，操作员在 Proposal 前提供需求清单。审批把清单与确切的方案版本一同封存，再绑定到 Apply。Stop 必须核对全部封存条目，审查器自己列漏的项目也不能跳过。当前基准清单选取生产行为要求，仍需操作员对照完整原文，核对否定约束与既有行为的保留要求。流程及条件性义务还需明确的检查。

对于已启用严格 Proposal 覆盖检查的项目，可选的 PlanReadiness 检查已实现并通过源码测试，默认关闭。宿主列出 Apply 的每个实际勾选项，审查器须逐项返回 READY、BLOCKED 或 UNVERIFIED，并引用已确认读取的当前方案。启用后，严格审批要求所有条目均为 READY。这项检查核对计划中的工作和验证是否具备执行条件，与功能需求覆盖分别判断。

可安装的插件包已包含这项检查。不支持的缩进勾选语法保持待验证。先前版本的插件通过了三项标准 OpenClaw 脚本对照：拒绝审批、正常完成和一次原生修复。此前一轮已评分的试验连接了完整方案就绪、审批及最终方案保留，但暴露了缺少依据的流程警告和来源解析限制。就绪判断不能证明检查已经执行，也不能证明 SDK 具备相应能力。

文档完整性失败和代码缺陷需要分别判断。替换一条验证说明可能违反当前的精确方案规则，但所有任务和需求仍然保留。缺少证据时应保持 UNVERIFIED，不能仅据此认定存在缺陷并发起以确认偏离为依据的修复。

覆盖只是正确性的一部分。方案可能提到全部功能，却安排了薄弱或互相矛盾的测试。操作员的清单本身也需要独立检查是否完整：未列入清单的原始需求仍可能漏检。

When and how the plugin intervenes

  1. During Proposal, the private reviewer compares drafts with the original request. Strict approval needs a clean review of the complete current plan and coverage evidence for every required item. Covered rows cannot override a blocking semantic finding. A clean recheck can recover without rewriting the files.
  2. During Apply, a write to an approved document triggers an immediate plan comparison. OpenClaw can act on that feedback within its existing run.
  3. At Stop, a confirmed plan change can request native restoration within the correction budget. The admitted run can read the sealed approved text. A genuine scope amendment needs operator approval.
  4. A confirmed code defect can trigger a separate native repair. After either kind of continuation, Stop checks the original requirements against the current code again. Restoration alone does not prove the implementation correct.

The host records admission, dispatch and actual model start. A request alone is not a completed intervention. Only a started correction consumes the repair allowance; the current evaluation permits two corrections in the same workflow. The continuation must retain the authenticated approval and requirement inventory. The evaluator checks that chain independently.

During an active Apply, feedback can prompt OpenClaw to gather evidence within its existing run. After Stop, missing evidence alone currently produces an unverified result without a native follow-up. A separate bounded mechanism for obtaining that evidence is still needed; it must preserve the approved requirements and cannot treat uncertainty as a confirmed defect.

The intended effects are better task completion, fewer missed requirements and fewer unnecessary interruptions at a reasonable review cost. These need live measurements. Scripted controls already verify the dispatch and requirement-continuity mechanisms; they do not establish how accurately Pro diagnoses real work.

The supplied plugin has an optional origin check, disabled by default. It lists observed upstream callers before production coverage is accepted. Each candidate needs a current read and a traced handoff or a source-based exclusion; missing, stale or incomplete evidence stays unverified. Controls on earlier plugin revisions verified the gate, healthy completion and one native repair on an exporter example in stock OpenClaw. Relevance and actual propagation still require semantic judgment. Automatic discovery currently covers JavaScript, TypeScript and ArkTS; strict mode keeps unsupported or incomplete indexes unverified. An earlier graded trial reviewed five original items with this check; the sixth remained unverified because the parser could not bound valid unbraced statements in an upstream callback.

Current citation validation checks source locations, file revisions and bindings. It cannot establish that every diagnostic is true. The recent-history view improves access to evidence, but a reviewer can still make an unsupported execution allegation. Host checks of execution ownership and freshness are proposed work. An unverified review still holds strict approval without establishing a confirmed defect.

插件何时介入，如何纠正

  1. Proposal 阶段，私有审查器把草稿与原始请求对照。严格审批要求当前完整方案的审查通过，并为每项必需需求提供覆盖证据。覆盖记录不能覆盖语义审查中的阻断错误。不改写文件，也可以通过一次干净的复查恢复审批条件。
  2. Apply 阶段，写入已批准文档后立即核对方案。OpenClaw 可以在现有回合内根据反馈自行恢复。
  3. Stop 阶段，确认方案改动后，可在修正额度内请求原生恢复。获准回合可以读取封存原文。主动调整范围仍需操作员批准。
  4. 确认代码缺陷后，可以另行启动原生修复。两类续跑结束后，Stop 都要沿用原始需求重新核对当前代码。方案恢复本身不能证明实现正确。

宿主分别记录准许执行、请求送达和模型实际启动。发出请求还不等于完成干预。只有已经启动的修正才占用额度；当前评估允许同一流程修正两次。续跑必须保留经过认证的审批和需求清单，评估器会独立核验这条执行链。

Apply 仍在运行时，反馈可以促使 OpenClaw 在现有回合内补充证据。Stop 后若仅缺少证据，当前只会记录待验证，不会启动原生续跑。仍需独立、有界的取证机制，保留获批需求，并避免把不确定性当成已确认缺陷。

预期效果是正确完成更多任务，减少漏掉的需求和多余打断，并让审查开销保持合理。这些效果需要实际测量。脚本对照已验证调度和需求延续机制，Pro 在真实工作中的判断准确率仍待验证。

当前交付的插件已加入可选的上游来源检查，默认关闭。接受生产覆盖前，宿主列出观察到的调用者。每个候选都需要读取当前源码，并给出传递链或基于源码的排除理由；证据缺失、过期或发现不完整时保持待验证。先前版本在标准 OpenClaw 的导出器对照中验证了该约束、正常完成和一次原生修复。相关性和实际参数传递仍需语义判断，自动来源发现当前覆盖 JavaScript、TypeScript 和 ArkTS；严格模式下，不支持或不完整的索引保持待验证。此前一轮已评分的试验用这项检查审查了五项原始需求；第六项因解析器无法界定上游回调中的合法无花括号语句而保留为待验证。

当前引用校验会核对原文位置、文件版本和绑定关系，但不能证明每项诊断都属实。近期历史视图改善了证据访问，审查器仍可能提出缺少依据的执行指控。由宿主核对执行证据归属和新鲜度，目前仍是拟开展的工作。待验证的审查仍会阻止严格审批，但不足以认定存在已确认缺陷。

What the 13-task benchmark has shown

SWE-ArkTS-Bench evaluates the plugin on 13 coding tasks. The plan repeats each task three times: 39 OFF/ON pairs and 78 runs. Each pair contains one OFF run and one ON run on the same task. The repetitions are intended to show variation between model runs. OFF disables runtime correction; ON enables it. What still needs to improve

  1. Demonstrate useful behavior on healthy and defective general coding tasks before expanding coverage. Record unnecessary interruptions, missed defects, successful repairs and added time. The newest trial stopped in planning, so reliable real-model completion remains unproven despite passing source tests and scripted controls.
  2. Test whether overlapping document reviews from one multi-file write can be combined without losing early feedback. Keep a fresh whole-plan review before approval; matching document hashes alone do not justify replaying old evidence.
  3. First allow one bounded proof-repair opportunity inside the same review when a current origin receipt is missing, preserving the inventory and deadline. Saved results remain immutable; unsupported analysis, stale source and denied access stay unverified. Automatic evidence gathering after a completed Stop remains further work.
  4. Measure the accuracy of PlanReadiness judgments beyond the completed approval-chain check. Before approval, distinguish optional command examples from mandatory tasks. READY does not attest execution; completion still requires fresh execution evidence. Genuinely required but unavailable checks remain unverified.
  5. Test the revised conditional-obligation guidance with real Pro reviews of inactive triggers, completed active duties and missing active duties. Preserve original conditions and separate unconditional checks; the prompt change does not enforce semantic correctness.
  6. Audit requirement-inventory completeness and planned test adequacy. Check the actual user entry paths, including required alternatives, rather than relying on helper tests alone.
  7. Qualify the PC runtime, then expand to the remaining tasks and coding tasks held out from development. Compare independent outcomes, regressions, missed defects, unnecessary repairs, requests, tokens and elapsed time. Hold Flash coding and correction policy fixed when measuring what Pro adds.

仍需解决的问题

  1. 先用健康与有缺陷的通用任务证明实际帮助，再扩展覆盖面。记录不必要的打断、漏检、成功修复和额外耗时。最新试验停在方案阶段，因此仍需可靠完成真实模型的全过程；源码测试和脚本对照不能代替这项证明。
  2. 测试能否合并一次多文件写入触发的重叠文档审查，同时保留提前反馈。审批前仍需新鲜的完整方案审查，不能只凭文档哈希相同就重用旧证据。
  3. 先在同一审查回合内，为缺少当前来源回执的提交提供一次有界补证机会，保留原清单和时限。已保存的结果仍不可修改；不支持的分析、陈旧源码和权限不足保持待验证。完整 Stop 结束后的自动取证仍是后续工作。
  4. 在已完成的审批链检查之外，测量 PlanReadiness 判断的准确率。审批前把可选命令示例与必需任务分清。READY 不证明已经执行；完成时仍需新鲜的执行证据。确实必需但无法执行的检查应保持待验证。
  5. 用真实 Pro 审查检验修订后的条件性义务指引，分别测试触发条件未成立、成立且已完成、成立但未完成。保留原始条件，另行核对无条件检查；提示词修订不能强制保证语义正确。
  6. 核对需求清单是否完整、计划中的测试是否充分。检查用户实际进入的路径及必需的替代分支，不能只依赖辅助函数测试。
  7. 验证 PC 运行时，再扩展到其余基准任务和未参与开发调优的编码任务。比较独立评分、回归、漏检、多余修复、请求数、令牌用量和耗时。测量 Pro 的贡献时，固定 Flash 编码和纠偏策略。
