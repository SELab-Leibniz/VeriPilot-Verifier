Runtime Corrector 运行时纠偏器

Runtime Corrector is an OpenClaw plugin that reviews coding work in progress. It compares the original request and OpenSpec plan with what the current code and checks show. When it finds a specific problem that can be fixed, it can ask OpenClaw to correct it before the task ends.

The target coding workflow

OpenClaw is the coding agent. It reads and edits the repository, builds the project, and runs checks. OpenSpec sets the order of work. Proposal comes first, followed by Apply and, in normal project use, Archive.

The user’s request specifies what needs to change. The behavior at the start of the task is the reference for what needs to keep working. The approved OpenSpec change spells out the requirements and tasks the reviewer checks against the implementation.

In the current paired evaluation, both arms use deepseek-flash for coding. The ON arm uses deepseek-v4-pro to review the Proposal and the finished code. The trial compares task outcomes and tracks review cost.

For an installed plugin, select custom/deepseek-flash as OpenClaw’s coding model and set plugins.entries.runtime-corrector.config.reviewerModel to custom/deepseek-v4-pro. New projects copy the reviewer setting during /rc-project init. Existing projects also need reviewers.defaults.model set to Pro in their .runtime-corrector/config.yaml, since project role settings take precedence.

Once enabled for a project and session, the plugin uses OpenClaw’s native hooks to review document writes and handle Stop. When OpenClaw writes to a configured OpenSpec document, the plugin runs project rules and checks its meaning against the relevant upstream documents. At Stop, a private reviewer inspects the current workspace with read-only access. OpenClaw makes any resulting edits. In an isolated test with networking disabled, stock OpenClaw loaded the packaged plugin and listed its registered hooks and tools.

The installed plugin reads the current task’s requirements and the project’s verification settings. The benchmark cases, test fixtures, and runner configuration stay in the evaluation workspace. 目标编码工作流

OpenClaw 是编码代理，负责读写代码仓库、构建项目和运行检查。任务按 OpenSpec 的固定流程推进，先拟定提案（Proposal），再实施变更（Apply）。项目通常会在完成后归档（Archive）。

用户的原始请求决定哪些行为需要改变，任务开始时的表现则是判断哪些行为应保留的依据。已批准的 OpenSpec 变更将这些要求写成可以对照代码核查的需求和任务。

当前配对评估中，两组统一用 deepseek-flash 编码。ON 组用 deepseek-v4-pro 审查提案和完成后的代码。试验比较任务结果，同时记录审查开销。

安装插件后，将 OpenClaw 的编码模型选为 custom/deepseek-flash，并把 plugins.entries.runtime-corrector.config.reviewerModel 设为 custom/deepseek-v4-pro。新项目在 /rc-project init 时复制审查模型设置。已有项目还需将 .runtime-corrector/config.yaml 中的 reviewers.defaults.model 设为 Pro，因为项目中的角色设置优先。

在项目和会话中启用插件后，它会通过 OpenClaw 的原生钩子审查文档写入并处理 Stop 事件。OpenClaw 写入配置范围内的 OpenSpec 文档时，插件运行项目规则，再参照上游文档核对内容。到 Stop 阶段，私有审查器以只读方式检查当前工作区，后续改动由 OpenClaw 执行。在隔离且断网的测试中，标准 OpenClaw 加载了打包后的插件，并列出了已注册的钩子和工具。

安装后的插件读取当前任务的需求，并采用项目配置的验证方式。基准任务、测试样本和运行器配置保留在评估工作区。扫描完整安装包时，没有发现 13 个任务的标识、抽样的需求原文或基准运行器名称。

How to tell when work is on or off track

At each checkpoint, ask what the task should have completed by then. Work is off track when current evidence shows a specific requirement for that stage has been violated.

Checking the same requirements at Proposal and Stop

  1. Before Apply. Break the request into requirements that can be checked independently. Give each one a stable ID and cite the original wording. Find the OpenSpec scenario and the tasks that implement and verify it. Confirm that any added requirements have an approved source, then save those links with the approved plan.
  2. At completion. Verify the approved scope. Use the same IDs to trace each requirement through the code path that implements it and the checks that cover it. Confirm which cases ran on the final code, then record whether the evidence supports, contradicts, or leaves each requirement unverified.

With strict coverage enabled, the operator supplies the list of production behaviors that must be delivered. Approval and Apply binding require a clean current full-plan review as well as coverage of each item. A newer blocking review of the same current documents holds approval, even if its coverage rows say covered. A full clean recheck can recover without rewriting the files; unavailable evidence stays unverified. Approving the Proposal fixes that list for the named Apply run. Stop checks each entry against the current code, including any entry the reviewer omitted from its own checklist. The current list is for unconditional production behavior. Document, process, and conditional requirements have their own review rules. This guarantee covers the supplied list. If the list omits an original requirement, that requirement can still escape review, so the list itself needs an independent check.

A document finding and a Stop checklist item can cite the same verified passage in the user’s original message. The identifier records the message revision and exact source bytes, so both stages can refer to the same wording.

Proposal review can record a requirement as covered, missing, or unverified. A record cites the original passage, any supporting lines in the plan, and the exact files under review. Before reporting an omission without a specific line to cite, the reviewer must read all the files in scope. In a local replay, we verified one manually selected trace from request to spec for each archived task.

If one committed Proposal review matches every file in the approved change byte for byte, approval can carry those records into Stop. Stop shows the relevant lines of the plan next to the original requirement. Checking off tasks leaves citations to unchanged spec files valid. A citation to checklist content that changed needs fresh evidence. Stop also checks the implementation and any required checks.

Sudoku’s archived plan gave the unique-solution requirement its own scenario and verification task. The scenario for the chosen mode assumed Diagonal mode was already active, and the seeded check called the generator directly. Neither covered how Start passed the choice from the UI. An independent replay showed ordinary Start passing and seeded Start losing the chosen mode.

The HappyWord 12 spec required 2 vp gaps on the 11-letter battle row. The approved checklist asked for a build and helper tests. It left the rendered row untested.

The HappyWord 13 spec requires a fixed preview manifest URL across backend environments. The checklist tests the URL constants. An end-to-end check would also capture the URL the service actually requests.

A second Sudoku control dropped the unique-solution requirement during Apply and completed the original checklist. Strict validation and the earlier workflow check both passed. The controller now requires each benchmark arm to preserve the approved proposal, design, specs, and task wording. The plugin can do its own comparison when a trusted operator approves the Proposal revision and requests verification after Apply in the same session. Intentional scope changes need a new approval.

Missing evidence leaves a completion claim unverified. Rerun a stale or interrupted check. If an item remains unchecked at the end of Apply, the workflow is incomplete. Request a code repair when evidence identifies a specific defect.

如何判断符合预期或已经偏离？

先明确当前阶段应完成哪些工作，再看证据是否表明其中某项要求未得到满足。有明确冲突时，才判定流程偏离。

检查点符合预期已偏离
提案范围相关文档覆盖所需变更和项目约束，Proposal 通过 OpenSpec 严格校验。遗漏或违背原始需求，或严格校验发现违反规范的内容。
获批方案获批文档除勾选状态外保持原文。当前精确方案策略也会冻结验证说明。未经批准的文字改动违反文档完整性约束。它是否改变需求或损害代码，还需单独核验。
实施进度勾选项对应实际已完成的工作。实施过程中保留未完成项属于正常进度。Apply 宣称完成了当前证据表明尚未完成的工作。
要求实现的行为当前证据覆盖从用户输入到最终结果的实际运行路径，包括任务涉及的其他分支。当前源码或可信检查显示某条必需路径的结果有误。例如，Sudoku 设置种子后执行 Start 时，丢失了用户选择的 Diagonal 模式。
应保留的行为范围内的既有行为仍能正常工作，出现的差异有对应的变更要求。验证确认，本次实现破坏了任务要求保留的行为。

Proposal 和 Stop 核对同一份需求

  1. Apply 前。 把原始请求拆成可以独立核验的需求，为每项分配固定编号并引用原文。找出对应的 OpenSpec 场景、实施任务和验证任务，确认新增要求有经过批准的依据，再把对应关系随批准的方案一并保存。
  2. 完成时。 核对批准的范围。沿用相同编号，逐项查找实现该需求的运行路径和相关检查。确认哪些用例在最终代码上运行过，再记录每项需求是有证据支持、有证据表明未满足，还是仍待验证。

启用严格覆盖检查后，操作员列出必须交付的实际运行行为。审批和 Apply 绑定既要求逐项覆盖，也要求当前完整方案审查通过。同一批当前文档的较新审查若有阻断错误，即使覆盖记录都标为已覆盖，也不能继续审批。完整且干净的复查可在不改写文件的情况下恢复核验；证据不可用时仍保持待验证。Proposal 获批时，这份清单会绑定到指定的 Apply。Stop 逐项核对当前代码，即使审查器自己列出的清单漏掉某一项，也必须检查。当前清单适用于无条件的生产代码行为。文档、流程和条件性需求按各自的规则审查。这项保证覆盖操作员提供的清单。若清单漏掉原始需求，该需求仍可能漏检，因此清单本身也需要独立复核。

文档审查发现和 Stop 清单项可以引用用户原始消息中同一段经过核验的文字。标识指向消息版本和原文的确切字节范围，两个阶段因此能引用同一处原文。

Proposal 审查可记录某项需求已覆盖、存在遗漏或仍待验证。每条记录引用原文、相关的方案行，以及本次审查涵盖的文件。若遗漏无法指向具体某一行，审查器须先读完整个范围内的文件。本地重放为每个归档任务人工选取一项需求，核对它在原文和规范中的对应内容。

如果一份已提交的 Proposal 审查记录涵盖变更中的全部文件，且每份文件都与获准版本完全一致，批准时就可以将这些记录带到 Stop。Stop 会在原始需求旁显示对应的方案段落。勾选进度不会影响对未改动规范的引用，引用已改动的清单内容则需要新证据。Stop 也会核验代码实现和规定的检查。

Sudoku 的归档方案为唯一解要求安排了专门的场景和验证任务。验证所选模式的场景假定对角线模式已生效，带种子的检查也直接调用生成器。两者都没检查 Start 如何传递用户的选择。独立重放显示，普通启动通过，带种子启动丢失了所选模式。

HappyWord 12 的规范要求对战界面中 11 个字母之间的间距为 2 vp。获准的清单安排了构建和辅助函数测试，实际渲染的字母行没有测试。

HappyWord 13 的规范要求各后端环境使用同一个预览清单网址。清单测试的是网址常量。端到端检查还需记录服务实际请求的网址。

另一项 Sudoku 对照在 Apply 中删除了唯一解要求，并完成了原清单的任务。严格校验和当时的流程检查均通过。现在，基准测试控制器要求两组保留已批准的提案、设计、规范和任务文字。可信操作员可在插件中批准 Proposal 版本，并在同一会话的 Apply 结束后请求核对。有意调整范围时需要重新批准。

证据不足时，完成声明仍待验证。 检查过期或中断后应重跑。Apply 结束时还有未勾选项，流程就没有完成。请求修正代码时，要有证据指出具体缺陷。

When and how the corrector intervenes

  1. During Proposal the reviewer cites the original requirement when an OpenSpec document omits or contradicts it. OpenClaw can revise the document before approval.
  2. At Stop the reviewer checks OpenClaw’s claim of completion against the current code and trusted tool results. If the evidence identifies a defect OpenClaw can fix, the reviewer can request a repair in the same session within its budget. The request includes the requirement, the affected path, and the evidence. After OpenClaw edits the code, the reviewer checks the original requirement again with fresh evidence.
  3. Once a plan is approved an authenticated operator can bind it to the next Apply run. When that run settles, Stop lists changed files and reports any confirmed departure from the plan. If the checklist is incomplete or evidence is unavailable, the result stays unverified.
  4. When Stop confirms an approved-plan change the plugin can request a native restoration run within the shared correction budget. The admitted run can read the sealed approved text. Its successor keeps the same original requirement list and must pass the ordinary code review. An intentional amendment needs new operator approval. The evaluator independently checks restoration and requirement continuity.

Work continues without repair when the checkpoint passes. The plugin records when it finds an issue, when it delivers the repair request, and when the repair begins. Only the start counts against the session’s repair allowance.

The reviewer checks different requirements at the end of a stage, at task completion, and when an external blocker stops work. The current code can show what was implemented. To confirm a check ran, the reviewer needs a trusted execution record for the same snapshot. A failed pinned public test can justify a repair if it covers an original requirement and the current code confirms the problem.

In the benchmark, the reviewer reports confirmed deviations from the original request. A project can also configure a documented set of requirements and ask the reviewer to check them item by item. A requirement can remain unverified when the evidence is unavailable or the budget runs out.

When the benchmark enables the plugin’s approval check, the ON runner compares the plugin’s Proposal preview with its own sealed Proposal. It approves the matching version and binds it to the first Apply run. The result records the plugin’s verdict for that run when available. Both arms also go through the same independent workflow and grading checks.

何时介入，如何拉回正轨？

  1. Proposal 阶段。 审查器发现 OpenSpec 文档遗漏或违背原始要求时，会引用对应的原文。OpenClaw 可在方案批准前修改文档。
  2. Stop 检查点。 审查器用当前代码和可信的工具结果核对 OpenClaw 的完成声明。证据指向可修复的问题时，审查器可在预算内请求 OpenClaw 在原会话中做一次修正，并说明哪项要求未满足、涉及哪条路径、依据是什么。OpenClaw 修改后，审查器用新证据复核原始要求。
  3. 方案获批后。 通过身份验证的操作员可把方案绑定到下一次 Apply。运行结束时，Stop 列出改动的文件，并报告已经确认的方案偏离。清单未完成或无法取得证据时，结果记为待验证。
  4. Stop 确认获批方案被改动时。 插件可在共享修正额度内请求原生恢复回合，获准回合可以读取封存的获批原文。后续回合沿用同一份原始需求清单，仍须接受正常的代码审查。主动修订方案需要操作员重新批准。评估器独立核对恢复结果和需求是否延续。

检查通过时，流程直接继续。插件分别记录问题何时发现、修正请求何时送达，以及修正何时开始。只有实际启动的修正才占用会话额度。

单个阶段结束、整个任务完成和遇到外部阻塞时，审查的要求各不相同。当前代码可以说明实现了什么。要确认某项检查运行过，需要同一代码快照的可信运行记录。固定版本的公开测试失败，如果对应某项原始要求，且当前代码也能证实问题，就可以据此请求修正。

基准测试只报告有证据确认的偏离，判断依据是原始请求。项目也可以配置注明来源的需求基线，请审查器逐项检查。证据不足或预算用完时，相应需求可保留为待验证。

基准测试启用插件的审批检查时，ON 组运行器会把插件预览的 Proposal 与自己封存的版本逐项比对。一致后，运行器批准该版本，并将它绑定到首次 Apply。结果会记录插件对这次运行给出的判定。两个试验组都要接受相同的独立流程检查和评分。

Expected effects

  • Complete more tasks correctly. Count fully resolved tasks and compare which target tests gained or lost passes. Use independent regression tests to check whether existing behavior still works.
  • Finish more workflows within their approved scope. Record whether strict OpenSpec validation passed, whether the checklist kept its wording, and whether each task was completed. Count the candidates eligible for independent grading.
  • Keep repair costs proportionate. Check whether each repair resolves the finding. Count missed defects and unnecessary interruptions, and measure the additional requests, tokens, and minutes spent reviewing and repairing.

Controlled tests have demonstrated repairs and reproduced cases the checks missed. The full benchmark is needed to measure how often live runs improve, how often the plugin intervenes unnecessarily, and what it costs.

预期效果

  • 正确完成更多任务。 统计完整解决的任务数，对比哪些目标测试转为通过或失败。用独立回归测试判断原有行为是否仍正常。
  • 让更多流程按已批准的范围完成。 记录 OpenSpec 是否通过严格校验、清单是否保持原文、任务是否全部完成，再统计具备独立评分资格的候选版本。
  • 把修正开销控制在合理范围内。 核对每次修正是否解决了发现的问题。记录漏掉的已知缺陷和被误打断的正常运行，以及审查和修正增加的请求数、令牌用量和耗时。

受控试验验证了若干修正，也复现了现有检查漏掉的问题。完整的基准测试还需统计实际运行中有多少得到改善、有多少被插件误打断，以及增加了多少开销。

SWE-ArkTS-Bench results

SWE-ArkTS-Bench tests whether the plugin helps on 13 coding tasks. Each task is scheduled three times, for 39 OFF/ON pairs and 78 runs. Each pair uses the same task input, OpenClaw, OpenSpec, coding model, public checks, and time budget. OFF disables runtime correction and ON enables it.

The schedule alternates which arm goes first. Before live runs, the evaluator calibrates against the exact starting version and a known reference solution. OpenClaw can use the public feature and regression checks while it works. The hidden tests and reference patches stay in the private grading environment. The grader receives the frozen implementation patch and returns totals for target and regression tests.

The quality comparison includes only pairs with two verified grades from the same grading setup. Ungraded runs still count toward workflow and cost measurements.

In the restarted Flash/Pro experiment, OFF ended Apply with public checks passing and 12 of 13 tasks checked. One linter item remains unverified. Three verification notes were added to the approved checklist file without changing the task wording, which triggered the exact-plan rule. This is a document integrity failure; requirement drift and code quality need separate evidence.

ON passed complete-plan review and authenticated approval for all six original requirements. It passed the public checks and marked all 20 tasks complete, then added one verification note. The early guard and Stop detected that change. The benchmark controller restored the approved text and 20 checkmarks, but its new run lost the six-requirement binding. A generic Stop cleared four objects; the evaluator correctly refused to count that as the required six-item review. Plugin-owned repairs: zero.

An interrupted design review recovered on recheck without changing the design. A later recheck falsely alleged fabricated verification. Independent audit found fresh build, test and acceptance receipts with matching production snapshots. The reviewer had read a truncated transcript containing the earlier planning prompt, without reaching those receipts or reading the source. The installable build now checks approval drift before explicit semantic rechecks and supplies a bounded recent-message view with full-history navigation. The updated installed plugin now has native plan restoration, and the evaluator recognizes its authenticated continuation chain. Scripted stock OpenClaw controls verified requirement continuity through restoration and a subsequent code repair. The paid pair used the earlier build, so its failed workflow outcome remains unchanged.

An independent audit found normative coverage for all six requirements, with a verification gap at the selected-mode entry point: the plan makes the actual UI handoff an optional manual check. Test task 5.3 also asks for a board invalid under Standard rules, while the design asks for a puzzle uniquely solvable only with diagonal constraints. The literal task conflicts with the shared row, column and box rules. Coverage records therefore need separate checks for test adequacy and internal consistency.

When OpenClaw’s native records confirm that a repair began, the evaluator can compare the patch sealed just before the first repair with the final patch. That comparison shows which tests started passing or failing. The benchmark also records workflow outcomes, confirmed repair starts, and request costs for attempted runs.

All task descriptions stayed unchanged; this edit alone does not establish requirement drift or poor code. It made 61 Flash requests in about 9.5 minutes. 在 macOS 上，另外两个标准 OpenClaw 对照都批准了同样的两项需求，并产出同一份可用补丁。两项都有当前源码证据时，Stop 记录为 NO_DEVIATION_FOUND。只提供一项的证据时，另一项仍为 UNVERIFIED，即使 Apply 已勾选全部任务。两次运行均未启动修正。

第三个脚本对照中，Stop 确认了一处缺陷，另一项需求则缺少证据。OpenClaw 在原会话启动了一次修正。复查沿用已批准的需求清单，核验了两条实际运行路径，结果为 NO_DEVIATION_FOUND。修正后的代码通过了独立检查。

Challenges and next checks

  • For longer tasks, measure how often the operator’s list captures all required production behavior and how often the reviewer finds enough current evidence for each item.
  • Early document reviews can pass while the full plan is unavailable. The previous paid ON run spent over five minutes on its first two such reviews. Compare partial-draft review with review at the complete Proposal checkpoint, measuring missed defects as well as delay.
  • Measure what Pro adds by comparing reviewer models with Flash coding and the correction policy held fixed.
  • Document-review validation checks cited locations and file bindings; it does not establish the truth of every diagnosis. The recent-history view improves access to evidence, but an unsupported execution allegation can still become a blocking error. Add explicit checks for the ownership and freshness of execution evidence. Missing evidence should remain unverified and should not authorize a confirmed repair.
  • In the archived macOS Sudoku 11 pair, each arm hit a workflow failure and neither earned a formal grade. Compare live quality once both arms complete the workflow and have independently verified scores.
  • The earlier pair exposed a lost requirement binding after controller-owned restoration and a false allegation based on truncated history. The updated plugin has native restoration and a bounded recent-history view. The approved new pair is testing these changes with Flash coding, Pro reviews and the same 120-minute business limit per arm. A local scripted success does not establish live reviewer accuracy or useful repairs.
  • Check the paths users actually take. The development build asks for separate evidence when branches in the same function dispatch to the same destination. The scripted Sudoku test repaired the defective path and left the healthy control alone. Live runs need to show how often the reviewer makes that distinction and whether its repairs work.
  • Measure the cost of review. Across the eight comparable pairs in the earlier 20-pair archive, seven had the same results and one ON candidate lost target and protected test passes. For the two pairs with complete attribution, ON made 154 requests, including 76 for review. OFF made 80. The current campaign will track cost alongside test outcomes.
  • Review the exact-plan rule’s false-positive risk. Added verification notes can trigger it even when requirement and task wording stay unchanged. In the previous OFF run, removing those notes alone would still leave a linter task incomplete. The new OFF run completed its checklist and replaced one verification note while keeping all task descriptions unchanged. Assess whether rejecting that edit helps the workflow.
  • In one paid Sudoku run, the document reviewer spent 26 requests on a changed tasks.md and reported no findings. The new early check saved three requests in a separate scripted control. Measure its savings and the model’s response in live runs.
  • Qualify the PC test environment. The unmodified device and Local Test routes still fail. The experimental Preferences unit backend completed all ten cases, but its starting versions retain two target-test errors and four regression failures. Resolve the failures and validate the backend’s behavior independently. Keep its results separate from native grading.
  • Test the plugin on held-out coding tasks. The shipped package passed six scripted controls across Node.js and Python. In each language, the faulty OFF patch failed its independent checks, ON started one repair and passed, and the healthy ON control needed no repair. Live tasks held out from development are still needed to measure quality gains and unnecessary work.

当前挑战与下一步验证

  • 在较长的任务中，统计操作员的清单能否涵盖所有应交付的生产行为，以及审查器能否逐项找到足够的当前证据。
  • 完整方案尚未齐备时，早期文档审查也可能通过。上一组付费 ON 运行的前两次此类审查合计用时超过五分钟。后续应比较局部草稿审查与完整 Proposal 检查点审查，同时衡量漏检和延迟。
  • 固定使用 Flash 编码和相同的纠偏策略，只替换审查模型，测量 Pro 带来的收益和开销。
  • 文档审查校验会核对引用位置和文件绑定，但不能证明每项诊断都属实。近期历史视图改善了证据访问，缺少依据的执行指控仍可能被接受为阻断错误。需要明确核验执行证据的归属和新鲜度。证据缺失时应保持待验证，不能据此发起以确认缺陷为依据的修复。
  • 归档的 macOS Sudoku 11 配对中，两组各遇到一处流程故障，均未取得正式评分。待两组都完成工作流并取得经核验的独立评分后，再比较实际运行的质量。
  • 此前的配对暴露了控制器恢复后丢失需求绑定，以及截断历史引发错误指控的问题。更新后的插件已加入原生恢复和有大小上限的近期历史视图。已获批准的新配对正在检验这些改动，仍由 Flash 编码、Pro 审查，每组业务时限为 120 分钟。本地脚本成功还不能证明实际审查判断准确或修复有帮助。
  • 核查用户实际走到的路径。 如果同一个函数有多个分支调用同一个目标，开发版会要求对每条路径分别提供证据。Sudoku 脚本测试修正了有缺陷的路径，正常对照直接通过。还需在实际运行中统计审查器能否区分这两种情况，以及修正是否有效。
  • 测量审查开销。 早期归档的 20 对运行中，8 对可比。7 对结果相同，另有 1 对的 ON 少通过了目标测试和受保护的回归测试。有两对保留了完整的请求记录，其中 ON 发出 154 次请求，76 次用于审查，OFF 发出 80 次。正式评估会同时记录开销和测试结果。
  • 复核精确方案规则的误报风险。需求和任务原文保持不变时，追加验证说明仍会触发该规则。上一组 OFF 即使删掉这些说明，仍有一项代码规范检查未完成。新 OFF 完成了清单，替换了一条验证说明，所有任务原文仍保持不变。需要评估拒绝这类编辑是否有助于流程。
  • 一次付费 Sudoku 运行中，文档审查器为改动后的 tasks.md 发出了 26 次请求，未报告问题。新的提前核对在另一项脚本对照中节省了 3 次请求。实际运行还需测量节省量，以及模型如何响应反馈。
  • 验证 PC 测试环境。 未修改的设备和 Local Test 路径仍存在故障。实验性 Preferences 单元测试后端已执行全部 10 个任务，但起始版本仍有两项目标测试错误和四项回归失败。需要查清失败原因，并独立核验后端行为。其结果继续与原生评分分开记录。
  • 用未参与调优的任务测试插件。 可安装的插件在 Node.js 和 Python 中通过了六组脚本对照。每种语言中，有缺陷的 OFF 补丁未通过独立检查，ON 启动一次修正后通过，正常的 ON 对照无需修正。仍需在未参与调优的任务上实际运行，以测量质量改善和多余的工作量。
